# MapleForge — 版本抽象式楓之谷伺服器・架構設計書

> 代號 **MapleForge**（暫定，可改名）。本文件是「把舊 OdinMS v113 私服重構成一個乾淨、可超越、可升級版本的全新伺服器」的架構準繩。
> 技術主力：**C# / .NET 8**。北極星：**版本抽象（Version Abstraction）**。
> 撰寫：2026-05-31。狀態：草案 v0.1，待作者審閱。

---

## 0. 這份文件要解決的問題

舊伺服器（OdinMS / 風迷 TMS113 系，~360 個 Java 檔）的根本問題不是「用 Java」，而是 **v113 被寫死在每一個角落**：opcode 數字、封包結構、加密、WZ 格式、遊戲邏輯全部糾纏在一起。所以：

- 想「**超越舊伺服器**」→ 要的是乾淨分層、可測試、可維護的核心。
- 想「**未來升級楓之谷版本**」→ 要的是把「版本獨有的東西」與「通用遊戲邏輯」徹底切開。

這兩件事其實是**同一個架構決定**：把伺服器拆成 **版本無關的核心** ＋ **可替換的版本適配層（Version Adapter）**。

## 0.5 對抗式 Review 修訂摘要（v0.2，2026-05-31，最高權威・蓋過下文衝突處）

本設計書經三位 AI（協定/多實例/完成度三攻擊面）5 輪對抗式 review，結論：**方向正確，但兩大支柱被過早、過強地承諾**。核心修訂如下，與下文衝突時以本節為準：

1. **「v113-first，抽象後長」**：刪除「加 adapter 不動 Core/Application」「handler 天生跨版本」這類承諾——那是 sample size=1 的假抽象。**M1~M2 先把 v113 寫具體**（`Maple.Protocol.V113` 直接定義 reader/writer/handshake/login DTO，Application 只吃 v113 use-case command）。**版本抽象接縫延到 M3/M4 才提取**：依據是「≥2 個封包族出現相同核心語意」才抽，而非預先幻想 enum。版本差異是**語意級**，接受 adapter 層會有版本特化 DTO，但**不准滲進 Core/Application**。
2. **零 static 降級為可稽核**：原則 6 改為「**Core/Application 嚴格禁 static 可變狀態；Adapter/Infra 層務實放寬**（cipher state、EF model cache、WZ 檔案快取本質上是 process/static），每個實例以 `instanceId` 追蹤」。M1 起加 **Roslyn analyzer** 只掃 `Core`/`Application`；第三方 static（EF、MapleLib WZ key、Serilog）列**審核清單**而非靜默接受。
3. **Cipher 介面方向化**：以 `IVersionCipherFactory.CreateSessionPair(iv) → (recv, send)` 取代 `IServerVersion.CreateCipher`，用介面強制「每連線每方向各一個有狀態 cipher」。**現在改零成本，M1 寫完 Session 再改要動已寫碼。**
4. **誠實的故障隔離**：明寫「**單進程多實例不提供故障隔離**——A crash 會終止整個進程」。緩解：每個實例的 `StartAsync` 外層包 try/catch，降級為「該實例停＋記 log」（~10 行）。**真隔離＝多進程，延到 M6+**。
5. **客戶端多開升為正式 workstream（M2.5）**：「雙伺服器」demo 約一半風險在客戶端（單一 mutex＋`FindWindow`＋共享記憶體、每 port 需 patch 過的 exe）。不解這塊，多實例支柱 demo 不出來。最具說服力的「v113＋新版本並排」還會撞上 MapleLib 的 `static` 版本綁定 WZ key。
6. **WZ 二進位 reader 延到 M3**：登入（M1/M2）不需要 WZ；先硬編/跳過。WZ-reader vs XML 的選擇不變（仍是二進位 reader），**只是時程移到 M3**。並明定 WZ 共享快取所有權（process 級單例 vs 每實例）＋檔案開啟需 `FileShare.Read`。

**信心**：直接照原 v0.1 進 M0 ≈ 45%；照本節修訂後 ≈ **75–88%**。修訂後**可進 M0**（修訂里程碑見 §7）。

## 1. 設計原則（修訂版）

1. **版本無關優先**：核心遊戲邏輯（角色、地圖、戰鬥、技能、背包）**只認邏輯概念，不認版本數字**。任何「v113 才這樣」的東西都關進 adapter。
2. **乾淨架構 / 依賴反轉**：依賴方向永遠由外往內。`Core`（領域）不依賴任何 I/O、網路、資料庫、版本。
3. **可測試**：協定加密、封包編解碼、技能公式都要能在沒有真客戶端的情況下用單元測試＋黃金樣本（golden test）驗證。
4. **以舊碼為「行為神諭」**：~360 檔 Java 不是要逐行翻譯，而是當作「v113 到底怎麼運作」的**規格參考**，用來對照、寫測試。
5. **每個里程碑都能跑**：不做「半年後才看到第一隻怪」的大爆炸重寫；每階段都留一個可啟動、可登入的伺服器。
6. **分層式零全域狀態（修訂，見 §0.5）**：**`Core`/`Application` 嚴格禁止任何 `static` 可變欄位/單例**（M1 起以 Roslyn analyzer 強制）。**Adapter/Infra 層務實放寬**——cipher state、EF model cache、WZ 檔案快取本質上是 process 級的，無法靠 DI 消滅；改以每實例 `instanceId` 追蹤＋第三方 static 審核清單管理。這仍是「多實例同時運行」的前提，但承認它是工程紀律＋工具稽核，而非一句口號。

## 2. 版本抽象核心（本專案的靈魂）

一個「楓之谷版本」之間到底差在哪？只差這四樣 —— 全部抽成介面，關進 adapter：

| 版本獨有的東西 | 抽象介面 | v113 的實作 |
|---|---|---|
| 封包加密 | `IPacketCipher` | AES-OFB ＋ 自訂 shuffle（對照舊碼 `MapleAESOFB` / `LoginCrypto`） |
| opcode 數字表 | `IOpcodeTable` | v113 的 `RecvPacketOpcode` / `SendPacketOpcode` 數值 |
| 封包結構（欄位順序/長度） | `IPacketSerializer<T>` | v113 各實體的序列化（對照舊碼 `MaplePacketCreator` 等） |
| WZ 資料格式 | `IDataProvider` | v113 的 WZ（先沿用既有 XML 萃取，或 C# WZ reader） |

### 2.1 關鍵手法：邏輯 opcode，而非數字 opcode

舊碼的 handler 直接 `switch (opcode 數字)`。新核心改成：

```
封包進來 → adapter 把【數字 opcode】翻譯成【邏輯 opcode（穩定 enum）】
        → 路由到「版本無關的 handler」
        → handler 操作領域模型
        → 要送封包時，adapter 把【領域意圖】序列化成【該版本的 bytes】
```

```csharp
// Maple.Core —— 版本無關，永遠不變
public enum ClientMessage { LoginPassword, CharSelect, MovePlayer, AttackMelee, NpcTalk, /* ... */ }
public enum ServerMessage { LoginStatus, CharList, SpawnPlayer, ShowDamage, NpcDialogue, /* ... */ }

// Maple.Versioning —— adapter 要提供的東西
public interface IOpcodeTable {
    bool TryMapRecv(short wireOpcode, out ClientMessage logical);
    short MapSend(ServerMessage logical);
}

public interface IPacketCipher {            // 有狀態：每次呼叫推進 IV，只屬於「一個連線的一個方向」
    void Decrypt(Span<byte> buf);
    void Encrypt(Span<byte> buf);
    int  ReadLength(ReadOnlySpan<byte> header); // v113 的 4-byte 加密長度頭
}

public interface IVersionCipherFactory {    // §0.5 修訂：用介面強制「每連線每方向各一個 cipher 實例」
    (IPacketCipher recv, IPacketCipher send) CreateSessionPair(ReadOnlySpan<byte> iv);
}

public interface IServerVersion {
    int  VersionNumber { get; }          // 113
    IOpcodeTable          Opcodes { get; }
    IVersionCipherFactory Ciphers { get; }   // 取代舊的 CreateCipher（方向化防呆）
    IPacketSerializer     Serializer { get; }
    IDataProvider         Data { get; }
}
```

> **效果**：要支援「楓之谷新版本」時，**不動 `Core`/`Application` 任何一行**，只新增 `Maple.Adapters.Vxxx`（一張 opcode 表、一份 cipher、一組 serializer、一個 WZ 綁定）＋換 WZ 資料。這就是「以前敢想卻不敢做」現在做得到的事。

## 2.2 第二支柱：多實例同時運行（私服界沒做到的事）

**目標**：同一台機器、甚至同一個進程，**同時跑多個完全獨立的伺服器實例**——可以是兩個 v113 世界，也可以是「一個 v113 ＋ 一個未來版本」並排。

### 為什麼老私服只能開 1 個（根因）
OdinMS 血統的致命傷是**滿地 `static` 全域單例**：`DatabaseConnection`、`ChannelServer`、`World` 註冊表、設定、資料提供者全是靜態的。兩個伺服器在同一進程會共用同一份全域狀態而互相踩爛；加上**埠/IP/DB schema 寫死**，根本開不出第二個。而且這是架構級的病，**事後補不回來**。

### 我們的解法：`ServerInstance` 為一等公民
- **零全域狀態**（原則 6）：沒有 `static` 可變欄位。所有東西都掛在一個 `ServerInstance` 物件上、靠 DI 注入。
- 每個 `ServerInstance` 自帶獨立的：

```csharp
public sealed class ServerInstance {        // 一個「世界」＝一個實例，彼此零共用
    public string         Name { get; }      // "爸爸的楓之谷"、"測試新版本"…
    public IServerVersion Version { get; }    // ← 可以是 V113，也可以是未來的 Vxxx
    public NetworkEndpoints Ports { get; }    // 各自獨立的 login/channel 埠
    public IDataProvider  Data { get; }       // 各自的 WZ
    public IDbContextFactory Db { get; }      // 各自的資料庫/連線字串
    public WorldRegistry  World { get; }      // 各自的頻道/角色註冊表（非 static！）
    public GameSettings   Settings { get; }   // 各自的 expRate/名稱/訊息…
}
```

- **Generic Host** 讀設定裡的一個 `instances[]` 陣列，為每個項目建立一個 `ServerInstance` 並以 `IHostedService` 拉起。要開第二個伺服器＝在設定裡多加一筆，**程式碼一行不改**。

```jsonc
// appsettings.json（示意）
"instances": [
  { "name": "爸爸的楓之谷", "version": 113, "loginPort": 8484, "db": "maple_v113",  "expRate": 4 },
  { "name": "新版本測試",   "version": 113, "loginPort": 8584, "db": "maple_test", "expRate": 1 }
]
```

### 誠實的邊界：這道牆有兩半
- **伺服器端（我們完全解決）**：多個獨立伺服器同時運行 ← 本架構的核心紅利。
- **客戶端端（另一回事）**：要讓「兩個客戶端」分別連兩個伺服器，需要 ① 各伺服器用不同 login 埠（我們天生支援）＋ ② 客戶端多開（繞過 MapleStory.exe 單一實例 mutex）——作者既有的 `視窗化(dxwnd)` / `單人測試登入器` 已是這塊的雛形。兩者分開看待，不混為一談。

> **這支柱必須從第一天執行**：任何 PR 引入 `static` 可變狀態都視為架構違規。這正是別人補不回來、而我們能做到的原因。

## 3. 方案結構（.NET Solution）

```
MapleForge.sln
├─ src/
│  ├─ Maple.Core/            領域模型 + 邏輯 opcode enum + 介面（零 I/O，純邏輯，可單測）
│  ├─ Maple.Application/     use case / handler（key = 邏輯 opcode），編排領域
│  ├─ Maple.Net/             TCP server、System.IO.Pipelines、Session、封包框架（版本無關）
│  ├─ Maple.Persistence/     文件模型 + LiteDB（每實例一檔）+ Repository
│  ├─ Maple.Content/         IDataProvider（WZ）抽象與載入
│  ├─ Maple.Scripting/       Jint 腳本宿主 + NPC/portal/quest/reactor 管理（沿用既有 .js）
│  ├─ Maple.Versioning/      IServerVersion 抽象 + 版本登錄表
│  ├─ Maple.Adapters.V113/   ★ v113 適配層：opcode 表、AES-OFB+shuffle、serializer、WZ 綁定
│  ├─ Maple.Host.Login/      登入伺服器進入點
│  ├─ Maple.Host.Channel/    頻道/世界伺服器進入點
│  └─ Maple.Host.Shared/     Generic Host、DI、設定、logging 共用裝配
└─ tests/
   ├─ Maple.Core.Tests/
   └─ Maple.Adapters.V113.Tests/   ★ 加密/封包黃金樣本測試（對照真客戶端封包）
```

依賴方向：`Host → Adapters/Net/Persistence/Scripting → Application → Core`。
`Core` 不依賴任何人。`Adapters.V113` 依賴 `Versioning` 介面，不被核心依賴。

## 4. 分層職責

### 4.1 `Maple.Core`（領域，純）
- 純遊戲模型：`Character`、`MapleMap`、`Monster`、`Skill`、`Inventory`、`Party`…
- 邏輯 opcode enum（`ClientMessage`/`ServerMessage`）。
- 領域介面（repository 介面、`IDataProvider`、`IServerVersion`…）。
- **規則**：不准 `using` 任何網路/DB/版本/檔案 API。所有外部世界都靠介面。

### 4.2 `Maple.Application`（用例 / handler）
- 每個邏輯 opcode 一個 handler（取代舊碼 `PlayerHandler`/`NPCHandler`… 的巨型 switch）。
- handler 只認領域模型與邏輯 opcode → **天生跨版本**。
- 例：`MovePlayerHandler` 收到 `ClientMessage.MovePlayer`，更新 `Character.Position`，廣播 `ServerMessage.SpawnPlayerMovement`。

### 4.3 `Maple.Net`（網路，版本無關）
- 用 **`System.Net.Sockets` + `System.IO.Pipelines`** 做高效非阻塞 TCP（現代、可控、無第三方依賴；替代舊碼的 Apache MINA）。
- `Session`：每連線一個，持有 `IPacketCipher`（由當前 `IServerVersion` 建立）。
- 流程：讀 4-byte 頭 → `cipher.ReadLength` → 收滿 body → `cipher.Decrypt` → 取數字 opcode → `Opcodes.TryMapRecv` → 丟給 `Application` 的 handler。
- 送封包反向走。
- 備案：若想要 batteries-included pipeline，可換 **DotNetty**（Netty 的 .NET 移植，貼近舊團隊的 Netty 經驗）；但預設用 Pipelines。

### 4.4 `Maple.Persistence`（2026-05-31 經圓桌改為**文件模型 + LiteDB**）
- **資料模型＝文件**：角色 = 一份完整文件（屬性+多分頁背包+技能+任務+buff+倉庫+寵物），Load/Save 是**原子單元**。對楓之谷 5-6 層巢狀資料阻抗失衡歸零；存檔＝一次 `ReplaceOne`（原子），無跨表交易/補償地獄。
- **引擎＝LiteDB**（純 C# 內嵌、零維運）：**每實例一個 `.db` 檔** → 完美呼應多實例支柱（隔離、備份=複製檔案、搬遷=複製檔案）。
- Repository 介面定義在 `Core`（如 `IAccountRepository`、`ICharacterRepository`，核心方法 `LoadCharacter`/`SaveCharacter`），實作在這層（取代舊碼 singleton `DatabaseConnection`）。
- **跨文件一致性**（玩家交易/楓幣轉移）：用輕量 **Saga**（`transactions` 集合狀態機 `pending→committed` + 冪等重試），不依賴 DB 原生跨文件交易。
- **未來擴展路徑**：Repository 介面不動，真要長期營運/多機共資料時換 **MongoDB** 或 **PostgreSQL+JSONB** 實作層（模型不變）。
- **待實測**：高頻定時存檔（每 3 分鐘 ~100 角色並發 `ReplaceOne`）下 LiteDB 的寫入鎖競爭——理論上此規模可接受，M2 後做壓力測試確認。

### 4.5 `Maple.Content`（WZ 資料）
- `IDataProvider` 抽象資料讀取（地圖、怪物、技能、道具、字串…）。
- **決議：直接做 C# 二進位 WZ reader**（解析 v113 `.wz`：目錄、property、PNG/canvas、加密字串）。可參考既有 C# WZ 解析作法（MapleLib/reWZ 思路），但包在 `IDataProvider` 後面，核心不知道格式。
- 提供記憶體快取與惰性載入；多實例可共享唯讀資料快取（唯讀 → 不違反零全域可變狀態）。

### 4.6 `Maple.Scripting`
- **Jint**（純 C# 的 JavaScript 直譯器）→ **直接沿用現有 `scripts/npc/*.js` 等內容資產**，不必重寫 NPC。
- 解決舊碼的 **Nashorn 已死** 問題（這是辯論中公認、跟語言無關都得處理的真技術債）。
- 腳本 API（`cm.sendOK` / `sendNext` / `sendGetNumber`…）重新實作成乾淨的宿主物件。
- 長期可選：把核心 NPC 改寫成 C# 或 DSL；但內容腳本維持可熱載。

### 4.7 `Maple.Host.*`（進入點）
- **.NET Generic Host**：DI、`IConfiguration`、`ILogger`、生命週期一次到位（這就是你要的「標準乾淨結構」）。
- 設定用 `appsettings.json` ＋ 強型別 Options，**取代 `settings.ini`**（expRate、頻道數、DB、port…）。
- **多實例裝配**：Host 讀 `instances[]`，為每筆建立獨立 `ServerInstance`（§2.2）並以 `IHostedService` 拉起；Login/Channel 服務都掛在各自的實例下。
- **故障隔離（誠實聲明，§0.5#4）**：**單進程多實例不提供故障隔離**——任一 `IHostedService` 未捕獲例外會終止整個進程，A crash 連帶殺死 B。緩解：每個實例的 `StartAsync`/tick 外層包 try/catch，把崩潰降級為「該實例停止＋記 log」而非浮出 Host。**真隔離需要多進程，列為 M6+ 選項，不在本版承諾內**（.NET 8 已無 AppDomain 可用）。

## 5. 並發模型

- **每連線**：async socket 讀寫迴圈（`await` 驅動，非 thread-per-connection）。
- **遊戲世界**：每張地圖 / 每頻道一個 **tick 迴圈**（怪物 AI、狀態、重生）。
- 跨執行緒指令用 **`System.Threading.Channels`** 排進地圖的單一處理緒，**單地圖序列化處理**以避免共享可變狀態的鎖地獄（這正是辯論中 Rust/Go 最痛、而我們用 actor 風格輕鬆解掉的點）。
- 規模現實：同時上線 <100，效能不是瓶頸；**設計目標是清楚與正確，不是吞吐**。

## 6. v113 作為「第一個 adapter」

`Maple.Adapters.V113` 要交付的東西，全部以舊 Java 為規格參考：

1. **Cipher**：在 C# 重現 AES-OFB ＋ v113 shuffle（參考 `tools/MapleAESOFB.java`、`client/LoginCrypto*.java`）。→ 用**黃金樣本測試**：拿真客戶端握手封包驗證加解密 bit 級一致。
2. **Opcode 表**：把 `RecvPacketOpcode` / `SendPacketOpcode` 的數值對應到邏輯 enum。
3. **Serializer**：v113 各封包結構（參考 `MaplePacketCreator`、`tools/packet/*`）。
4. **WZ 綁定**：接上既有 v113 資料。

> 客戶端是 2010 二進位、協定寫死、一個 byte 都不能錯 —— 所以這層的策略是「**精準重現 + 黃金測試**」，舊 Java 就是我們的對照真值來源。

## 7. 分階段里程碑（每階段都可啟動）

> **修訂版（§0.5）：先求能動，再求乾淨。v113 全程硬編具體，抽象延到 M3 才長。**

| 里程碑 | 內容 | 驗收（看得到的反應） |
|---|---|---|
| **M0 骨架** | Solution + Generic Host + DI + **單一** appsettings + logging + 空 `LoginHandler` stub（只聽 port，不解碼） | server 能啟動、listening、讀得到設定 |
| **M1 管線打通** ★ | `Maple.Net` + **硬編** v113 cipher（`CreateSessionPair`）+ **硬編** opcode 表 + 握手；**跳過 WZ** | **真 v113 客戶端連上、伺服器回「登入失敗」(硬編錯誤碼)** → 證明封包管線端到端通 |
| **M2 登入成功** | EF Core schema + 帳密驗證 + 角色列表/建立；**加 Roslyn analyzer** 守 Core/Application | 客戶端**登入成功**、能建角/選角 |
| **M2.5 客戶端啟動器** | patch/mutex-bypass 驗證 + 雙客戶端連不同 loginPort（沿用 dxwnd/單人登入器） | **兩個登入畫面同時開著** |
| **M3 進地圖＋抽象提取** ★ | Channel host + **C# 二進位 WZ reader** + 進場 + 移動；**此時才把版本抽象接縫長出來**（已有真封包可依據） | 角色進地圖、能走動、被看到 |
| **M4 戰鬥** | 怪物生成/AI + 攻擊封包 + 傷害公式 + 背包 | 能打怪、掉寶、撿物 |
| **M5 腳本＋多實例** | Jint 跑既有 `.js`（NPC/portal/quest/商店）；**正式啟用 `instances[]` 多實例** | NPC 能對話買賣傳送；**同機跑兩個獨立伺服器** |
| **M6+ 進階/真隔離** | 商城、組隊、技能進階、活動；**多進程版（真故障隔離）** | 逐步補齊到「超越舊伺服器」 |

順序刻意是「**最短路徑先讓客戶端有反應**」：M1 目標是「客戶端顯示登入失敗」而非成功——因為那已經證明 cipher＋opcode＋framing 整條管線正確。登入成功（M2）只是再加 DB。抽象（M3）等手上有真封包才提取，避免「不知道是版本問題還是介面問題」的除錯地獄。

## 9. 風險與緩解

| 風險 | 緩解 |
|---|---|
| 加密/opcode 一個 bit 錯就連不上 | 黃金樣本測試 + 以舊 Java 為對照真值；M1 先打通 |
| 360 檔邏輯量大、易半途而廢 | 不逐行翻譯；里程碑制、每階段可玩；舊碼當參考而非負擔 |
| WZ 解析工作量 | 先沿用既有 XML 萃取，延後做二進位 reader |
| 「版本抽象」過度設計 | v113 先做扎實，只留**乾淨接縫**；真要第二版本時才長出第二 adapter（YAGNI 但不堵死） |
| NPC 腳本相容 | Jint 直接跑既有 .js，宿主 API 對齊舊 `NPCConversationManager` |

## 10. 開放問題決議（2026-05-31 作者拍板）

1. **代號**：`MapleForge` ✅ 採用。
2. **版本抽象力度**：✅ v113 先做扎實、只留乾淨接縫，**先不**實作第二版本。
3. **WZ 來源**：✅ **一開始就上 C# 二進位 WZ reader**（乾淨路線）。→ `Maple.Content` 提供 `IDataProvider`，實作為直接解析 v113 的 `.wz` 二進位（含 PNG/canvas、加密 string 解碼）。可參考 MapleLib/reWZ 等既有 C# WZ 解析作法，但包在 adapter 後。
4. **進程模型 + 多實例**：✅ 先單進程多服務。**並正式納入「多實例同時運行」為第二支柱（§2.2）**——Host 以設定的 `instances[]` 拉起多個獨立 `ServerInstance`，達成「私服界沒做到、同機同時開多個伺服器」。

### 之後（到 M2 才需定）的待決點
- **多實例的資料庫策略**：每個 `ServerInstance` 一個獨立 schema（隔離乾淨、推薦）vs 共用 schema 加 `instance_id` 欄位（省事）。預設走「每實例一 schema」。
- **多實例的典型用途**：同版本多世界 / 不同版本並排測試 / 兩者皆要——影響角色資料與跨世界互動設計，到 M2 再定。
