# MapleForge — 自動化與工作流程（workflow.md）

> 本文件定義「AI 如何自動推進開發、何時暫停、如何協作、如何追蹤」的規則。
> 與 `重構架構設計書.md`(why)、`任務追蹤.md`(狀態)、`進度日誌.md`(敘事) 並列。
> 建立 2026-05-31。狀態：v2（2026-06-01 §2 改為「能力圓桌」定版的 AI 能力地圖）。

---

## 1. 目的
讓 AI 能在使用者一句「開工/繼續」後**連續推進多個任務**而不必逐一打擾，同時用明確的**護欄**（額度、風險、phase 邊界）保證不失控、不超量、不亂動既有資產。

---

## 2. AI 能力地圖與任務路由（2026-06-01「能力圓桌」定版）

> **2026-06-01 重跑「能力圓桌」**（R1 各 AI 能力自評 → R2 互評指出彼此高估/低估 → R3 收斂分歧）。
> 修正了過去「讓 AI 競標具體功能」的做法：**先釐清每個 AI 本質擅長的「能力領域」，再依任務性質路由到對的能力**。本節是派活的**單一依據**——任何任務先判斷它屬於哪類性質，再對照下表，不必每個任務重新爭一次。

### 核心原則
按「任務性質 → 能力軸 → owner」路由。八條能力軸的共識 owner（R2 全員投票結果）：

| 能力軸 | owner | 票況 | 說明 |
|---|---|---|---|
| **A 實跑/工具迭代** | **Codex** | 3/4 | 邊跑邊修、短回饋循環最強 |
| **B 底層/逆向/封包** | （Opus 相對第一） | 4/4 | ⚠️**全隊共同短板**，沒人真強——靠流程不靠人（見反直覺結論①） |
| **C 量產** | **Codex（速度）/ Sonnet（一致性）** | 拆分 | 判準見下方派活規則 |
| **D 架構/邊界/系統思考** | **Opus** | **4/4 全票** | 長鏈 trade-off、最終拍板 |
| **E 品質守門** | **Opus（主閘門）** | 3/4 | 三層守門，見反直覺結論② |
| **F 研究/探索/逆向取真值** | **agy** | **4/4 全票** | 唯一全票的非 Opus 軸 |
| **G 脈絡/長任務穩定** | **Opus** | 3/4 | 複雜狀態不漂移 |
| **H 成本/速度** | **Codex** | 3/4 | Sonnet 次之 |

### 每個 AI 的本質定位

| AI | 定位 | 不可取代性 | 禁區（不該交給它） |
|---|---|---|---|
| **Opus**（我，Claude，主控） | 架構大腦與最終仲裁 | 深層架構推理 + 跨層整合 + 最終品質守門 + 與使用者直接對話／live 測試（D/G 全隊最強，E 守門首選） | 量產（太貴）、底層逐步除錯、高頻試錯 |
| **Codex**（gpt-5.5） | 高速執行引擎 | 把「可執行變更」高速落地並用工具立即閉環驗證（A/H 第一、C 速度型量產、live 驗證第一線） | 無法驗證真值又要長期單點拍板的高不確定決策。**※ 硬核二進位逆向「能戰但非王牌」，不是 binary 專家** |
| **Sonnet**（Claude） | 性價比一致性量產線 | 規格約束下、需讀懂現有碼的一致性量產——同品質下速度/成本比最佳 | 模糊需求初次設計（會亂填假設）、跨系統影響評估、「錯一次＝多人返工」的決策節點 |
| **Kiro** | 結構重構工兵 + 平行產能備援 | AST 語義級安全重寫 + subagent 平行派工 + 在既有專案走完「讀→析→改→驗→測」閉環；**額度幾乎全新＝便宜的平行戰力**（純執行/量產與 Codex 高度重疊、上限略低，誠實版） | 純理論推理、底層逆向、需付費 API 的整合 |
| **agy**（Gemini） | 前置研究導航儀 | 超長 context + 搜尋 + 沙盒，做開發前的全局盲點偵測、依賴釐清、逆向取真值（讀舊 Java 神諭、查文件出規格書）。F 全票第一，**主動選擇專注研究、不當守門** | 無原始碼的動態二進位逆向（補不了，需 Codex 實跑踩雷） |

### 三個反直覺結論（能力圓桌最有價值的產出）
1. **「Codex＝binary 專家」是錯覺。** 底層逆向是全隊弱項，正解是**流程而非人**：agy 出理論地圖（舊 Java 神諭 + 文件）→ 離線夾具／反編譯器／封包 trace 轉測試向量 → Codex 實跑踩雷驗證。
2. **品質守門是「三層」不是一個人**：源頭層 **agy**（研究階段就堵掉爛設計）→ 第一線 **Codex**（live 邊跑邊驗）→ 最終閘門 **Opus**（定不變式、可審計地否決）。
3. **Kiro 不假裝獨佔**：誠實定位為「平行備援 + 結構重構工兵」，靠便宜額度與 AST/subagent 差異化，而非搶 Codex 的主戰場。

### 派活判準（拿這張表就能分工，不用再吵）
- **要讀懂現有碼才能寫** → Sonnet；**給規格就能寫** → Codex
- **開發前的不確定/盲點/取真值** → agy 先探
- **需 live 跑起來才知道對不對** → Codex 實作或驗收
- **架構拍板 / 跨層 trade-off / 最終放行** → Opus
- **大量機械性結構重構 / 要省錢的平行支線** → Kiro

### 鐵則：實作主責 ≠ 驗收主責
「需要 live-debug 驗證」只決定**誰驗收**，不決定**誰實作**。可單測/契約驗收的乾淨 C# 一律由 **Sonnet/Kiro 實作**，**Codex/Opus 只做 live 驗收**。防止把所有「跑起來才知道對不對」的任務全堆給 Codex。

### agy 使用規範（2026-06-01 新增）
- **觸發條件**：≥3 個不確定關鍵字的開放式問題（如「哪裡處理登入流程？」）；單點符號查詢直接 Grep。
- **輸出格式**：MD 含具體檔案路徑＋函數名稱＋行號；模糊描述不算合格交付。
- **可靠等級**：「選配加速器」——agy 失效可自補（Grep/Glob 降級），不是依賴。
- **備援策略**：超時（建議 24h 上限）→ 切 Kiro/Sonnet 自行推導；降級改小批次重試一次，仍失敗標記 `前置探索: 缺席` 繼續。
- **任務表格欄位**：`前置探索: agy: [探索目標]` 或留 `—`。
- **agy → Kiro 協作介面**：agy 產出 MD 後，Kiro 整理成決策文件，Sonnet/Codex 接手實作。

### Opus（主控）— 不可替代的環節
架構決策｜與使用者直接對話/釐清需求｜**live 測試（跑 server+真客戶端、截圖、改登錄檔——只有 Opus 能碰使用者本機）**｜整合驗證｜圓桌主持與裁決｜審核並整合委派產出｜更新追蹤。

### 委派判準（值不值得丟給 agent）
`委派價值 = 任務複雜度 × 獨立性 − Opus 審核成本`
- **值得委派 ✓**：規格清楚、有測試可驗、純後端不需看客戶端、產出 Opus 一眼能審。
- **Opus 自做 ✗**：需 live 客戶端驗證、需求模糊、檔案 <50 行（自己寫比審快）、架構決策。
- **鐵律**：Opus 省得下「寫碼+測試」，但**省不下「live 驗證」那一下**——那只有 Opus/使用者能做。

### 委派安全（2026-05-31 事故教訓）
- **premise 未定不委派**：任務前提（如資料層選型）還在決策中時，不要先委派實作——會白做＋污染工作樹。
- **kill 後要驗證**：`kill_process` 回報 terminated **不代表 agent 真的停了**。停掉後必檢查 `git status`，必要時 `git checkout -- . && git clean -fd` 還原。
- **背景 agent 會改追蹤文件**：委派時若不希望它動 `任務追蹤.md`/設計書，prompt 要明講「只動程式碼、不要改 docs」。

### 評審圓桌（panel）
重大設計決策辯論、對抗式 review：Codex / Sonnet / Kiro / agy（選配）。各被指派立場/攻擊面，Opus synthesize。
**agy 納入圓桌條件**：通道穩定確認後（每次使用前 peek 測試）；圓桌任務為探索型而非精確實作。

### 使用者（你）
方向拍板｜高風險批准（Approval Queue）｜Phase 邊界確認｜live 互動（必要時親自啟動客戶端，Opus 觀察）。

## 3. 三層追蹤（單一真相來源）
1. **`任務追蹤.md`** = 狀態真相（勾選框 + 儀表板）。
2. **git commit 帶任務 ID**（如 `M1-3: ...`）= 可驗證帳本。
3. **`進度日誌.md`** = 敘事紀錄（每次 session 一條）。

三者由主控 AI 在每個任務完成時**順手同步**，使用者不需額外維護。

## 4. 單一任務生命週期

```
取下一個 ⚪ 任務
   ↓
檢查執行者資格（任務定義的「執行者」與「資格要求」是否匹配）
   ↓   ├─ 不匹配 → 重新指派或升級圓桌裁決
   ↓
動工前共識（輕量 or 圓桌，見 §6）
   ↓
執行前置探索（若任務有「前置探索」欄位，依指示執行 agy/Grep）
   ↓   ├─ 探索失敗 → 降級或標記缺席繼續
   ↓
執行任務（主控自做 or 委派執行 AI）
   ↓
自我驗收：對照該任務的 DoD（驗收標準）
   ↓   ├─ 不過 → 修正；連續失敗 → 標 🟥 failed，暫停回報（§11）
   ↓
更新追蹤：勾選 + 儀表板 + 進度日誌
   ↓
git commit（訊息帶任務 ID）
   ↓
Usage Guard 查詢（§7）
   ↓   ├─ 任一 AI < 15% → 暫停回報
   ↓
判斷是否 Phase 邊界（§9）→ 是則暫停確認方向
   ↓
回到頂端取下一個任務
```

## 5. 自動推進（Auto-Advance）

### 授權觸發詞
使用者說出任一詞，即進入自動推進模式：
> **繼續** ／ **開工** ／ **自動推進** ／ **一直跑**

### 流程
授權後依序執行 `任務追蹤.md` 的待辦任務，無需逐一詢問，直到遇到**暫停條件**。

### 暫停條件（任一觸發即停）
- 任一可查詢 AI 剩餘額度 **< 15%**（§7）
- 遇到**高風險操作**（Approval Queue，§8）
- 任務**連續失敗**進入 failed 狀態（§11）
- **Phase 完成**（里程碑邊界，需使用者確認方向，§9）
- 出現**設計層級的歧義/分歧**，需圓桌或使用者裁決

### 恢復條件
使用者回覆「**繼續**／**開工**」即從下一個任務接續。

## 6. 動工前共識（分級）

不是每個任務都要開會。依任務性質分兩級：

| 級別 | 適用 | 做法 |
|---|---|---|
| **輕量共識（預設）** | 明確、低風險、機械性任務（建檔、scaffolding、照規格實作） | 主控 AI 用一兩句說明「要做什麼、預期結果」，直接執行 |
| **圓桌共識（升級）** | 重大架構決策、技術選型、有多種合理走法、會影響後續多個任務、或不可逆 | 召集評審圓桌（§10）辯論/review，收斂後再動工 |

**升級判斷準則**（命中任一即升圓桌）：影響 ≥2 個里程碑 ｜ 動到兩大支柱（版本抽象 / 多實例）｜ 引入新的外部依賴或框架 ｜ 改變協定/資料格式 ｜ 主控 AI 自評信心 < 70%。

## 7. Usage Guard

### 查詢程序
每完成一個任務後，主控 AI 執行額度查詢（`ai-cli usage` / `query_usage`）。
> 效率調整：usage 結果快取 120 秒。若多個分鐘級小任務落在同一快取窗，於該批次的**最後一個任務或 Phase 邊界**做一次查詢即可，不重複貼相同數字（符合「別超量」本意）。

### 解析對照
| AI | 查詢 | 判斷欄位 |
|----|---------|---------|
| Claude | ✅ | `Current session: XX% remaining` |
| agy (Antigravity) | ✅ | 各模型取**最低** available |
| Kiro | ✅ | `Credits ... XX% remaining` |
| Codex | ✅ | `5h limit` 與 `Weekly limit` 取**最低**；查詢偶爾卡選單雜訊 → 沿用上次值並註明 |
| Gemini（獨立） | ⚠️ 不支援 | `N/A`，暫不計入門檻；待後續 QuotaAdapter 補齊 |

### 門檻判斷
```
任一可查詢 AI 剩餘 < 15% → 暫停，回報：
  ⚠️ [AI] 剩餘 XX%，低於 15% 門檻，自動推進暫停。請補充額度後回覆「繼續」。
```

### 回報格式（每任務完成後）
```
✅ [任務 ID] 完成
📊 Usage Guard：Claude XX% | agy XX% | Kiro XX% | Codex XX% | Gemini N/A
→ 繼續執行 [下一個任務 ID]
```

## 8. Approval Queue（高風險操作需人類批准）

遇到以下操作 **一律暫停、列出、等使用者明確批准**，不自行執行：
- **刪除或覆寫既有資產**：舊 Java 伺服器、客戶端二進位、WZ 檔、現有資料庫。
- **不可逆操作**：`git push --force`、`reset --hard`、大規模檔案刪除、schema 破壞性遷移。
- **對外/發布**：推送到遠端、發佈、對公網開放、寄送任何資料到外部服務。
- **付費/外部資源**：會產生費用或呼叫外部付費 API。
- **動到客戶端**：patch MapleStory.exe、mutex bypass 等（M2.5）——須使用者在場確認。
- **安全敏感**：加密金鑰、帳密、憑證的處理。

回報格式：
```
🛑 高風險操作待批准：[操作描述]
   影響：[範圍]　可逆性：[可逆/不可逆]
   請回覆「批准」以執行，或指示替代做法。
```

## 9. Phase 邊界（里程碑確認）

每個里程碑（M0→M1→…）是一個 Phase。**Phase 完成時暫停**，回報成果與下一 Phase 計畫，待使用者確認方向後再續。
理由：里程碑之間常有方向選擇（如 M2.5 客戶端策略、M3 抽象提取時機），值得使用者拍板。

## 10. 多 AI 圓桌協作規範

### 何時召集
重大設計決策、技術選型、對抗式 review（如本專案的選型辯論、設計書 review）。

### 如何運作
1. 主控 AI 指派**立場或攻擊面**給各 panel 成員（避免同質、製造有效碰撞）。
2. 多輪：開場 → 交叉質詢 → 深挖 → 修法 → 裁決＋信心值。
3. 用 ai-cli `session_id` 維持各成員上下文；Gemini(agy) 通道不穩時可剔除或單次重試。
4. 主控 AI **synthesize**：收斂共識、列出確認的問題與修法、落地成文件修訂。

### 產出
圓桌結論必須落地為**文件修訂**（設計書/任務清單）或**任務**，不能只是討論。

---

## 11. 失敗處理（failed 狀態）

任務執行失敗 → 嘗試修正。**連續失敗（同一任務 2 次無進展）**→ 標 🟥 failed、暫停、回報：
```
🟥 [任務 ID] 失敗
   現象：[錯誤]　已試：[嘗試]　研判：[原因]
   需要：[使用者輸入 / 環境 / 決策]
```

---

## 12. 提交規範（commit convention）
- 訊息開頭帶**任務 ID**：`M1-3: AES-OFB cipher 通過黃金測試`。
- 一個任務一個 commit（小任務可合併，但訊息列出所有 ID）。
- 高風險/破壞性操作不在自動流程內 commit（見 §8）。
- 訊息語言：標題簡潔、必要時補條列說明。
