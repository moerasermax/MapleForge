# 登入框鍵盤注入 — 團隊研究綜整（待討論，勿再搜尋）

> 2026-06-02 深夜爬文成果（Codex/Kiro/agy）。目標：對 v113 客戶端**登入畫面帳密欄**自動輸入。
> 已確認根因：**中文 IME 攔截合成 scancode → WM_KEYDOWN wParam=0xE5 (VK_PROCESSKEY)**，字進不了欄位。
> 環境約束：HVCI 開、不重開機、不裝 kernel 驅動、windower 已在客戶端內。私服(GameGuard 幾乎確定關閉)。

## 候選方法（按「對我們 IME 根因的針對性」排序）

### ⭐ A. 切英文鍵盤佈局後再送 scancode（Codex#1 + agy 都指向，最對症、未試過）
- `LoadKeyboardLayoutW("00000409", KLF_ACTIVATE)` 載入美式英文 HKL
- `PostMessageW(hwnd, WM_INPUTLANGCHANGEREQUEST, 0, (LPARAM)hklUS)` 對 MapleStory 窗要求切輸入語言
- 確認 `GetKeyboardLayout(tid)` 變 0x0409 / `ImmIsIME(hkl)` 為 false
- 再聚焦欄位 + `SendInput(KEYEVENTF_SCANCODE)`
- **為何對症**：切成非 IME 的英文 HKL 後，實體 scancode 不再進中文 IME 的 ProcessKey → 不再變 VK_PROCESSKEY。
- 註：我們試過 `ImmAssociateContext(hwnd,NULL)`(視窗層級，失敗)、`ImmSetConversionStatus`(切英數失敗)，但**沒試過切「鍵盤佈局」**——這是缺的那一塊。

### B. ImmDisableIME 在「第一個 top-level window 建立前」於 process 內呼叫（Codex#2）
- `ImmDisableIME((DWORD)-1)` 關整個 process 的 IME，但**必須夠早**(CREATE_SUSPENDED→注入→ImmDisableIME→Resume)
- 解釋了為何我們在視窗存在後才 ImmAssociateContext(NULL) 擋不住(太晚)
- 較複雜(要早期注入時機)，但最乾淨

### C. DirectInput Hook（GetDeviceState 注入）（Kiro#1）
- Kiro 主張登入畫面也走 DInput。**但我們 diag 顯示登入走訊息泵(WM_CHAR)、登入時 DInput 0 calls** → 對「登入框」存疑；對「遊戲內」適用(windower 已 hook)。
- 討論點：登入框到底有沒有讀 DInput？(我們的證據說沒有)

### D. KEYEVENTF_UNICODE 送 VK_PACKET → WM_CHAR（Codex#3）
- 已試過(AttachThreadInput+Unicode)，WM_CHAR 到 WndProc 但欄位不收 → **已知失敗**，除非配合別招。

### E. GameGuard 繞過（Kiro#2）/ 硬體 HID（全體）/ SendPlay WH_JOURNALPLAYBACK（agy#1）
- GameGuard：私服幾乎確定關閉，**大概率非我們的 blocker**(我們的 blocker 是 IME)。
- 硬體 HID(CH9329/Arduino)：使用者已否決。
- SendPlay/WH_JOURNALPLAYBACK：UAC 後受限、已過時，不優先。

## ✅ 團隊定案（2026-06-02，未重新搜尋，依此綜整 + 已實作程式碼）

**結論：方法 A 為對症首選、已實作、可直接 controlled live 測。** 投票：Codex = Go、agy(IME 機制視角) = 對症首選、Kiro = 策略保留(見下)。

**已落地實作**（`tools/windower/windower.cpp`）：
- `BeginEnglishLayout`/`EndEnglishLayout`：`LoadKeyboardLayoutW("00000409",KLF_ACTIVATE)` → `PostMessageW(hwnd,WM_INPUTLANGCHANGEREQUEST,0,hkl)` → `ActivateKeyboardLayout(KLF_SETFORPROCESS)` → 輪詢驗證 → 送完還原。
- 接在 `TryAttachThreadInputSendText` 內，IME 中和留作 belt-and-suspenders。
- 預設開啟；`MAPLEFORGE_WINDOWER_KBD_LAYOUT_EN=0` 可關掉做 A/B 對照。

**已採納 Codex 審查的小修**：
1. `WM_INPUTLANGCHANGEREQUEST` 的 `wParam` 用 `0`（指定明確 HKL，非 `INPUTLANGCHANGE_FORWARD` 切「下一個」）。
2. 驗證改用 `ImmIsIME(hkl)==false`（`HklIsNonImeEnglish`），不只看 low-word 0x0409。
3. 切換請求與驗證統一用 hwnd 實際所屬 thread，避免 foreground/focus 跨 thread 驗錯執行緒。

**Live 觀察點**（`windower_inject.log`）：
- 關鍵成功線：`kbd-layout verified en-US(non-IME) active`，且 WndProc probe 的 `WM_KEYDOWN wParam` 從 `0xE5` 變成正常 VK（如 0x41/0x31）並有對應 `WM_CHAR`。
- `NOT verified` 且仍 `0xE5` → 切換沒到目標 thread，**fallback：改 `SendMessageTimeoutW(...,SMTO_ABORTIFHUNG,...)` 同步化**（Codex 建議的下一招）。
- `verified` 但 `WM_CHAR` 正常卻欄位不吃 → IME 根因已排除，下個 blocker 是登入控制本身的文字接收/驗證邏輯。

**Kiro 的策略保留（如實記錄）**：協定學習的關鍵路徑是 headless 客戶端（已能程式化跑完整協定），GUI 鍵盤只為「最後肉眼驗證那一哩」，優先級可低。→ 使用者已拍板要全無人值守真客戶端自動化，故方法 A 仍在目標路徑上；但若 A 失敗，**不要陷進鍵盤死胡同**，回退順序：A → B（早期 `ImmDisableIME`，CREATE_SUSPENDED 注入時機）→ 直接寫記憶體 buffer。C(DirectInput) 對登入框已被 diag 否定，留給遊戲內。
