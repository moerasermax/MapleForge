# 背包/道具 領域分層設計（團隊決策）

> 2026-06-02 團隊紅隊會議（Gemini 3.1 Pro red-team + codex gpt-5.4 持久化/dupe + Opus 分層綜整）決策。
> 承接 in-game 執行期狀態架構（富領域 Core / session 黏合 App / 傳輸 Net、組合非繼承、Character=LiteDB 文件根）。
> 移植來源：Java `InventoryHandler.java`(2819 行) + `MapleInventory`/`Item`/`Equip` + `PacketHelper.addInventoryInfo`。**非 1:1 照抄 OdinMS。**

## 決策一：下一個子系統＝背包（不是 shop、不是戰鬥）

背包是**依賴樞紐**：shop＝addItem+扣 meso／removeItem+gainMeso（無背包不存在）；戰鬥掉寶/撿物→背包；NPC 腳本最常呼叫的 `cm.gainItem/haveItem`→背包；並把目前 SetField 造假的 inventory 區塊補成真。風險上它是**自足的「資料＋封包」練習**，遠低於戰鬥（需怪 AI／傷害公式／field-actor 並行／且 s2c 無 ground truth）。**先背包＝同時 de-risk 並解鎖三個下游系統。** 團隊一致背書。

## 決策二（關鍵）：持久快照 ≠ 執行期富領域 —— 兩者分離

> 紅隊推翻了「把富 Inventory 聚合直接掛 Character 文件根」的初版。兩個獨立模型同時反對：①行為掛文件根→他層繞過 Player 亂動、Character 變活的狀態機；②LiteDB 重建繼承樹（Equip:Item）＝版本/建構子/mapper 一變就潛在資料腐化。

**最終形（比照 Position 前例：富領域在執行期、持久面扁平）**：

- **持久面**：`Character` 嵌入扁平 `List<ItemRecord>`（單一具型 DTO，`Kind` 判別 Normal/Equip + 裝備欄位 nullable），**取代** 現有 `List<EquipEntry>`。整份 Character 文件**單次原子寫**（勝過 Java 兩張表的部分存檔風險）。注意 LiteDB **1MB 文件上限**。
- **執行期面**：`Player` 在 session 載入時 **hydrate** ItemRecord → 富 `Inventories` 聚合（含 `Item`/`Equip`/`Inventory` 領域型別與全部不變式）；**所有變動經 Player**（GainItem/HasItem/RemoveItem/Equip/Unequip，跨背包＋職業/等級檢查，唯一入口，比照既有 `GainMeso`）；checkpoint 時 **flush** 回 ItemRecord。

統一原則：**Player 是唯一行為入口**；純量（meso）直接 live-mutate 在 Character；複雜聚合（inventory）用執行期領域模型 hydrate 於 Player、扁平 DTO 落盤。

## 決策三：MVP 切到「rollback-safe」邊界

> codex 關鍵洞見：**純 reorder/equip/unequip ＝ crash 後 roll back 無害（近乎 cosmetic）；consume/sell/drop/trade/buy ＝ 改變價值/所有權→才是 dupe/loss 雷區、需 app-journal。** 切線因此 = 安全性，不只「聚合可否容納」。

- **MVP-0（第一刀，零 journal 即安全）**：Core 背包領域 + ItemRecord 持久 + SetField 真實序列化五欄 + 格內 ITEM_MOVE move/merge 經 ModifyInventory round-trip。種道具用 `cm.gainItem`（兼作 NPC 整合證明）。
- **MVP-1（同里程碑）**：equip/unequip（owner-side ModifyInventory）。**look-broadcast 給同圖他人**＝薄 follow-up，重用既有 movement field-broadcast 路徑，單客戶端 smoke 下為 no-op、不擋 MVP。
- **Defer（需先有 app-journal）**：USE_ITEM(需 vitals+WZ)、DROP-to-ground(需 field drop 物件)、PICKUP(需 field drop/戰鬥)、NPC buy/sell、trade、ITEM_SORT/GATHER、cash-item、pets、item-maker。介面藏後，parser 分支先 no-op log（不讓客戶端 desync）。

## 風險與過度設計警戒（團隊共識，按殺傷力）

1. **耐久邊界（codex 最擔心）**：memory→封包→checkpoint 對「改價值/所有權」的 op **不安全**（客戶端已見成功、DB 未落盤，crash 後 relog 看舊狀態＝dupe/loss）。→ **deferred 那批上線前必須先做 fsync 的 append-only app-journal**（ack 前先寫 journal，checkpoint 折進 Character 快照）。**MVP-0/1（reorder+equip）roll-back 無害、不需 journal**＝安全切片。
2. **dupe 利用（Gemini/codex 同列最大）**：swap/drop-lag——客戶端在 server 0x1B 回覆前對同一 src 連發多個 ITEM_MOVE。→ **per-player 單執行緒變動佇列（＝既有 field-actor 序列化）**＋apply 時對**權威狀態**重驗 src 占用＋qty（不信 request 時快照）。junior 雷：對同一份 pre-mutation 快照驗兩次→兩個 move 都「移走」同一疊。
3. **LiteDB**：①嵌入式單文件原子寫（別學 Java 兩張表）②扁平 ItemRecord 別讓它重建 Item/Equip 繼承樹③留意 1MB 文件上限④視需要註冊 BsonMapper 設定。
4. **SetField 容量**：DB 載入的道具數別超過封包宣告的 slot limit（client 硬上限會崩）→ 載入時驗/夾。
5. **過度設計**：先**不**建 WZ 道具資料庫（stack-size 硬編、藏在 `IItemMetaProvider` 後）；不碰 trade/storage/cashshop；DTO 扁平不要每型一個；app-journal 留到需要它的那一刀才做。
6. **分層滲漏**：Core 背包零傳輸/零 session/零 ConcurrentDictionary；出站一律 App→Adapter 編碼→Net。

## 落地順序

1. Core/Inventory：`InventoryType`/`Item`/`Equip`/`Inventory`/`Inventories`/`ItemRecord`（純領域，build 綠）。
2. `Character`：`Equips`→`Items(List<ItemRecord>)`；`Player` hydrate/flush + GainItem/Equip/Unequip。
3. Adapters.V113：`AddInventoryInfo` 五欄真實序列化（接 records/runtime）。
4. Adapters.V113：`V113InventoryParser` 解 ITEM_MOVE + `ModifyInventory` 編碼；Application `MoveItem.Apply`（per-session 序列化）。
5. `cm.gainItem` 種道具 → headless/里程碑 smoke：進圖看到道具、格內拖移 round-trip。
6. （MVP-1）equip/unequip + look-broadcast follow-up。
