## 0. 一句話結論

**取「制度」與「方法論」，不要照搬「Python 目錄」與「source-less 逆向」。** MapleForge 程式分層/測試資產已有 .NET 底子，但最脆弱的是「文件同步硬閘門」與「逆向證據保存」——這正是黃逸最成熟、最該拿回來的兩塊。另外 Antigravity 提出一個直擊 MapleForge 痛點的新打法：**用舊 Java server 當 S2C 預言機**。

## 2. 方法論精華（跑跑卡丁車，可直接平移）

**核心對應**：跑跑的 `decompiled/`（stub server 原碼）＝ MapleForge 的舊 Java 原碼（OdinMS 系）＝「server 行為的標準答案」。「真機迭代迴圈」整套可平移：
> 起透明 server（解密全 RX/TX log）→ 跑真客戶端 → 看 log 卡在哪個封包 → **回 Java 原碼逐行讀那個 handler** → byte 級忠實補上（別猜/別簡化/別 no-op）→ 重跑真機 → 里程碑 commit。

**最該記住的 4 條坑（移植 Java handler 時）**：
1. **別猜欄位，照原碼 byte 級對照**——一個 byte 偏移就讓客戶端記憶體損壞。
2. **一對多發送（1:N）**——一個 C2S 不一定只回一個 S2C（例：交易/組隊/升級會同時觸發多個 stat/庫存/廣播）。移植時要追完該 handler 所有 `sendPacket`，漏一個就阻塞。
3. **辨識背景 keepalive vs 阻塞**——看見無限重送先檢查「重送同時有沒有冒新業務封包」，有＝背景心跳不是卡點（MapleStory Ping/Pong）。
4. **Console I/O 別卡發送路徑**——verbose log 同步印在送 socket 之前會破壞 client gated timer 時序 → 用非同步 log 或把 TX log 移到實際寫 socket 之後。

**真相來源優先序（MapleForge 版）**：
> Java 權威原碼（標準答案）→ 真客戶端解密 Log（事實）→ Winsock 側錄 → 黑箱猜測（禁止）

## 3. 明確「不該照搬」

1. 不照搬 source-less 逆向優先級——MapleForge 有 Java 權威，反編譯 SOP 改成 **Java-first，client reverse 只補洞**。
2. 不照搬 8-context 目錄樹——只取 context mapping 與依賴規則，落在既有 .NET solution。
3. 不照搬 Mongo 偵測規則——MapleForge 用 LiteDB，gate 要偵測 `Bson/LiteDatabase/repository/Character 文件欄位/ItemRecord`。
4. Doc-Sync 初版別過嚴——先擋協定/DB/世界/評審四類；低風險(測試/log/工具 UI)只提示不 block，免得開發者繞 hook。
5. fixture 不取代設計真相——封包 archive 只存證據；真相在 Java 權威 + Core domain + protocol spec。

## 4. 建議落地順序

1. **P0-1 Doc-Sync Gate MVP**：`doc_sync_check.py`(Codex 骨架) + 兩個 hook，啟用前用近 3-5 個 commit 模擬調誤判。
2. **P0-2 `docs/specs/persistence-model.md`**：寫清 LiteDB 文件形狀，給 DB gate 落點。
3. **P0-3 PacketArchive**：windower capture → 解密 → SQLite，先 `query`/`stats`，後接 `export-fixture`。
4. **P0-4（與 3 併）S2C 預言機**：舊 Java server 雙向側錄 → S2C 黃金向量（解 `packet-capture-design` 待續①②）。
5. **P1**：architecture test 擴充 → MapleBot 動作 API → Combat/Inventory/AOI domain event 化 → Gated Replay 時序測試 → tools/README。
