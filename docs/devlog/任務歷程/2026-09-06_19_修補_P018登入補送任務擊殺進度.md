## 🎯 目標（執行前先寫死，過程不偷改）

延續 P016/P017「系統性 grep 每個 `V113*Packets.cs` 找零呼叫者」找到的候選清單，本次處理
`V113QuestPackets.UpdateQuestMobKills`。完成判準：玩家登入時，對每個「已接受（Started）且有
怪物擊殺目標」的任務補送一次擊殺進度封包（比照 Java 登入流程逐一檢查 `hasMobKills()`）；沒有
擊殺目標的一般任務、未接受、已完成的任務都不送；單元測試覆蓋封包版型與過濾邏輯。

## 📋 背景與假設

- Java 來源：`InterServerHandler.java:292-297`（登入流程，緊接在 keymap 送出之後）：
  ```java
  // 任務狀態
  for (MapleQuestStatus status : player.getStartedQuests()) {
      if (status.hasMobKills()) {
          c.sendPacket(MaplePacketCreator.updateQuestMobKills(status));
      }
  }
  ```
  `MapleQuestStatus.hasMobKills()`（`client/MapleQuestStatus.java:158`）只判斷 `killedMobs` 這個
  Map 是否非空（不管當前擊殺數是 0 還是有進度）——代表「這個任務有怪物擊殺子目標」，不是「已經
  殺過至少一隻」。
- MapleForge 現況：`V113QuestPackets.UpdateQuestMobKills(QuestRecord quest)` 封包建構式已存在
  （序列化 `quest.MobKills` 為固定 3 位數字串拼接，符合 Java `getMobKillsAsString` 版型慣例），
  但 grep 全專案零呼叫者。既有 `SET_FIELD`（`V113ChannelPackets.SetField`）內嵌的任務段只有
  `questId`/`customData`，不含逐怪擊殺數——這與 Java 一致（Java 的 `addQuestInfo` 在 SET_FIELD
  也只寫 customData，擊殺進度本來就是登入後另外補送的獨立封包），故這不是 SET_FIELD 版型缺陷，
  是「補送」這一步被漏掉了。
- 修法：`V113ChannelConnectionHandler` 新增 `internal static SendStartedQuestMobKillsAsync(Character,
  Func<byte[],CancellationToken,Task> sendSelf, CancellationToken ct)`，在 `SendNormalChannelEntryPacketsAsync`
  （送 SET_FIELD 的地方）之後呼叫。方法本身用 `Func<byte[],CancellationToken,Task>` 而非直接吃
  `MapleSession`，是刻意選擇——這個類別的其餘私有方法多半直接吃 `MapleSession`（難以脫離真實
  session 單元測試），改用委派讓這段新邏輯可以像其他 handler 一樣被獨立單元測試，不需要整個
  連線流程的整合測試骨架（目前這個專案裡也還沒有這種骨架）。
- 範圍邊界：只補「登入時的擊殺進度初始化」。既有的擊殺進度即時更新（打怪當下更新任務進度）已經
  是另一條路徑（Combat/Quest 服務），不在本次範圍，未受影響。

## ✅ 結果與結論

- 這是本次系列（P015→P018）第三次用「讀 Java 某段流程程式碼 → 對照 MapleForge 找零呼叫者封包 →
  補送」的手法收斂缺口，且是目前為止**驗證成本最低**的一次——因為登入流程那段 Java 程式碼在更早
  的 phase（讀 `InterServerHandler` 找 Family 缺口時）就已經完整讀過，這次只是回頭核對清單裡還有
  哪一行沒被 MapleForge 覆蓋，屬於「一次深讀、多次收割」的效益體現。
- 刻意把新方法設計成吃委派而非 `MapleSession`，是為了不讓「這個類別太多方法只能靠整合測試」的
  既有技術債繼續擴大——即使只是一個小方法，也選擇對齊「可獨立測試」的慣例，而不是圖方便直接複製
  `SendNormalChannelEntryPacketsAsync` 的簽章。
