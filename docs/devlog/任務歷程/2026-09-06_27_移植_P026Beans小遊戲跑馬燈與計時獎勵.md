## 🎯 目標（執行前先寫死，過程不偷改）

P020 收尾列出的「需要前置設計」候選之一：`EventMiniGame` 的 `RewardBeans`/`BeansMarquee`（綁在
「未完整的 Monster Carnival Beans 小遊戲 reward UX」）。查證後發現範圍其實明確可完成：Beans 小
遊戲（`BeansGameAction` c2s 封包）的 8 種子類型 MapleForge 早就有完整的 switch 路由與大部分邏輯
（Start/Pause/Light/Shoot/Reset），只有「上跑馬燈+固定獎勵」與「計時分級獎勵」兩個分支是
`SelfOnly(EnableActions())` 空樁，不是整個小遊戲系統缺失。完成判準：這兩個分支對照 Java
`BeanGame.BeansGameAction` type=5/type=7 補上真正的獎勵邏輯。

## 📋 背景與假設

- Java 全域搜尋確認 `RewardBeans`＝Java `BeansPacket.rewardBalls`，`BeansMarquee`＝Java
  `BeansPacket.marqueeMessage`，兩者的呼叫端都在 `handling/channel/handler/BeanGame.java` 的
  `BeansGameAction(LittleEndianAccessor, MapleClient)`——一個以 `byte type`（0~7）分派的小遊戲
  狀態機，MapleForge 對應的 `V113EventMiniGameHandler.HandleBeansGameAction` 早已用相同的 8 分支
  結構（含 `or 0x01`/`0x02`/`0x03`/`0x05`/`0x07` 這種同時接受 Java `type` 值與 MapleForge 自訂
  子碼的 fallback 寫法）路由，只是 `type=5`（上跑馬燈+2000顆固定獎勵）與 `type=7`（計時三段分級
  獎勵）兩支的 body 是 `SelfOnly(EnableActions())` 佔位樁。
- **type=5（上跑馬燈+固定獎勵）**：`CanUseBeans() && canGainBeansReward()` 才發；發放後
  `setCanGainBeansReward(false)`（當次只能發一次，要重新 Shoot 才能再發）；廣播跑馬燈訊息給
  **全地圖**（`chr.getMap().broadcastMessage`），固定送 2000 顆並 `gainBeans(2000)`（內部觸發
  `updateBeans()` 送 `UPDATE_BEANS` 封包）。
- **type=7（計時三段分級）**：同樣要 `CanUseBeans() && canGainBeansReward()`，但**不清除**
  `canGainBeansReward`（允許重複觸發，這是 Java 原始設計，不是缺陷，照抄不修）；以客戶端傳來的
  時間戳 `now` 與 `beans_stage==0` 時建立的 `beans_time` 基準比對：經過 >10s 給 0 顆（stage 重置為
  5，這裡的「5」是封包參數不是進度語意）、5~10s 給 100 顆（stage=4）、<5s 給 100 顆（stage=1）。
  **第一次呼叫必為 <5s 分級**——因為 `beans_stage==0` 時 `beans_time` 才剛被設成當下 `now`，
  `now-beans_time` 必為 0。
- MapleForge `BeansGameSession`（Core）已有 `IsActive`（≈`CanUseBeans`）、`CanGainReward`
  （≈`canGainBeansReward`），但缺 `Stage`/`StageStartTime`（≈`beans_stage`/`beans_time`），這次
  補上，放在既有的 session 物件而非 `Character`（MapleForge 既有架構把小遊戲執行期狀態集中在
  `BeansGameSession`，不是照 Java 把欄位散落在 `MapleCharacter` 上，延續既有分層決定）。

## 🔧 實作內容（依分層）

- **`Maple.Core`**（`src/Maple.Core/MiniGames/BeansGameSession.cs`）：新增 `Stage`/`StageStartTime`
  屬性（`Reset()` 一併歸零）；`TryGainMarqueeReward(currentBeans)`：`IsActive && CanGainReward` 才發，
  發放後清 `CanGainReward`，固定 +2000；`EvaluateTiming(clientTime, currentBeans)`：
  `IsActive && CanGainReward` 才評估（否則回 `null`），三段分級邏輯逐行對照 Java，**不清除**
  `CanGainReward`；新增 `BeansTimingReward` record struct（`Amount`/`Stage`/`BeansAfter`）。
- **`Maple.Adapters.V113`**（`V113EventMiniGameHandler.cs`）：`BeansMarqueeReward or 0x05` 改接
  `MarqueeRewardBeans(player)`——`SelfPackets`＝`RewardBeans(2000)`+`UpdateBeans`+`EnableActions`，
  `MapPackets`＝`BeansMarquee(player.Character.Name)`（`HandleEventMiniGameResultAsync` 既有的
  `MapPackets`→`BroadcastPacketToMapAsync` 語意本來就含自己，不需另外重複送）；`CharacterMutated`
  依是否真的發獎而定。`BeansTiming or 0x07` 改接 `TimingBeans(reader, player)`：解析封包載荷
  `[int 未使用][int 客戶端時間戳]`，呼叫 `EvaluateTiming`，`Amount>0` 才更新
  `player.Character.Beans` 並加送 `UpdateBeans` 封包（0 顆時不送、不標記 `CharacterMutated`，
  對照 Java `gainBeans` 只在真的有增量時才觸發 `updateBeans()`）。

## ⏯️ 接手點

刻意排除的範圍：MapleForge 現有 8 個 Beans 子類型分支使用的實際 byte 值（`0x00/0x04/0x06/0x08/
0x0B/0x0D/0x0E/0x0F`）與 Java `type`（0~7）並非簡單線性對應，這批數值來源不明（可能是先前某輪
真封包擷取結果），這次刻意不重新推導或改動任何既有的子類型 byte 常數，只補了兩個既有分支底下
缺失的獎勵邏輯本體——重新驗證整個 opcode 對應表是另一個範圍更大、需要真封包擷取佐證的獨立課題，
不在這次範圍內。

## ✅ 結果與結論

- 這是本輪（P021-P026）第四次把「聽起來像需要前置設計的大功能」拆解後發現實際範圍明確可完成
  的案例——P020 把 `RewardBeans`/`BeansMarquee` 歸類為「小遊戲 reward UX 未完整」，但實際查證後
  發現「小遊戲」本身早就完整（狀態機、Start/Shoot/Light/Reset 全部到位），只是兩個 reward 分支
  是空樁，屬於「把已存在的路由接上真邏輯」而非「打造一個新系統」。
- 這次也是第一次在同一個候選裡遇到「MapleForge 既有子類型 byte 值與 Java type 值不一致」的情況——
  選擇刻意不動它（維持既有 `or` fallback 寫法的雙重相容），只補邏輯本體，是本輪目前最保守的一次
  範圍收斂：改動限定在「大家都同意需要真邏輯」的部分，不去動有不確定性、且改動代價高（可能破壞
  真封包相容性）的既有 opcode 假設。
