## 🎯 目標（執行前先寫死，過程不偷改）

延續 P022，接上公會 NPC 腳本 `scripts/npc/2010007.js` 實際呼叫的 `cm.increaseGuildCapacity()`。
完成判準：楓幣足夠且有公會時真的擴充公會人數（+5，上限 100）並廣播給全公會在線成員；楓幣不足彈出
提示；無公會靜默不送包；**楓幣扣款行為完整對照 Java（含其「回傳值被忽略」的行為特性）**。

## 📋 背景與假設

- Java 呼叫鏈：`NPCConversationManager.increaseGuildCapacity()` → 檢查 `meso>=250000`（否則
  `getPopupMsg("金錢不足25萬.")`）→ 檢查 `gid>0`（否則靜默 return）→
  `World.Guild.increaseGuildCapacity(gid)`（**回傳值完全未被檢查**）→ 無條件
  `c.getPlayer().gainMeso(-250000, ...)`。`MapleGuild.increaseCapacity()`：
  `capacity>=100 || capacity+5>100` 則回 false（不廣播不持久化）；否則 `+5` 並
  `broadcast(guildCapacityChange(id, capacity))` + 持久化。
- **刻意保留的 Java 行為特性**：即使公會已達 100 人上限（`increaseCapacity()` 回 false、容量
  沒有真的增加），Java 因為沒檢查 `World.Guild.increaseGuildCapacity` 的回傳值，**楓幣依然被扣**。
  這符合 MapleForge「Java 是行為神諭，不修得比原版更合理」的鐵律（P020/P021 已有先例），所以
  MapleForge 的 `GuildService.IncreaseGuildCapacityAsync` 同樣無條件扣款，不因為容量已滿而提前
  return 省下這筆扣款。
- MapleForge `Guild.TryIncreaseCapacity(amount=5)`（`src/Maple.Core/Guilds/Guild.cs:124`）
  在更早的批次移植就已經寫好、邏輯與 Java `increaseCapacity()` 完全一致（`capacity>=100 ||
  capacity+amount>100` 則回 false），但全專案零呼叫者——是這次要接線的域方法。
- `V113GuildPackets.GuildCapacityChange(guildId, capacity)` 封包格式也早已存在且與 Java
  `MaplePacketCreator.guildCapacityChange` 逐位元組一致（`GUILD_OPERATION` opcode + `0x3A` +
  int guildId + byte capacity），這次之前完全沒有單元測試覆蓋，一併補上黃金向量測試。

## ✅ 結果與結論

- 這次刻意「不修正」Java 的怪異行為（已滿仍扣款）是本輪第三次遇到類似判斷（P020/P021 已有
  「不把 MapleForge 修得比 Java 更完整」的先例）——每次遇到都要先確認這是 Java 真實行為而非我方
  誤讀，這裡透過直接看 `World.Guild.increaseGuildCapacity(gid);`（無 `if` 包住、無檢查回傳值）
  確認無誤才照抄。
- `NpcContext` 目前處理「需要 I/O 才能完成的操作」都遵循同一個模式：sync 決策 + pending flag →
  async flush 委派做實際 I/O + 廣播，這次是第二次套用（第一次是 P021 buddy capacity，但那次的
  I/O 只是送包；這次的 flush 委派內部還多了一層呼叫 `GuildService` 的 async 域邏輯）——證明這個
  分層模式可以優雅地延伸到「域邏輯本身需要 repository I/O」的情境，不需要為此另開新模式。
