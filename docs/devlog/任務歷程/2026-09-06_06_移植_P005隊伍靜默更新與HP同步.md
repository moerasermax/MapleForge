## 🎯 目標（執行前先寫死，過程不偷改）

對照 Java `MapleMap.addPlayer` 尾端：玩家進地圖時，若已在隊伍中，要 ①刷新自己在隊伍快照中的
Level/Job/MapId/Channel（`silentPartyUpdate`）②回送自己一份最新隊伍狀態封包 ③與其他在線隊友
雙向同步 HP（`updatePartyMemberHP`/`receivePartyMemberHP`）。這是 PartySearch 任務（`2026-09-06_01`）
發現的既有技術債：`V113PartyPackets.UpdateParty(SilentUpdate)`/`UpdatePartyMemberHp` 封包 builder
與 `PartyService.UpdateMember` 都已存在，但從未被 Adapters 呼叫過（純死碼）。完成判準：進地圖（含
登入首次進場與 WarpAsync 換圖）時，若在隊伍中，隊伍快照與 HP 隨之刷新且封包送出；有單元測試；
既有測試不退。

## 📋 背景與假設

- Java 來源：`MapleMap.java` 2149-2154 行；`MapleCharacter.silentPartyUpdate/updatePartyMemberHP/
  receivePartyMemberHP`（`client/MapleCharacter.java` 3200/2844/2858 行）。
- `silentPartyUpdate()` 呼叫 `World.Party.updateParty(partyId, SILENT_UPDATE, freshSnapshot)`——
  這正是修復我在 P004 PartySearch 任務中發現的技術債（`PartyMember.MapId/Level/JobId` 從未被
  `UpdateMember` 刷新）的正確掛載點。
- `IV113PartySessionHook`/`CentralPartySessionHook` 已有 `FindOnlinePlayerByNameAsync`/
  `SendToCharacterAsync`，足以取得其他在線隊友並送封包，但 `V113PartySessionPlayer` 目前不帶
  HP/MaxHp，需要擴充。
- **已知相關但不在本次範圍的缺口**：`PartyUpdateKind.LogOnOff`（隊友上下線廣播）與
  `PartyMember.IsOnline` 從未在 Adapters 被更新（永遠 `true`），本次不修——那需要在登入/登出流程
  另外掛 hook，屬於獨立的一塊工作，列 P006+ 候選。本次的 `IsOnline` 過濾判斷先寫成正確語意，等
  未來接上 LogOnOff 就會自動生效。

  不是只更新自己本地狀態，而是對**所有在線隊友**（含自己）都送一份新的 `updateParty` 封包——這與
  既有 `V113PartyOperationHandler.BroadcastPartyUpdateAsync`（用於 Join/Leave/Expel 等操作廣播）走的

  另外重寫一次廣播迴圈——省下重複程式碼。

## ✅ 結果與結論

- 補上 P004 PartySearch 任務發現的技術債：`PartyMember.MapId/Level/JobId` 現在會在玩家進地圖時
  透過 `silentPartyUpdate` 等效邏輯正確刷新，不再是建立/加入當下的一次性快照。
- **可轉移心法**：讀 Java 來源時不能只看呼叫點的方法名（`silentPartyUpdate` 聽起來像「只更新自己」），
  要往下追一層實際實作（`World.Party.updateParty`）才會發現它其實是全隊廣播——命名和行為不一致
  是舊碼常態，得靠追蹤呼叫鏈驗證，不能望文生義。
- 重用既有 `BroadcastPartyUpdateAsync` 私有方法而非另寫一份廣播迴圈，是本次「有機會簡化就直接做」
  的實例：兩者的資料流（`PartyCommandResult.Recipients` → 逐一送封包）完全相同，只是觸發來源不同。
