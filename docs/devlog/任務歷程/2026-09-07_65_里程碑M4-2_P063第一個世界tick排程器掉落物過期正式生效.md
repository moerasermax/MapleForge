## 🎯 目標（執行前先寫死，過程不偷改）

完成 P061（資料模型）→ P062（可測試用例）之後，這是三步驟的最後一步：接上 MapleForge
第一個真正週期性執行的 `BackgroundService`，讓掉落物過期從「存在但沒人呼叫」變成玩家真的
會看到——這是這一系列裡**唯一一個會改變現有伺服器行為**的 P，之前兩步都刻意保持零副作用。

## 📋 背景與查證

- 對照 Java `World.Respawn`：`WorldTimer.getInstance().register(new Respawn(), 3000)`，每 3
  秒巡一次所有地圖（`handleMap`），非同步、單一計數器 `numTimes` 遞增。MapleForge 是每頻道
  一個 process（不像 Java 單一 process 內巡全部頻道），所以排程器巡邏範圍是「這個 channel
  process 自己持有的 field」，這是架構差異造成的必要調整，不是刻意偏離。
- 排程間隔選 3 秒，忠實對照 Java（掉落物過期檢查在 Java 端不像寵物飢餓/坐騎疲勞那樣被
  `numTimes % X` 額外降頻，每次 `handleMap` 呼叫都會檢查，所以周期就是 `Respawn` 本身的 3
  秒）。
- **關鍵風險（設計文件早已預警，這裡是第一次真正撞上）**：`docs/design/in-game-執行期狀態
  架構.md`「風險#1」明講 `FieldInstance` 刻意不用 `ConcurrentDictionary`，領域變更要序列化
  （目前的實際作法是呼叫端 `lock(field)`，見 P056/P058 等既有戰鬥/拾取 handler）。背景排程器
  是獨立執行緒，若直接呼叫 `DropService.ExpireDrops` 而不上鎖，會跟其他玩家連線執行緒同時
  修改同一個 `Dictionary`（`FieldInstance._objects`）——**這個併發風險在第一輪實作時被漏掉**，
  是在把 lock 拿掉後才意識到要補回去（`lock` 不能橫跨 `await`，所以只把同步的
  `_drops.ExpireDrops(...)` 包進 `lock(field)`，非同步廣播留在鎖外，跟既有戰鬥 handler
  同款寫法）。已在程式碼註解記下這個教訓。
- **不移植的部分**（沿用 P062 已記錄的判斷）：Java 的 `randDrop`（過期自動補生隨機獎勵箱）
  分支繼續不做；`everlast` 地圖旗標繼續不存在（P061 已記錄）。

## 🔧 實作內容

- **`Maple.Application`**：
  - `IFieldInstanceRegistry` 新增 `All`（`IReadOnlyCollection<FieldInstance>`），
    `InMemoryFieldInstanceRegistry` 實作為鎖內快照（跟 `GetOrCreate` 共用同一把 `_gate`）。
  - `IMapSessionRegistry` 新增 `GetAll(mapId)`（不排除任何人，區別於既有 `GetOthers` 的排除
    語意——背景排程器沒有「自己」），`InMemoryMapSessionRegistry` 實作沿用
    `ConcurrentDictionary` 既有讀取安全性。
- **`Maple.Adapters.V113`**（新檔 `V113DropExpiryHandler.cs`）：`public sealed class
  V113DropExpiryHandler`——單一 field 的 tick 處理單位，`ExpireDropsAsync(field, now, ct)`：
  `lock(field)` 內呼叫 `DropService.ExpireDrops` 拿到過期清單，鎖外用 `IMapSessionRegistry
  .GetAll` 取得場上所有玩家，逐一廣播 `V113DropPackets.RemoveItemFromMap(objectId, animation:
  0)`（best-effort，斷線 session 忽略例外）。跟 `V113GuildOperationHandler`/`V113SummonHandler`
  一樣是薄封裝角色，排程節奏不歸它管。
- **`Maple.Host.Shared`**（新檔 `DropExpiryHostedService.cs`）：`internal sealed class
  DropExpiryHostedService : BackgroundService`——`PeriodicTimer(3 秒, TimeProvider)` 迴圈，
  每次 tick 巡 `IFieldInstanceRegistry.All` 逐一呼叫 `V113DropExpiryHandler.ExpireDropsAsync`，
  單一 field 處理失敗（例外）只記警告並繼續下一個，不讓整個排程器掛掉。`TimeProvider?
  timeProvider = null` 沿用專案既有的 DI-safe 可選參數慣例（`StatsService`/
  `V113BuffItemHandler` 同款寫法，避免需要額外註冊 `TimeProvider` 服務）。
  - `MapleServerHost.cs`：註冊 `V113DropExpiryHandler`（singleton）+
    `AddHostedService<DropExpiryHostedService>()`。

## ✅ 結果與結論

- **這是 M4-2 三步驟計畫的第一個真正落地成果**：伺服器啟動後，地圖上的掉落物現在會在 120
  秒後真的消失並廣播給玩家看見，忠實對照 Java 行為。
- 過程中補上的 `lock(field)` 併發保護是這次最重要的教訓：**任何要新增背景排程器/週期性
  任務的後續工作，只要會碰觸 `FieldInstance`，都必須複查是否需要 `lock(field)`**——這點已經
  記進這篇任務歷程，供 M4-2 後續項目（怪物重生等）直接參考，不需要重新踩一次坑。
- `DropExpiryHostedService` 建立的排程器骨架（`PeriodicTimer` + 逐 field 巡邏 + 單一 field
  失敗不影響其他 field）可以直接被 M4-2 後續項目重用，不需要另開一個 `BackgroundService`——
  可以考慮之後把它重構成通用的「WorldTickHostedService」讓多個 tick 消費者（掉落物過期、
  未來的怪物重生等）掛在同一個排程迴圈下，但這個重構本身留給有實際第二個消費者出現時再做
  （避免對只有一個使用者的抽象過度設計）。
- M4-2 里程碑至此完成第一個具體切片（掉落物過期）。里程碑本身仍未完結——怪物重生、寵物
  飢餓衰減、坐騎疲勞等其餘 Java `handleCooldowns`/`Respawn` 項目仍待後續評估是否要接上同一個
  排程器骨架，這些留給使用者決定優先順序。
