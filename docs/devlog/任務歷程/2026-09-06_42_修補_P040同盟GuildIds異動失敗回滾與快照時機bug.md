## 🎯 目標（執行前先寫死，過程不偷改）

比照 P036/P037/P039 對 `GuildService` 的修法，檢查 `AllianceService` 是否有相同的
「物件欄位異動先於持久化、失敗未回滾導致重試被自身狀態擋死」問題。完成判準：
`AddGuildLockedAsync`/`RemoveGuildAsync` 在持久化失敗後，`Alliance.GuildIds` 要能正確
復原到操作前狀態，讓呼叫端可以安全重試。

## 📋 背景與查證

- 全檔案 grep 確認 `TrackAllianceLocked`/`UntrackAllianceLocked` 呼叫點（`CreateAllianceAsync`、
  `InviteGuildAsync`、`AcceptInviteAsync`、`ChangeLeaderAsync`、`UpdateRanksAsync`、
  `UpdateNoticeAsync` 等）本來就都是「持久化成功後才追蹤」，順序正確，不需修。
- 只有 `AddGuildLockedAsync`（`TryAddGuild`）與 `RemoveGuildAsync`（`TryRemoveGuild`）在
  持久化之前就先對 `Alliance.GuildIds` 做物件欄位異動，跟 P039 修過的
  `Guild.Members`（`TryAddMember`/`TryRemoveMember`）是同一種缺口形狀。
- `Alliance.GuildIds` 是 `public List<int> GuildIds { get; set; }`（有 public setter），
  可以直接整份快照/復原，不需要像 Guild 那樣逐一呼叫 Try 方法逆向操作。

## 🔧 實作內容

- **`Maple.Application`**（`src/Maple.Application/Alliances/AllianceService.cs`）：
  - `RemoveGuildAsync`：原本就已經在 `TryRemoveGuild` **之前**拍下 `guildIdsBeforeRemove`
    快照，順序本來就對，兩個分支（`DeleteAsync` 解散 / `SaveAsync` 一般移除）補上
    `try/catch` 失敗時 `alliance.GuildIds = guildIdsBeforeRemove` 後 rethrow。
  - `AddGuildLockedAsync`：**第一版有 bug**——快照 `guildIdsBeforeAdd` 是在
    `TryAddGuild(guildId)` 呼叫「之後」才拍下，導致快照本身已經包含新加入的
    `guildId`，`catch` 區塊的「復原」等於把 `GuildIds` 設回它自己（新公會仍在清單
    裡）。改成把快照移到 `TryAddGuild` 呼叫「之前」，才是真正的操作前狀態。

## 🧪 測試

- 新增 `tests/Maple.Application.Tests/Alliances/AllianceServiceTests.cs`（本檔案首次出現
  `AllianceService` 的單元測試），含 `FakeAllianceRepository`（`ThrowOnNextSave`/
  `ThrowOnNextDelete` 一次性故障注入）與 `NoOpGuildRegistry`（只有 `SetAllianceIdAsync`
  可用）兩個測試替身：
  - `AddGuildAsync_RepositorySaveFails_GuildIdsRollback_CanRetry`
  - `RemoveGuildAsync_NonLeaderGuild_RepositorySaveFails_GuildIdsRollback_CanRetry`
  - `RemoveGuildAsync_LeaderGuild_RepositoryDeleteFails_GuildIdsRollback_CanRetry`
- 過程紀錄：
  1. 第一次跑測試「沒有拋出例外」——原因是 `CreateAllianceAsync` 用預設
     `Alliance.InitialCapacity = 2`，測試建立時只給 leader+partner 兩個公會就已經
     滿額，`AddGuildAsync` 的 `TryAddGuild` 在呼叫到故障注入的 `SaveAsync` 之前就先
     因為 `AllianceFull` 提前回傳。改成 `CreateAllianceAsync(..., capacity: 3)` 後
     故障注入才真正生效。
  2. 修正後測試變成 `Assert.True(retry.Succeeded)` 失敗——追查發現就是上述
     `AddGuildLockedAsync` 的快照時機 bug；修正快照位置後三組測試全數通過。
- `dotnet build` 0 warning/0 error；全 8 個測試專案 957 passed / 1 skipped
  （P039 收案基準 954 +3：Application 253→256）；Core/Application 禁區 grep clean。

## ✅ 結果與結論

- `RemoveGuildAsync` 本來就寫對了（快照在異動前），只是缺 try/catch 復原；
  `AddGuildLockedAsync` 則是「try/catch 骨架看起來對，但快照時機錯」——這種
  bug 光看程式碼結構容易誤判為已修好，必須靠「失敗後立刻重試」的測試才能
  真正驗證復原邏輯有沒有生效，呼應 P039 的教訓：判斷回滾正確性不能只讀程式碼。
- `Alliance.GuildIds` 有 public setter，回滾用整份 List 覆蓋即可，比 Guild 需要
  用 `TryAddMember`/`TryRemoveMember` 逆向操作更單純、更不容易寫錯——但這次仍然
  因為「快照時機」而不是「復原手法」本身出錯，提醒即使是看似簡單的複製/還原，
  也要注意快照必須在第一次物件欄位異動「之前」拍下。
