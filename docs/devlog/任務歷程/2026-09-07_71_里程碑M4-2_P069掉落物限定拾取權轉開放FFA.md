## 🎯 目標（執行前先寫死，過程不偷改）

延續 M4-2 排程器骨架，追查 P062 規劃階段順手發現的另一個 Java `World.handleMap` 世界 tick
項目：`item.shouldFFA()`——限定主人（`dropType=0`）/限定隊伍（`dropType=1`）的掉落物滿 30
秒還沒被撿走，就轉成任何人可撿（`dropType=2`）。跟掉落物過期是同一個資料模型
（`MapDrop`）、同一個排程器（`WorldTickHostedService`→`V113DropExpiryHandler`），是目前
排程器骨架最低成本的一次擴充。

## 📋 背景與查證

- 對照 Java：`MapleMap.spawn*Drop` 系列方法在 `dropType == 0 || dropType == 1` 時呼叫
  `mdrop.registerFFA(30000)`；`World.handleMap`（跟掉落物過期同一段迴圈）檢查
  `item.shouldFFA()` 就 `item.setDropType((byte) 2)`——**這個狀態轉換本身不廣播任何封包**，
  純粹是伺服器內部拾取權限判斷用的旗標翻轉，跟過期需要 `REMOVE_ITEM_FROM_MAP` 廣播不同。
- 查證 MapleForge 現況：`MapDrop` 已經有 P061 建立的 `SpawnedAt`，`DropService.CanPickUp`
  現有邏輯（`dropType>=2` 一律允許、否則限定 `OwnerId`）本來就會在 `DropType` 真的變成 2 之後
  自動放行——不需要改 `CanPickUp` 任何一行，只要把 `DropType` 這個狀態在對的時間點翻轉，
  既有的拾取權限判斷就自然生效。
- 因為不需要廣播，這次選擇**不新增獨立的 handler 方法**，而是直接讓 P063 建立的
  `V113DropExpiryHandler.ExpireDropsAsync` 在同一個 `lock(field)` 區塊內多做一步
  `PromoteFfaDrops`，貼近 Java 原版「掉落物過期跟 FFA 轉換本來就是同一段迴圈依序做」的
  結構，也避免為一個不需要 I/O 的純狀態變更多包一層 async handler。

## 🔧 實作內容

- **`Maple.Core`**（`MapDrop.cs`）：
  - `DropType` 從純唯讀屬性改成 `private set`（沿用專案既有的「用具名方法做受控狀態轉換」
    風格，不直接開放外部任意賦值）。
  - 新增 `public static readonly TimeSpan FfaAfter = TimeSpan.FromMilliseconds(30_000)`。
  - 新增 `ShouldBecomeFfa(now)`：`!IsPickedUp && DropType < 2 && now - SpawnedAt >= FfaAfter`，
    對照 Java `shouldFFA()` 逐行核對。
  - 新增 `MarkFfa()`：`DropType = 2`。
- **`Maple.Application`**（`DropService.cs`）：新增 `PromoteFfaDrops(field, now)`——掃
  `field.Objects.OfType<MapDrop>()`，命中 `ShouldBecomeFfa` 就 `MarkFfa()`，回傳轉換清單
  （供測試直接驗證，呼叫端不需要拿這個清單做任何事，因為沒有廣播需求）。
- **`Maple.Adapters.V113`**（`V113DropExpiryHandler.cs`）：`ExpireDropsAsync` 的 `lock(field)`
  區塊內，`_drops.ExpireDrops` 之前先呼叫 `_drops.PromoteFfaDrops`——兩個領域操作在同一次鎖
  裡依序完成，跟 Java 原版行為結構一致，也不需要額外的鎖或 async 邊界。

## ✅ 結果與結論

- **這是繼掉落物過期（P063）、怪物重生（P067）後第三個真正改變伺服器行為的 P**：限定
  主人/隊伍的掉落物現在會在 30 秒後對其他玩家開放拾取，忠實對照 Java 行為。
- 排程器骨架的重用價值再次驗證：這次甚至不需要新增 handler 方法或修改
  `WorldTickHostedService` 本身，只在既有的 `V113DropExpiryHandler.ExpireDropsAsync` 裡加一行
  呼叫就完成——因為這個項目跟掉落物過期共用同一個資料模型（`MapDrop`）跟同一個 Java 世界
  tick 迴圈，是目前為止成本最低的一次擴充。
- 查證過程中順手發現 `DropService.SpawnDropsFromMonster` 目前把怪物擊殺掉落物的
  `dropType` 寫死成 `0`（程式碼註解「Java: solo non-FFA monster drop」），對照 Java 實際上
  組隊擊殺時應該是 `dropType=1`（隊伍限定，隊友可撿）——這是另一個獨立範圍的缺口（涉及
  `DropService` 要能查詢擊殺者是否在隊伍中，可能需要注入 `IPartyRegistry`），跟這次的 FFA
  轉換不同層次，記下留給後續 P-phase 評估（`CanPickUp` 目前也沒有比照 Java 補上隊伍成員
  可撿 `dropType=1` 掉落物的判斷，是同一組缺口的兩個面向）。
