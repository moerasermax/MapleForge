## 🎯 目標（執行前先寫死，過程不偷改）

延續 P061 訂下的三步驟計畫，這是第二步：在 `Maple.Application` 層新增
`DropService.ExpireDrops(field, now)` 用例——給定一個 field 跟時間，找出該過期的掉落物、
標記已撿走並從場上移除、回傳被移除清單。**仍然刻意不接任何背景排程器**，這個方法目前
沒有任何生產程式碼呼叫它，只透過單元測試直接呼叫驗證行為正確——把「副作用邏輯本身對不
對」跟「排程器什麼時候、多頻繁觸發它」兩個問題繼續分開驗證。

## 📋 背景與查證

- 對照 Java `MapleMapItem.expire(map)`：`pickedUp = true` → 廣播
  `removeItemFromMap(objectId, 0, 0)`（`animation=0` 代表 Expire，向下相容既有 P056 已用過的
  `V113DropPackets.RemoveItemFromMap` 簽章，只是這次要傳 `animation: 0` 而非既有 pickup 路徑
  用的 `animation: 2`）→ `map.removeMapObject(this)` → 若 `randDrop` 為真則補生一個隨機獎勵箱。
- **刻意不移植的部分**：`randDrop` 分支（過期後自動補生隨機獎勵箱）綁在掉落表系統一個獨立
  旗標上，MapleForge 目前的 `MonsterDropEntry`/掉落表資料模型沒有對應欄位，這是另一個獨立
  範圍的資料/邏輯缺口，不在這次動；廣播封包本身（`RemoveItemFromMap`）也還沒接，因為
  Application 層本來就不該知道怎麼編碼封包——這塊留給 P063 的排程器（Adapter/Host 層）處理。
- 沿用既有 `TryPickup` 的成熟模式（`TryMarkPickedUp()` 判斷成功才 `field.Remove`），保持跟同一
  個服務裡其他掉落物生命週期方法一致的寫法，不另外發明新模式。

## 🔧 實作內容

- **`Maple.Application`**（`DropService.cs`）：新增 `ExpireDrops(FieldInstance field,
  DateTimeOffset now)`——`field.Objects.OfType<MapDrop>().ToArray()`（先物化成陣列，避免邊
  遍歷邊 `field.Remove` 觸發「集合被修改」例外）逐一檢查 `ShouldExpire(now)`，命中就
  `TryMarkPickedUp()` + `field.Remove(drop.ObjectId)`，回傳所有被移除的 `MapDrop`。

## 🧪 測試

  `ExpireDrops_RemovesOnlyDropsPastThreshold`（field 內混有已過期跟還沒過期的掉落物，只有
  過期那個被移除且回傳，field 裡的另一個不受影響）、

  不受影響）。

## ✅ 結果與結論

- 跟 P061 一樣，這步**刻意不改變任何現有伺服器行為**——`ExpireDrops` 存在且測試通過，但
  沒有任何排程器或 handler 呼叫它，玩家端完全感受不到差異。
- M4-2 三步驟計畫至此走完前兩步（資料模型/純函式 → 可測試用例），第三步（P063+）是真正
  的臨界點：在 `Maple.Host.Shared` 新增第一個 `PeriodicTimer` 型 `BackgroundService`，需要
  額外解決兩個目前還沒碰過的問題——(1) 如何列舉所有活躍的 `FieldInstance`
  （`InMemoryFieldInstanceRegistry` 目前只有 `GetOrCreate`，沒有列舉能力，需要新增）；(2) 移除
  掉落物後怎麼把 `RemoveItemFromMap` 封包廣播給場上玩家（需要知道哪些玩家在該地圖/頻道，
  這塊要重用既有的 `IMapSessionRegistry`/`BroadcastPacketToMapAsync` 慣例，但呼叫端是背景
  服務而非某個玩家的連線 session，廣播路徑要重新接一次）。這兩點會是 P063 的主要工作範圍。
