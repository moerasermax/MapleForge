## 🎯 目標（執行前先寫死，過程不偷改）

玩家斷線（非主動按 EXIT 離開密友聊天）時，MapleForge 完全沒有清理密友聊天（Messenger）狀態，
對照 Java `MapleClient` 斷線流程會呼叫 `World.Messenger.leaveMessenger(messengerid, chrm)`。完成
判準：玩家斷線時若身處某個 Messenger，要被移出且其他成員收到移除通知（沿用主動 EXIT 已有的
`RemoveMessengerPlayer` 廣播邏輯）；未加入任何 Messenger 的玩家斷線不觸發任何動作；單元測試覆蓋
兩種情況。

## 📋 背景與假設

- Java 來源：`MapleClient.java` 的斷線清理流程（`disconnect`/`logout` 路徑）中有一段呼叫
  `World.Messenger.leaveMessenger(messenger.getId(), player)`，緊接著對其餘成員廣播移除封包——
  行為與玩家主動按「退出密友聊天」按鈕（`CMessengerHandler` MODE=EXIT）完全一樣，Java 是直接重用
  同一段登出/離開邏輯。
- MapleForge 現況：`V113MessengerHandler.HandleExitAsync`（僅由 client 主動送出的 EXIT opcode 觸發）
  已經正確實作「離開 Messenger + 廣播 RemoveMessengerPlayer」，但 `V113ChannelConnectionHandler.cs`
  的斷線清理區塊（`_guildOperationHandler.OnPlayerLoggedOutAsync`/`_buddyHandler.OnPlayerLoggedOutAsync`
  所在的 best-effort 通知區塊）完全沒有呼叫任何 `_messengers`/Messenger 相關方法——經 grep 全檔案
  確認零匹配。這是純粹的遺漏（缺配線），不是刻意的架構選擇，需要修。
- 修法：不重寫邏輯，直接把 `HandleExitAsync` 私有方法抽成共用的 `LeaveMessengerAndNotifyAsync`，
  對外新增一個公開方法 `NotifyDisconnectAsync(Player, CancellationToken)`（語意上對應斷線觸發，
  內部呼叫同一段共用邏輯），再於 `V113ChannelConnectionHandler.cs` 的登出通知區塊比照
  `_guildOperationHandler.OnPlayerLoggedOutAsync`/`_buddyHandler.OnPlayerLoggedOutAsync` 的呼叫模式
  加一行 `_messengerHandler.NotifyDisconnectAsync(player, CancellationToken.None)`。
- 範圍邊界：僅處理「斷線觸發離開」這一個缺口。Messenger 其餘功能（邀請、聊天、加入）已存在且不動。

- 找到的是「純配線遺漏」類型的 bug（邏輯已存在，只是沒被斷線路徑呼叫），修法是重構出共用方法

  檢查清單項目。
