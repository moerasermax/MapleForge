## 🎯 目標（執行前先寫死，過程不偷改）

P029 收尾明確記下：`V113UseCashItemHandler.cs` 有兩處 VipRock TODO（現金道具傳送石／
任意門票的「使用」流程），範圍比 TROCK_ADD_MAP 大，留給後續獨立查證。完成判準：
`HandleCashTeleportRock`（mode=0 地圖模式）與 `HandleAnyDoorTicket` 在目前地圖或目標
地圖任一設有 `FieldLimitType.VipRock` 旗標時擋下傳送，沿用 P029/P030 已就緒的
`MapService`/`FieldLimitType` 基礎元件。

## 📋 背景與查證

- 對照 Java `InventoryHandler.UseTeleRock`（現金傳送石地圖模式，2320000/5040000/5040001/
  5041000）與 `InventoryHandler.UseCashItem` 任意門分支（5560000/5561000）：兩者都在
  `changeMap` 之前檢查 `!FieldLimitType.VipRock.check(目前地圖) && !FieldLimitType.VipRock.check(目標地圖) && getEventInstance() == null`，任一旗標成立就整段跳過（`used` 維持
  `false`，靜默略過、不送錯誤訊息，但方法尾端仍會送 `enableActions()`，對照 C# 既有的
  `EnableActionsOnly()` 慣例）。
- 查證發現 Java 這兩處判斷式其實比「純 VipRock」更大：還包含楓之島（MapleLand）排除、
  傳送石已註冊地圖清單驗證（`isRockMap`/`isRegRockMap`）、大陸比對、`EventInstance` 排除、
  玩家導向傳送模式。這次**刻意只做 VipRock 場地限制**這一項可獨立驗證的切片，
  其餘留給後續：MapleLand／已註冊地圖清單驗證需要新增查詢方法（C# 目前只有
  `AddRegularRock`/`AddVipRock` 等新增/移除方法，沒有純查詢的 `IsRockMap`/
  `IsRegularRockMap`）、`EventInstance` 排除依賴尚未存在的活動副本子系統（MONSTER_CARNIVAL
  同一批未做功能）、玩家導向傳送模式依賴跨玩家查找基礎設施，範圍都明顯更大。
