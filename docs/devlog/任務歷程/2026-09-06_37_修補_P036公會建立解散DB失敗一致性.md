## 🎯 目標（執行前先寫死，過程不偷改）

使用者請 ai-cli（Codex）對 MapleForge 與 Java 舊版架構做獨立第二意見時，抽樣發現一個真實風險：
`GuildService.CreateGuildAsync`（registry 層）「先改 registry 記憶體，再寫 DB」，中間沒有回滾，
`_repository.AddAsync` 拋例外時會留下部分成功狀態。查證後確認這個風險真實存在，且
`DisbandGuildAsync`（P024 寫的）也有同一種反向風險。完成判準：兩個方法改成「先確保持久層成功，
再更新記憶體 registry」，DB 失敗時記憶體狀態完全不變（不需要 rollback 邏輯，用順序保證代替）。

## 📋 背景與查證

- **`CreateGuildAsync` 的風險**：原本的順序是 `_guilds.Add(...)` → `_guildByCharacter.Add(...)` →
  `await _repository.AddAsync(guild, ct)`。若 `AddAsync` 拋例外（DB 連線問題等），registry 已經
  登記了 `characterId → guildId` 映射，但這筆公會從未真正寫進 DB。該角色之後再嘗試建公會，
  `_guildByCharacter.ContainsKey(leader.CharacterId)` 恆為真，回 `AlreadyInGuild`——**該角色被
  永久卡死，再也建不了公會**，直到 process 重啟清空記憶體 registry 為止。
- **`DisbandGuildAsync` 的風險**（方向相反、後果更隱蔽）：原本順序是先把成員從
  `_guildByCharacter` 移除、把公會從 `_guilds` 移除，才呼叫 `_repository.DeleteAsync`。若
  `DeleteAsync` 拋例外，registry 已經認為公會不存在（成員可以另建/加入新公會），但 DB 那筆
  紀錄還在。**process 重啟後這個「已解散」的公會會從 DB 重新載入、詐屍復活**，但此時成員可能
  早就以為自己沒有公會、已經加入別的公會了——比 CreateGuild 的風險更難察覺，因為錯誤要等到
  下次重啟才會顯現。
- 兩者都在同一把 `_gate`（`SemaphoreSlim`）保護下執行，`finally` 區塊確保鎖一定會釋放（不會
  因為例外而死鎖），純粹是「記憶體異動」跟「持久層異動」的順序反了。

## 🔧 實作內容

- **`Maple.Application`**（`src/Maple.Application/Guilds/GuildService.cs`）：
  - `CreateGuildAsync`（registry 層）：改成先 `await _repository.AddAsync(guild, ct)`，成功後
    才 `_guilds.Add(...)` + `_guildByCharacter.Add(...)`。
  - `DisbandGuildAsync`：改成先 `await _repository.DeleteAsync(guildId, ct)`，成功後才把成員
    從 `_guildByCharacter` 移除、公會從 `_guilds` 移除。
  - 兩處都不需要額外的 rollback 邏輯——因為只是把「持久層寫入」搬到「記憶體異動」之前，例外
    自然會在任何記憶體異動發生前就往外拋，記憶體狀態保持跟拋例外前一樣（等同於整個操作沒發生
    過），比寫 try/catch + 手動回滾更簡單也更不容易漏寫。

## ⏯️ 接手點

`GuildService.cs` 裡另外約 10 個 `UpdateAsync` 呼叫點（`ChangeRankAsync`/`ChangeRankTitlesAsync`/
`ChangeEmblemAsync`/`ChangeNoticeAsync`/`IncreaseCapacityAsync` 等）也是同樣的「先改物件欄位、
再寫 DB」模式，但風險性質不同——那些是**物件欄位值**在失敗後暫時跟 DB 不同步（下次成功寫入會
自我修正、不會造成 registry 字典層級的永久不一致），比這次修的「registry 字典結構不一致」風險
低很多，且涉及範圍是全部 update 類方法（系統性重構等級），這次刻意不展開，留給後續評估是否需要
統一的交易/回滾機制。同樣的「持久層優先、記憶體異動延後」模式若後續要應用到其他 registry
（Alliance/Family 等），建議個別查證各自的失敗後果再決定優先順序。

## ✅ 結果與結論

- 這是本輪第一次由**外部（第二意見）而非我方排查手法**找到的缺口——使用者請 Codex 做架構第二
  意見時抽樣抓到的，證明外部/獨立視角確實能看到我方排查方法論的盲點（P021-P035 全部聚焦在
  「功能是否接線完整」，沒有專門審視「持久層失敗時的狀態一致性」這個維度）。
- 選擇「重排順序」而非「加 rollback」是刻意的取捨：這類 in-memory + repository 雙寫模式，用
  「先確保外部依賴成功，再異動本地狀態」的簡單排序就能達到跟 rollback 邏輯相同的一致性保證，
  且更不容易在未來新增程式碼時漏寫（rollback 邏輯需要每個新的失敗路徑都記得補，排序保證只要
  維持「持久層在前」的慣例即可）。
