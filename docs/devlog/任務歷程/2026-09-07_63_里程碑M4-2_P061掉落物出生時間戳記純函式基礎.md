## 🎯 目標（執行前先寫死，過程不偷改）

使用者拍板啟動 M4-2「世界 tick 排程器」里程碑（任務追蹤.md 早已記錄「怪物 AI／移動
tick／respawn scheduler 尚未正式完成」）。沿用 FamilyService 並行改造（P051-053）驗證過的
「先拆出純函式與資料模型，最後才接上真正的排程器與行為」三步驟劇本，這是第一步：
掉落物（`MapDrop`）補上出生時間戳記 + 對照 Java `shouldExpire` 的純函式判斷，**刻意不接上
任何真正會移除掉落物的行為**——伺服器目前的實際運作（掉落物永不過期）在這個 P 完全不變，
只是把「該不該過期」這個問題變成可查詢、可單元測試的能力。

## 📋 背景與查證

- 追蹤 P061 候選過程中，順藤摸瓜追出 Java `handling.world.World.handleMap`/`handleCooldowns`：
  一個全域 world timer 迴圈（`numTimes` 遞增計數器）驅動多項週期性行為——冷卻/減益到期、
  寵物飢餓值衰減（每 100 tick）、坐騎疲勞（每 18000 tick）、地圖掉落物過期
  （`item.shouldExpire()`）、怪物重生（`map.canSpawn()`/`map.respawn()`）。MapleForge 目前
  完全沒有任何週期性背景排程機制（`Maple.Host.Shared` 唯一的 `IHostedService`
  ——`HiredMerchantReloadHostedService`——只在啟動時跑一次，不是週期迴圈）。
- 對照設計文件 `docs/design/in-game-執行期狀態架構.md`「風險#1」跟「落地順序#5」：團隊早已
  預期「並行模型（field-actor）視需要引入」，本次是第一次真正需要引入的時機。
- 選擇掉落物過期作為 M4-2 的第一個真實行為切片（而非怪物重生）：風險最低——掉落物過期
  只是移除一個已經在地圖上的物件，不影響經驗值/掉寶率/戰鬥平衡，跟怪物重生（牽動刷怪
  演算法、地圖人數判斷、可能的難度/農怪速率變化）比起來對現有玩法的影響面小很多，適合
  當作驗證整條「world tick → 逐 field 處理 → 廣播」管線的第一個試金石。
- 查證 Java `MapleMapItem.shouldExpire`：`!pickedUp && nextExpiry > 0 && nextExpiry <
  System.currentTimeMillis()`，`nextExpiry` 在 spawn 時透過 `registerExpire(120000)` 設定
  （固定 120 秒，`MapleMap.spawn*Drop` 系列方法統一呼叫，`!everlast` 地圖才會註冊——
  MapleForge 目前沒有 everlast 地圖旗標，這個例外暫不移植，統一套用 120 秒，已在程式碼
  註解跟此文件明確記下這個刻意簡化）。

## 🔧 實作內容

- **`Maple.Core`**（`MapDrop.cs`）：
  - 新增 `public static readonly TimeSpan ExpireAfter = TimeSpan.FromMilliseconds(120_000)`。
  - 建構式新增 `spawnedAt` 參數（`SpawnedAt` 唯讀屬性），`ForItem`/`ForMeso` 工廠方法新增
    對應的必要參數（不給預設值——出生時間必須由呼叫端明確傳入，不能悄悄用
    `DateTimeOffset.UtcNow` 藏起來，維持專案「時間來源集中由 TimeProvider 控管、不散落
    DateTime.Now」的既有慣例）。
  - 新增 `ShouldExpire(DateTimeOffset now)` 純函式：`!IsPickedUp && now - SpawnedAt >=
    ExpireAfter`，對照 Java 邏輯逐行核對。
- **`Maple.Application`**（`DropService.cs`）：建構式新增 `TimeProvider? timeProvider = null`
  （沿用既有 `DropServiceOptions? options = null` 的可選參數風格，預設 `TimeProvider.System`），
  3 個 `MapDrop.ForItem`/`ForMeso` 呼叫點（悔幣掉落、怪物擊殺道具/悔幣掉落）都改用
  `_timeProvider.GetUtcNow()` 帶入 `spawnedAt`。

## ✅ 結果與結論

- 這一步**刻意不改變任何現有伺服器行為**——掉落物目前依然不會真的消失，因為還沒有任何
  排程器會呼叫 `ShouldExpire`。這是有意的：先讓資料模型跟純函式判斷邏輯獨立可測試、可對照
  Java 核對正確，再在後續 P-phase 疊上真正會產生副作用（移除物件、廣播封包）的排程機制，
  降低單一 P 裡「資料模型 + 排程器 + 廣播」三件事同時出錯難以定位的風險——跟 P051（先拆
  Locked helper，不换並行原語）、P052（換原語，不動持久層順序）分階段的精神一致。
- 下一步（P062）：在 `Maple.Application` 層新增一個可測試的「給定 FieldInstance + now，找出
  該過期的掉落物並從場上移除」用例（先不接背景排程器，用單元測試直接呼叫驗證），把
  `MapDrop.ShouldExpire` 這個純函式跟「真的動手移除」的副作用之間再插一層可控制的邊界。
- 之後（P063+）：在 `Maple.Host.Shared` 新增第一個真正的週期性 `BackgroundService`
  （`PeriodicTimer`），把 P062 的用例接上並對每個活躍 field 廣播移除封包給場上玩家——這才是
  真正讓玩家看見「掉落物會消失」的最後一塊拼圖，也是怪物重生等後續 M4-2 項目可以直接重用
  的排程器骨架。
