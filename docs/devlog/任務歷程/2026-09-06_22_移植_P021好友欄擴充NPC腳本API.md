## 🎯 目標（執行前先寫死，過程不偷改）

P011→P020 收官後留下的零呼叫者候選之一：`V113BuddyPackets.UpdateBuddyCapacity` 已寫好封包格式
但全專案零呼叫者。上一輪判斷「需要先確認 NPC 賣家腳本是否已移植到 `scripts/npc/*.js`」，本輪查證
發現該判斷的前提有誤（詳見下方背景）。完成判準：`cm.getBuddyCapacity()` / `cm.updateBuddyCapacity()`
兩個腳本 API 從 Application 層到 Adapter 層完整接通，兩支既有 Java NPC 腳本（1002003.js / 2040046.js）
不需改一行就能正常運作；單元測試覆蓋 `NpcContext` 領域行為與 `NpcConversation` 送包時機。

## 📋 背景與假設

- **上一輪判斷的前提有誤**：P020 收尾時筆記寫「需要先確認 Java `NPCConversationManager.updateBuddyCapacity`
  對應的 NPC 賣家腳本是否已移植到 `scripts/npc/*.js`（本輪未找到）」——這次查證才發現 MapleForge
  的 NPC 腳本引擎（`JintNpcScriptFactory`）刻意**不複製、不改寫**任何 Java `.js` 腳本，而是在執行期
  直接讀取 sibling 目錄 `MapleStory_Server/scripts/npc/{npcId}.js`（見
  `src/Maple.Host.Shared/Configuration/ServerInstanceOptions.cs:40` 的 `ScriptsDirectory` 預設值，
  以及 `JintNpcScriptFactory` 類別註解「用 Jint 跑既有 OdinMS NPC .js 腳本（不重寫腳本）」）。
  上一輪在 MapleForge repo 內（`scripts/npc/`）找不到這兩支腳本，就判斷「未移植」——但 MapleForge
  repo 本來就不會有任何 `.js` 檔案（`find . -iname "*.js"` 全專案零命中），這是設計上的必然，不是
  移植缺口。實際檢查 `MapleStory_Server/scripts/npc/1002003.js`（Mr. Goldstein，Victoria Road）與
  `2040046.js`（Robert Holly，Ludibrium）兩支腳本，內容都完整存在且會呼叫
  `cm.getBuddyCapacity()` / `cm.updateBuddyCapacity(newcapacity)`。
- **Java 呼叫鏈**（`NPCConversationManager.java:699`）：
  ```java
  public void updateBuddyCapacity(int capacity) {
      c.getPlayer().setBuddyCapacity((byte) capacity);
  }
  ```
  `MapleCharacter.setBuddyCapacity`（`MapleCharacter.java:4837-4840`）：
  ```java
  public void setBuddyCapacity(byte capacity) {
      buddylist.setCapacity(capacity);
      client.sendPacket(MaplePacketCreator.updateBuddyCapacity(capacity));
  }
  ```
  即：設定容量後**立即送包**通知客戶端，非登入時批次同步、也非跟隨其他封包附帶送出。全域搜尋
  Java 原始碼確認 `setBuddyCapacity`/`updateBuddyCapacity` 唯一呼叫入口就是 NPC 腳本
  `cm.updateBuddyCapacity`，沒有其他觸發路徑（無 GM 指令、無道具效果、無任務獎勵）。
- **封包格式已驗證正確**：`MaplePacketCreator.updateBuddyCapacity`（`MaplePacketCreator.java:2847-2852`）
  寫 `BUDDYLIST` opcode + `0x15` + `capacity` 一個 byte，與既有的
  `V113BuddyPackets.UpdateBuddyCapacity` 完全一致，本輪不需要改封包格式，只補上「誰會呼叫它」。
- **對照 MapleForge 既有的 `cm` 橋接模式**：`NpcContext`／`INpcScriptContext`／`NpcConversation` 三層
  已有成熟的「領域類即時委派、需要送包的另外走 Pending+Flush」模式（`PendingWarp`/`PendingShop`/
  `PendingStorageNpcId` 皆同此模式，見 `docs/devlog/任務歷程/2026-06-02_12_重構_移植NPC對話腳本引擎.md`）。
  `UpdateBuddyCapacity` 需要送一個特定 S2C 封包（非單純域狀態變更，如 `GainMeso` 目前完全不送包），
  故採用相同的 `PendingXxx` + `NpcConversation.FlushAsync` 委派模式，而非直接讓 Application 層碰
  session（違反 §4 分層鐵律）。

## ✅ 結果與結論

- 這次的教訓與 P016/P019/P020 系列相反：不是誤判「不是缺陷」，而是誤判「範圍需要擴大」——
  上一輪把「MapleForge repo 內找不到 `.js` 檔案」直接解讀成「腳本未移植」，沒有先去確認 MapleForge
  的 NPC 腳本引擎架構本來就是讀取外部 sibling 目錄、原封不動執行 Java 腳本。教訓：判斷「是否需要
  前置工作」之前，要先確認現有架構的實際運作方式（哪個目錄、怎麼載入），不能只憑 repo 內搜尋
  結果就下結論範圍有多大。
- 這也是本輪十個 P-phase（P011-P020）方法論之外，新增的第四種排查手法：**零呼叫者候選的「範圍
  評估」本身也要對照神諭驗證**——上一輪把 `UpdateBuddyCapacity` 歸類為「需要先做前置設計」是草率的，
  只查了 repo 內部就下結論，沒有去查 Java 原始碼確認觸發路徑、也沒有去查 MapleForge 腳本引擎怎麼
  載入腳本。實際查證後這是一個可以在單一 P-phase 內完成、範圍完全明確的乾淨候選。
