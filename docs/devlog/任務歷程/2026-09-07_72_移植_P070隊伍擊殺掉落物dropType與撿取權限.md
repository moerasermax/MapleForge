## 🎯 目標（執行前先寫死，過程不偷改）

延續 P069 查證時順手發現的缺口：`DropService.SpawnDropsFromMonster` 把怪物擊殺掉落物的
`dropType` 寫死成 `0`（程式碼註解自己承認「Java: solo non-FFA monster drop」），對照 Java
`dropFromMonster` 實際上組隊擊殺時應該是 `dropType=1`（隊伍限定，隊友可撿，30 秒後 P069
的 FFA 排程器會自動開放給所有人）；`DropService.CanPickUp` 也沒有比照 Java 補上「隊友可撿
`dropType=1` 掉落物」的判斷。這是 `/goal 一路推到P70` 這一輪的最後一個 P-phase。

## 📋 背景與查證

- 對照 Java `MapleMap.dropFromMonster`：
  ```java
  final byte droptype = (byte) (mob.getStats().isExplosiveReward() ? 3
      : mob.getStats().isFfaLoot() ? 2
      : chr.getParty() != null ? 1
      : 0);
  ```
  四種來源：爆炸獎勵怪（3）、天生 FFA 戰利品怪（2）、擊殺者有隊伍（1）、其餘（0）。前兩種
  是綁在特定怪物模板旗標（`isExplosiveReward`/`isFfaLoot`）上的資料，MapleForge 的
  `MobStats` 目前沒有對應欄位，若要完整移植需要先擴充怪物資料模型，是另一個獨立範圍的
  缺口，這次不動；只修「有沒有隊伍」這個最常見、影響面最大的分支。
- 對照 Java `PlayerHandler.PlayerPickup` 的拾取權限判斷：`dropType==0` 只有 `getOwner() ==
  chr.getId()` 才能撿（隊友也不行）；`dropType==1` 除了主人本人，`chr.getParty() != null &&
  chr.getParty().getMemberById(mapitem.getOwner()) != null`（撿的人在主人所在的隊伍裡）也放行。
  這個「隊友放行」的例外只對 `dropType==1` 成立，`dropType==0` 沒有例外——兩者判斷邏輯不同，
  移植時要分開處理，不能用同一個條件涵蓋。
- 查證 `IPartyRegistry`：`IsCharacterInParty(characterId)`/`GetPartyForCharacter(characterId)`
  早就存在且已有先例（`DoorService` 已經用同樣的可選依賴注入模式），這次直接沿用，不需要
  新增任何隊伍系統 API。

## 🔧 實作內容

- **`Maple.Application`**（`DropService.cs`）：
  - 建構式新增 `IPartyRegistry? parties = null`（沿用 `DoorService` 已驗證過的可選依賴模式，
    DI 容器已經有 `IPartyRegistry` 註冊，不需要改 `MapleServerHost.cs`）。
  - `SpawnDropsFromMonster`：`dropType` 從寫死的 `(byte)0` 改成
    `_parties?.IsCharacterInParty(ownerId) == true ? (byte)1 : (byte)0`。
  - `CanPickUp`：從 `private static` 改成 `private`（需要讀 `_parties`），`dropType==1` 時
    新增「撿的人是否在掉落物主人所在的隊伍裡」判斷（`GetPartyForCharacter(drop.OwnerId)` 找
    主人的隊伍，`GetMember(player.Character.Id)` 確認撿的人也在裡面）；`dropType==0` 維持原判斷
    不變（沒有隊伍例外，忠實對照 Java）。
