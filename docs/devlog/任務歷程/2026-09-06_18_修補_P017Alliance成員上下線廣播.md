## 🎯 目標（執行前先寫死，過程不偷改）

P016 發現「封包建構式已存在但零呼叫者」是一類值得系統性掃描的缺口，本次對整個 `Adapters.V113`
的 `V113*Packets.cs` 逐一 grep public 方法找零呼叫者，鎖定 `V113AlliancePackets.AllianceMemberOnline`
最貼近既有 Family/Guild 上下線同步的既定模式，優先處理。完成判準：公會屬於某個同盟時，成員上下線
狀態實際翻轉會廣播給同盟裡**其他公會**的所有在線成員（來源公會整體排除，因為公會內部已經用
`GuildMemberOnline` 通知過）；公會不屬於任何同盟時不觸發、不噴例外；單元測試覆蓋上線/下線/
無同盟三種情況。

## 📋 背景與假設

- Java 來源：`MapleGuild.setOnline`（`handling/world/guild/MapleGuild.java:461`）：
  ```java
  public final void setOnline(final int cid, final boolean online, final int channel) {
      boolean bBroadcast = true;
      for (MapleGuildCharacter mgc : members) {
          if (mgc.getGuildId() == id && mgc.getId() == cid) {
              if (mgc.isOnline() == online) { bBroadcast = false; }
              mgc.setOnline(online);
              mgc.setChannel((byte) channel);
              break;
          }
      }
      if (bBroadcast) {
          broadcast(MaplePacketCreator.guildMemberOnline(id, cid, online), cid);
          if (allianceid > 0) {
              World.Alliance.sendGuild(MaplePacketCreator.allianceMemberOnline(allianceid, id, cid, online), id, allianceid);
          }
      }
  }
  ```
  `World.Alliance.sendGuild(packet, exceptionId, allianceid)` 用 **guildId** 當排除鍵（`gid != exceptionId`，
  見 `World.java:1307`），代表整個來源公會都被跳過（不是排除觸發者本人——公會內部已經在
  `broadcast(guildMemberOnline(...), cid)` 這行用「排除本人」的方式通知過了）。
- MapleForge 現況：`GuildService.SetMemberOnlineAsync`（既有，P011 之前就存在）已經正確做到「狀態
  翻轉才通知」（`changed` 旗標），`V113GuildOperationHandler.OnPlayerLoggedInAsync`/
  `OnPlayerLoggedOutAsync` 也已正確送 `GuildMemberOnline` 給同公會其他在線成員——但完全沒有第二段
  同盟層級的 cascade。`V113AlliancePackets.AllianceMemberOnline(int allianceId, int guildId,
  int characterId, bool online)` 這個封包建構式已存在（P017 開頭的全域 grep 找到），零呼叫者。
- 修法：
  1. `GuildCommandResult` 新增 `bool OnlineStatusChanged = false`（既有的 `changed` 旗標原本只影響
     `RecipientCharacterIds` 是否為空，但無法從「空清單」反推「狀態是否真的翻轉」——因為公會目前
     剛好零其他在線成員時，即使狀態真的翻轉，`RecipientCharacterIds` 也會是空的，若只靠這個清單判斷
     會誤判成「沒翻轉」而漏發同盟通知）。
  2. `V113GuildOperationHandler` 新增 `AllianceService` 依賴，新增私有方法
     `BroadcastAllianceMemberOnlineAsync`：解析 allianceId（沿用 P009/P010 已驗證過的
     「guild.AllianceId 快取優先，沒有再問 AllianceService」解析順序）→ 用 `AllianceService.
     GetAllianceInfoAsync` 取得同盟裡的 `GuildIds` → 排除來源公會 → 對其餘每個公會的每個在線成員
     送 `AllianceMemberOnline` 封包。
  3. `OnPlayerLoggedInAsync`/`OnPlayerLoggedOutAsync` 在既有的公會內部廣播之後，若
     `result.OnlineStatusChanged` 則額外呼叫這個新方法。
- 範圍邊界：只補「同盟層級的上下線 cascade 通知」，不動既有的公會內部通知邏輯（那段本來就對）。

## ✅ 結果與結論

- 這次驗證了 P016 提出的「系統性 grep 每個 Packets 檔案找零呼叫者」手法確實能穩定挖出同一類缺口
  （P015 Family 資料同步 → P016 Family 通知廣播 → P017 Guild/Alliance 通知廣播，三個 P 一脈相承）。
- Java 原始碼裡「排除鍵」到底是 characterId 還是 guildId，光看呼叫端的變數名稱容易搞混（`exceptionId`
  這個參數名沒有透露它其實是 guildId）——這次先往下追了兩層方法定義（`sendGuild`→`sendGuildPacket`
  的姊妹方法 `sendGuild(byte[],int,int)`）才確認語意，再次印證「命名和行為不一致是舊碼常態，要往下
  追到底層實作」的鐵律。
- `GuildCommandResult` 新增的 `OnlineStatusChanged` 欄位是本次踩到的一個小陷阱教訓：「recipients 清單
  是否為空」不能拿來反推「狀態是否翻轉」，因為兩者在「翻轉了但剛好沒有其他在線成員」這個邊界情況下
  會給出錯誤答案——這類「用衍生資料反推原始判斷」的簡化，未來要更小心。
