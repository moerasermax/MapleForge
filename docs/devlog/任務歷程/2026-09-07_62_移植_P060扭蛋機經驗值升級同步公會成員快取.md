## 🎯 目標（執行前先寫死，過程不偷改）

P059 完成公會成員升級同步（`GuildMemberLevelJobUpdate`），但只接了打怪經驗值升級這條
主要途徑，明確記錄「道具/藥水直接領經驗值升級」路徑（`V113BuffItemHandler`）刻意留給
後續。這次把同一款檢查也接進 MapleForge 目前唯一另一個會呼叫 `GainExperience` 的地方——
扭蛋機經驗值兌換（`HandleGachExp`）。完成判準：升級時一樣觸發公會成員快取同步 + GP +
廣播，跟 P059 打怪路徑的行為完全一致。

## 📋 背景與查證

- P059 收尾時已經查證過：MapleForge 全專案只有兩處呼叫 `Player.Stats.GainExperience`——
  `SendMobKillRewardsAsync`（P059 已接）跟 `V113BuffItemHandler.HandleGachExp`（本次目標）。
  Java 端 `MapleGuild.memberLevelJobUpdate` 本來就是任何等級變動都會觸發，不分經驗值來源，
  所以這條路徑理論上本來就該覆蓋，只是 P059 為了控制單次改動的檔案數量刻意先留著。
- 查證 `V113BuffItemHandler` 結構：`HandleGachExp` 回傳 `V113BuffItemHandleResult`（不含
  `session`/廣播能力），實際發送封包跟公會廣播都要靠中央 dispatcher 的
  `HandleBuffItemResultAsync` 完成——沿用它既有的 `CharacterMutated` 旗標模式，新增同款的
  `LeveledUp` 旗標，兩邊職責邊界跟 P059 的 `SendMobKillRewardsAsync`（直接讀
  `PlayerStatsMutation.Updates`）不同，但殊途同歸。

## 🔧 實作內容

- **`Maple.Adapters.V113`**（`V113BuffItemHandler.cs`）：
  - `V113BuffItemHandleResult` 新增 `bool LeveledUp = false`（預設值保持所有既有呼叫端/
    測試不受影響，沿用 `record` 加欄位不動既有建構式的慣例，跟 P047
    `MobStats.Fly`/P057 同款手法）。
  - `HandleGachExp`：兌換完經驗值後檢查 `mutation.Updates` 是否含 `PlayerStatKind.Level`，
    寫進回傳結果的 `LeveledUp`。
- **`Maple.Adapters.V113`**（`V113ChannelConnectionHandler.cs`）：`HandleBuffItemResultAsync`
  （目前所有 `V113BuffItemHandleResult` 呼叫端共用的統一收尾方法）在既有的
  `CharacterMutated` 分支之後，新增 `LeveledUp` 分支呼叫
  `_guildOperationHandler.SyncMemberLevelJobAsync`——跟 P059 打怪路徑呼叫的是同一個方法，
  行為完全一致（全公會廣播含自己 + 同盟轉發）。

## ✅ 結果與結論

- P059 明確記錄的「刻意不覆蓋」四項裡，第一項（道具經驗值升級路徑）在這次補齊；`LeveledUp`
  旗標的加法設計（沿用 `CharacterMutated` 既有模式）代表未來若 `V113BuffItemHandler` 新增
