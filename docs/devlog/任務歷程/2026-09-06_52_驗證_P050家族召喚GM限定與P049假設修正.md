## 🎯 目標

P049 收尾寫下「家族召喚的 `DestinationPosition` 精確落點...留給後續獨立處理」，暗示
家族召喚也該用 `findClosestSpawnpoint`。這次動手查證前先核對 Java 家族召喚的實際實作，
確認這個假設是否成立，再決定要不要真的接線。

## 📋 查證過程與結論

### 修正 P049 的假設：家族召喚不用 `findClosestSpawnpoint`

- 全域 grep `findClosestSpawnpoint` 在 Java 原始碼樹的所有呼叫點：`InventoryHandler`
  傳送石（P049 已接線）、`GMCommand`／`PracticerCommand`（GM 專用指令，MapleForge 無 GM
  系統不適用）——**沒有任何家族相關呼叫點**。
- 直接讀 `FamilyHandler.java:217` 的 `FamilySummon` 方法：實際warp呼叫是
  `c.getPlayer().changeMap(tt.getMap(), tt.getMap().getPortal(0))`——固定用編號 0 傳送門，
  不是最近重生點。**P049 的假設是錯的**：MapleForge 現有的
  `WarpAsync(..., famWarp.DestinationMapId, ...)`（用預設 `spawnPortalId=0`）其實已經
  對照正確，`FamilyWarpTarget.DestinationPosition` 沒被用上不是缺口，是這個欄位本身
  目前用不到（可能是原作者預留、或未來要支援別種落點時的伏筆）。

### 意外發現：Java 家族召喚整段功能是 GM 限定，MapleForge 沒有這個限制

- `FamilyHandler.FamilySummon` 方法最開頭：
  ```java
  if (!c.getPlayer().isGM()) {
      c.getPlayer().dropMessage("目前本功能不開放使用");
      c.sendPacket(MaplePacketCreator.enableActions());
      return;
  }
  ```
  這代表在這個 Java v113 版本裡，家族召喚對**一般玩家整段停用**，只有 GM 能用。
- MapleForge 的 `FamilyService.HandleFamilySummonAsync`（`cm` 之外、由
  `V113ChannelConnectionHandler` 直接處理 `FamilySummon` opcode 的既有邏輯）完整實作了
  聲望消耗、buff 使用次數、召喚請求/接受流程，**沒有任何 GM 限制**——查證全部
  `docs/devlog/任務歷程` 找不到這個決定的說明紀錄。
- 這不是明確的「bug」（MapleForge 沒有 GM 系統，若忠實複刻 Java 的 GM 限定會讓這個
  已經做好的功能對所有玩家永久無法使用，等同做了又鎖死），但也不是查有實據的「刻意決策」
  ——是一個需要使用者判斷的產品決策：要不要對照 Java 真實行為鎖住（等同下架這個功能）、
  或維持現狀（對一般玩家開放，屬於「合理化 Java 限制」的既有先例，類似其他無 GM 系統
  情境的處理方式）。這次刻意不單方面決定，只記錄查證結果。

## ✅ 結果與結論

- 沒有程式碼異動。P049 提到的「後續獨立處理」不需要再排——查證後發現本來就不需要修，
  是我自己上一輪的假設有誤，這次核對 Java 才發現。
- 新發現一個需要使用者拍板的產品行為問題：家族召喚在 Java 是 GM 限定功能，MapleForge
  目前對所有玩家開放，沒有紀錄說明這是刻意decision。留給使用者決定方向，比照
  `FamilyService` 並行改造（P038/P044）跟大陸限制／已註冊清單等查證原則一致：查到就記錄，
  不倉促片面決定產品行為。
