## 🎯 目標

延續 P045 修好的零呼叫者掃描方法論，把剩餘候選（`CreateGuildAlliance`/`MarriageRingLook`/
`SpawnSummon`/`RemoveNpc`）逐一查到 Java 行為 + MapleForge 現狀，判斷是否為 P045 那種
「單一 cm API 橋接」等級的小範圍缺口，或需要前置設計。

## 📋 查證過程與結論

### `V113AlliancePackets.CreateGuildAlliance`（同盟建立廣播封包）

- 查 Java `World.Alliance.createAlliance` 才知道同盟「建立」本身是透過 NPC 腳本
  `cm.createAlliance(name)`（`NPCConversationManager.createAlliance`，腳本
  `scripts/npc/2010009.js`），不是直接封包操作——跟 P021-P023/P045 同一類 `cm` 橋接。
- 但深入後發現規模遠超單一方法：腳本流程依賴 `cm.getPartyMembers()`/`cm.isLeader()`/
  `cm.partyMembersInMap()`（隊伍成員內省，`INpcScriptContext` 完全沒有這類 API）、
  `cm.addCapacityToAlliance()`/`cm.disbandAlliance()`（`AllianceService` 目前根本沒有
  對應方法，`RemoveGuildAsync` 移除會長公會會連帶解散只是副作用，不是獨立入口）。
- **架構级阻塞**：Java 腳本用 `if (!cm.createAlliance(name))` **同步**分支對話流程，
  但 `AllianceService.CreateAllianceAsync` 是 async（要打 repository）。MapleForge 的
  `NpcContext` 刻意設計成「送對話類只記 pending、不在腳本同步呼叫中碰 async」（避免
  sync-over-async 死鎖），`createAlliance` 這種「馬上要用到非同步結果做同步分支」的
  API 跟這個既有設計原則直接衝突，需要先決定橋接模式（例如：改良版兩階段對話——
  先問完 yes/no 再在 resume 前非同步跑完，或允許 pending-then-resume 模式）。

### `V113RingPackets.MarriageRingLook`（角色外觀戒指顯示）

- 對照 Java `MaplePacketCreator.addMarriageRingLook`：內嵌在 SPAWN_PLAYER 封包裡（`spawnPlayerMapobject`），跟 rings 清單、聊天板等一起送。
- MapleForge 的 `V113MapPackets.SpawnPlayer` **已經保留對應位元組位置**（`// marriage ring look` 註解 + 硬編碼 `WriteByte(0)`），是典型的「架構就位、資料沒接」缺口——但接線需要
  在 spawn-broadcast 迴圈裡讀到「對方角色」的 `MarriagePartnerCharacterId`/`MarriageRingId`
  （這兩個欄位定義在 `Player.Ring.cs`，是 `Player` 專屬的執行期欄位，不在 `Character` 上）。
- **架構级阻塞**：`IMapSessionRegistry.GetOthers` 回傳的 `MapPlayerEntry` 只帶
  `Character`，不帶 `Player`（`Register` 呼叫點也只傳 `chr`，見
  `V113ChannelConnectionHandler.cs:469`）。要接線必須先決定：戒指狀態搬到 `Character`
  持久化（讓 registry 天然帶得到），或是把 `MapPlayerEntry`/`Register` 契約整個改成帶
  `Player`（目前有 FollowHandler/PartySearchHandler/RingHandler/SummonHandler/
  ChannelConnectionHandler 共 5+ 處呼叫點，屬於全域契約異動）。

### `V113SummonPackets.SpawnSummon`（召喚獸生成廣播）

- `V113SummonHandler.cs` 只有 Move/Attack/Damage/Remove 四種既有召喚獸操作的處理，
  全域搜尋找不到任何 `new Summon` 或 `SummonService`——**技能施放「產生」召喚獸這件事
  本身完全沒有實作**，現有的 Move/Attack/Damage/Remove 是為了一個尚未存在的「施放
  召喚獸技能」子系統預先蓋好的骨架。這不是「漏一個廣播」，是「整個技能觸發鏈缺失」，
  規模等同 P004 記錄的 MTS/Monster Carnival 這類多日級功能，不適合塞進單一 P-phase。

### `V113MapPackets.RemoveNpc`（NPC 移除廣播）

- 對照 Java 兩個呼叫來源：① `MapleNPC` 單一玩家離開視野時的個人清理、②
  `MapleMap.java:1443/1460` 一段跟地圖狀態相關的動態移除（範圍待查，疑似跟特定
  NPC 條件顯示/隱藏有關）。MapleForge 現行 NPC 都是進場時一次性靜態展開
  （`SpawnMapNpcsAsync`），沒有任何「NPC 於運行期消失」的觸發條件或子系統，接線
  `RemoveNpc` 前需要先確認 MapleForge 是否要支援這類動態 NPC 可視性，屬於前置範圍
  評估，非單一方法接線。

## ✅ 結果與結論

- 四個候選逐一查證，結論一致：**都需要先做一個獨立的前置設計/決策，不是「橋接已就位
  的服務方法」這種可以直接動手的形狀**——跟 P045（`sendRepairWindow`：服務、資料、
  cm 橋接模式全部就緒，純粹補一條線）明顯不同量級。
- 沒有程式碼異動，但把「為什麼不能像 P045 一樣直接做」的具體阻斷點記錄下來（同盟
  建立的 sync-over-async 衝突、戒指外觀的 registry 契約缺口、召喚獸缺整條技能鏈、
  NPC 移除缺動態可視性子系統），供後續評估優先順序時參考。
- 零呼叫者封包候選清單至此除了已知需前置設計的 Door 傳送門（`SPECIAL_MOVE(0x55)`）外，
  再新增這四項，皆需要使用者決定方向後才適合排入獨立 P-phase。
