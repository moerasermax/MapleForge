## 🎯 目標（執行前先寫死，過程不偷改）

P011→P020 連續十個 P 階段的最後一個。收斂 P016/P019 系列查出的最後一個家族登入封包缺口：
`V113FamilyPackets.FamilyInfo`（個人家族資訊：花費/親等數/首領/公告/已用 buff 次數）。完成判準：
登入時無條件送給玩家自己（不限是否已加入家族，對照 Java）；有家族與無家族兩種情況封包內容都正確；
單元測試覆蓋兩種情況。

## 📋 背景與假設

- Java 來源：`InterServerHandler.java:265-269`（登入流程，緊接公會/勳章段之後）：
  ```java
  //家庭
  if (player.getFamilyId() > 0) {
      World.Family.setFamilyMemberOnline(player.getMFC(), true, c.getChannel());
  }
  c.sendPacket(FamilyPacket.getFamilyInfo(player));
  ```
  `c.sendPacket(FamilyPacket.getFamilyInfo(player))` 在 `if (getFamilyId() > 0)` 區塊**之外**，
  與 P019 處理的 `getFamilyData()`（特權清單）同一種「無條件送給所有玩家」模式。
  `FamilyPacket.getFamilyInfo(chr)`（`tools/packet/FamilyPacket.java:61`）對沒有家族的玩家
  （`family == null`）走 `else { mplew.writeLong(0); }` 分支——代表函式本身就是為「不限家族身分」
  設計的，NOT 一個只有家族成員才會呼叫的函式。
- **第二次修正 P016 的誤判**：P016 任務歷程原文「登入時 `FamilyPacket.getFamilyInfo` 自身資訊封包
  是否要補送...本次判斷為低優先級，非行為缺陷」——這次重讀 Java 原始碼逐行確認，`getFamilyInfo`
  呼叫確實在 if 區塊外、無條件執行，P016 的判斷是錯的（可能是被同一行裡「個人」兩個字誤導，
  聯想成「只有本人查詢時才需要」）。MapleForge `FamilyService.GetFamilyInfo(characterId)` 早就
  正確實作了「沒有家族回傳預設值」分支（P016 當時應該有機會發現，但沒有深究）。
- 修法：`V113FamilyHandler.NotifyLoginAsync`（P015/P016 已建立）在既有的線上狀態同步/廣播之前，
  加一步：透過 `_sessions.SendPacketAsync(player.Character.Id, ...)` 直接把 `FamilyInfo` 封包送給
  「自己」——沿用同一個 session hook 介面，不需要新增 `sendSelf` 委派參數（玩家在呼叫這個方法前
  已經在 `_onlinePlayers` 完成註冊，`SendPacketAsync` 用 characterId 查得到自己的 session）。
- 範圍邊界：只補這一個封包。P019 的 `FamilyPrivilegeList` 已在同一個登入流程掛好；至此 Java
  `InterServerHandler` 家族段落（`getFamilyInfo`+`setFamilyMemberOnline`+`getFamilyData`）三行
  全部收斂完畢。

## ✅ 結果與結論

- P020 是本輪第二次「回頭複查抓到自己稍早誤判」的案例（P019 是第一次），且是同一個誤判的延伸
  （P016 那一句話同時誤判了兩個封包：`getFamilyData()` 在 P019 修正、`getFamilyInfo()` 在 P020
  修正）。這強化了同一個教訓：對 Java 原始碼的「一句話摘要」式判斷（P016 當下沒有貼出完整程式碼、
  只憑記憶下判斷）風險很高，之後任何「這個是不是缺陷」的判斷都應該先貼出實際程式碼再下結論，
  不能只憑印象。
- 本輪十個 P-phase（P011-P020）沉澱出三個可重複使用的排查手法，值得寫進未來的方法論：
  1. **對稱性掃描**：找「哪些子系統的『進入/開始』動作有處理，但『離開/結束』動作沒有對應處理」
     （P013 Messenger、P014 HiredMerchant 訪客斷線清理）。
  2. **登入/登出流程逐行核對**：把 Java 登入或斷線流程完整讀一輪，對照 MapleForge 是否每一行
     都有對應實作（P015/P016 Family online、P017 Alliance cascade、P018 Quest mob kills、
     P019/P020 Family 静態/個人資訊封包）。
  3. **零呼叫者封包掃描**：全域 grep 找出「已經寫好但沒人呼叫」的封包建構式，逐一用 Java 原始碼
     核對是否為真缺口或 Java 自身死碼（本輪篩出約 24 個候選，處理 3 個真缺口，確認 5 個死碼，
     其餘因涉及更大範圍的未完成功能而擱置）。
