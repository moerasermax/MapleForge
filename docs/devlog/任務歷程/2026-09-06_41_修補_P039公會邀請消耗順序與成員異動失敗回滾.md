## 🎯 目標（執行前先寫死，過程不偷改）

P037 記下一個獨立小缺口：`AcceptInviteAsync` 的 `ConsumeInviteAsync`（消耗邀請）發生在
`AddMemberAsync`（加入公會）之前且不可逆，若後者失敗，邀請已作廢但玩家沒真的入會。完成判準：
調整順序讓邀請只在真正加入成功後才消耗。**過程中撰寫「失敗後可以重試」的驗證測試時，意外證明
P036/P037 當時判定「較輕微、留給後續」的 `guild` 物件欄位異動風險，其實會直接擋死重試**（不是
單純「暫時跟 DB 不同步」），因此這次一併把 `AddMemberAsync`/`LeaveGuildAsync`/`ExpelMemberAsync`
三個方法的物件欄位異動補上失敗回滾。

## 📋 背景與查證

- **邀請消耗順序**：`AcceptInviteAsync` 原本 `ConsumeInviteAsync` 在前、`AddMemberAsync` 在後。
  新增 `IGuildRegistry.HasPendingInviteAsync`（只檢查存在且未過期，不消耗），把流程改成
  「確認邀請存在→嘗試加入→加入成功才真的消耗」。
- **物件欄位異動的回滾必要性（意外發現）**：撰寫「`AddMemberAsync` 因 DB 失敗，之後重試應該
  成功」的測試時，測試失敗——追查發現 `guild.TryAddMember(member)` 在 `UpdateAsync` 之前就已經
  把成員加進 `guild.Members`（P036/P037 當時判斷這只是「暫時跟 DB 不同步、下次成功會自我修正」
  而不處理），但 `UpdateAsync` 失敗後這個物件欄位異動**沒有自動復原**，導致重試時
  `guild.TryAddMember` 判斷「已經是成員」直接失敗（回 `InvalidOperation`）——角色被**永久卡在
  半成員狀態**，既不在 DB 裡、也無法重新嘗試加入。這比 P036/P037 原本估計的「較輕微」風險嚴重，
  值得回頭補上。
- 同樣的道理也適用於 `LeaveGuildAsync`（`TryRemoveMember` 成功後若 `UpdateAsync` 失敗，成員已經
  從 `guild.Members` 消失，重試會被判斷「早就不是成員」回 `TargetNotFound`）與 `ExpelMemberAsync`
  （同理）。

## 🔧 實作內容

- **`Maple.Application`**（`src/Maple.Application/Guilds/GuildService.cs`）：
  - `IGuildRegistry`/`InMemoryGuildRegistry` 新增 `HasPendingInviteAsync(guildId, characterName, ct)`：
    邏輯跟 `ConsumeInviteAsync` 幾乎一樣（含 `PruneInvitesLocked`），差別是不移除。
  - `GuildService.AcceptInviteAsync`（player 層 wrapper）：改成先 `HasPendingInviteAsync` 確認，
    `AddMemberAsync` 成功後才呼叫 `ConsumeInviteAsync`。
  - `InMemoryGuildRegistry.AddMemberAsync`/`LeaveGuildAsync`/`ExpelMemberAsync`：`UpdateAsync`
    包一層 `try/catch`，失敗時分別呼叫 `guild.TryRemoveMember`/`guild.TryAddMember`（用先前
    clone 的成員快照）+ 對應方向的 `GainGuildPoints` 復原，再 `throw` 往外拋，讓呼叫端仍然看到
    例外（行為對外不變，只是記憶體狀態恢復到操作前）。

## ✅ 結果與結論

- 這次是本輪「先查證、記下但不動手」的紀律第一次被自己的後續測試推翻——P036/P037 判斷物件
  欄位異動風險「較輕微、留給後續評估」是基於「下次成功寫入會自我修正」的假設，但這個假設沒有
  考慮到「使用者會立刻重試同一個操作」這個真實場景，重試時反而被半成功的中間態擋下。這提醒
  往後遇到「較輕微、可自我修正」這類判斷時，最好順手寫一個「失敗後立即重試」的測試驗證假設，
  而不是純粹用讀程式碼的方式推論嚴重程度。
- 回滾邏輯選擇 `try/catch` 而非重新設計資料流（跟 P036/P037 的「純調換順序」不同），是因為
  這裡的物件欄位異動**必須**先於持久化發生（要存的內容就是這些欄位），沒有「調換順序」這個
  選項，只能在失敗時明確復原——三個方法各自用「操作前已 clone 的成員物件」逆向操作
  （加回去/移除掉 + 反向調整 GP），维持跟原操作對稱、容易驗證正確性。
