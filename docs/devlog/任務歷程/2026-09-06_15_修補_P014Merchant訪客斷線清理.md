## 🎯 目標（執行前先寫死，過程不偷改）

延續 P013 發現的「主動操作 vs. 斷線隱含觸發」對稱性缺口類型，這次收斂 HiredMerchant（精靈商人）：
玩家斷線時若正瀏覽某個精靈商人（`player.ActiveShopId` 有值），要被移出訪客名單且其餘仍在場的
參與者收到 `ShopVisitorLeave` 通知；若玩家本身是 owner（在 Visitors 清單中查無 slot），維持 no-op
（不關店，對照 Java 邏輯 owner 分支）；未瀏覽任何商店的玩家斷線不觸發任何動作。單元測試覆蓋三種
情況。

## 📋 背景與假設

- Java 來源：`MapleClient.removalTask`（`disconnect()` 一開始就呼叫的清理方法）：
  ```java
  synchronized (this) {
      final IMaplePlayerShop shop = player.getPlayerShop();
      if (shop != null) {
          shop.removeVisitor(player);
          if (shop.isOwner(player)) {
              if (shop.getShopType() == 1 && shop.isAvailable() && !shutdown) {
                  shop.setOpen(true);
              } else {
                  shop.closeShop(true, !shutdown);
              }
          }
      }
  }
  ```
  `IMaplePlayerShop.HIRED_MERCHANT = 1`，故 owner 分支對 HiredMerchant 是「若可用就保持開放」，
  不是關店——這與 MapleForge 現行「owner 離線後過期才轉 claimable」的背景服務設計（`ExpireOpenMerchantsAsync`）
  精神一致，本次**不動**這塊差異，僅補上 `shop.removeVisitor(player)` 這行對所有斷線玩家無條件執行
  的訪客清除。
- MapleForge 現況：`V113PlayerInteractionRouter.HandleMerchantExitAsync`（僅由玩家主動送出
  `PLAYER_INTERACTION` Exit(0x0A) 子指令觸發）已經有完整的「離開 + 廣播 ShopVisitorLeave + session
  deregister」邏輯，但 `V113ChannelConnectionHandler.cs` 的斷線清理區塊（與 P013 Messenger 同一個
  best-effort 區塊）沒有任何呼叫——grep `LeaveMerchantAsync` 全專案只有 `HandleMerchantExitAsync`
  一處呼叫者，確認缺口為真。
- 修法：比照 P013 的做法，把 `HandleMerchantExitAsync` 的核心邏輯抽出（略去只跟「還有連線」相關的
  `SendEnableActionsAsync` 回應自己），新增公開方法 `NotifyDisconnectAsync(Player, CancellationToken)`，
  在 `V113ChannelConnectionHandler.cs` 登出通知區塊掛上呼叫。
- 範圍邊界：只收斂「訪客斷線沒被清出」這一格。owner 端「shop 是否該因斷線關閉/保持開放」的完整語意
  與 MapleForge 既有背景到期機制的關係，屬於更大的既有架構決策，明確不在本次範圍內。

- 「主動操作 vs. 斷線隱含觸發」對稱性缺口第三次出現後收斂（P004/P006 隊伍、P013 Messenger、
  P014 HiredMerchant），驗證了這類系統性掃描（找「哪些子系統的『離開』只掛在主動 opcode 上，
  沒掛在斷線路徑上」）值得作為後續排查其他 in-game 子系統的固定檢查手法。
- 過程中差點誤判 Java owner 分支語意（一開始以為斷線會關店），細讀 `IMaplePlayerShop` 常數定義
  後才確認實際是「保持開放」——再次印證「命名和行為不一致是舊碼常態，呼叫鏈要往下追到底層實作」
  的鐵律價值：光看 `if (shop.getShopType() == 1 ...)` 這種魔術數字，不查常數定義就會做出錯誤修法。
