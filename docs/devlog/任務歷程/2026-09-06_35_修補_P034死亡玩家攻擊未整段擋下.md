## 🎯 目標（執行前先寫死，過程不偷改）

延續 P033 對 `registerOffense` 呼叫點的排查，檢查 Java 三個攻擊路徑
（`closeRangeAttack`/`rangedAttack`/`MagicDamage`）共用的 `ATTACKING_WHILE_DEAD` 守門結構。
發現 MapleForge 只有 `HandleMagicAttackAsync` 有對應的 `IsAlive` 早退，`HandleCloseRangeAttackAsync`
完全沒有、`HandleRangedAttackAsync` 只靠域層服務內部保護——不是「反作弊記錄」缺口（P033 那種），
是**真的行為缺口**：死亡玩家的近戰攻擊動作仍會廣播給同圖其他玩家看見。完成判準：三個攻擊路徑
在解析封包前一致擋下死亡玩家的攻擊，並記錄警訊（比照 P033 的記錄風格）。

## 📋 背景與假設

- Java `PlayerHandler.closeRangeAttack`/`rangedAttack`/`MagicDamage` 三者結構逐字一致：
  ```java
  if (!chr.isAlive() || chr.getMap() == null) {
      chr.getCheatTracker().registerOffense(CheatingOffense.ATTACKING_WHILE_DEAD);
      return;
  }
  ```
  **在解析攻擊封包之前**就整段擋下，不只是不造成傷害，連攻擊動作封包都不會被建構、更不會廣播
  給其他玩家。
- MapleForge 現況查證：
  - `HandleCloseRangeAttackAsync`：**完全沒有** `IsAlive` 檢查——先呼叫
    `V113CombatPackets.CloseRangeAttackBroadcast` 廣播給同圖其他玩家，然後才呼叫
    `_combatService.ApplyAttack`（該方法內部有 `if (!attacker.IsAlive) return empty;` 保護，
    傷害本身不會發生）。實際影響：**死亡玩家的攻擊動畫仍會被其他玩家看見**，只是不會造成傷害
    ——視覺一致性缺口，非安全性漏洞，但確實跟 Java 行為不符。
  - `HandleRangedAttackAsync`：沒有 adapter 層早退，但域層 `RangedMagicCombatService.
    ApplyRangedAttack` 已有 `if (!attacker.IsAlive) return AttackerDead 狀態;`，`result.Applied`
    為 false 時 adapter 提前 `return`（廣播動作也在 `Applied` 判斷之後），**功能上已經安全**，
    只是判斷順序跟另外兩路徑不一致、也沒有比照 Java 記錄違規。
  - `HandleMagicAttackAsync`：**已經有** `if (!player.IsAlive) return;`，行為正確，只是沒有
    比照 Java 記錄警訊。
- 沿用 P033 剛建立的風格：只記錄（`_log.LogWarning`），不新建違規追蹤系統。

## 🔧 實作內容

    移到檢查之後，死亡玩家不再產生任何可見的攻擊動作）。

## ✅ 結果與結論

- 延續 P033 的排查思路（逐一查證 Java 的 `registerOffense` 呼叫點），這次找到的不是單純「記錄
  缺口」，而是**真正的行為不一致**——`CloseRangeAttack`/`RangedAttack`/`MagicAttack` 三個理應
  對稱的攻擊路徑，實際上死亡玩家守門的落實程度各不相同（完全沒有/域層才有/adapter 層才有），
  這種「同類三個路徑本該對稱卻實作不一致」的模式，適合用「找到一個路徑做對了，檢查其他相似路徑
  是否也做對了」的排查手法，跟 P013/P014 的對稱性掃描是同一個家族的技巧，只是這次比較的是「同一
  種鐵律在多個並列路徑上的落實程度」而非「進入/離開」的對稱性。
- 域層 `ApplyRangedAttack` 早就有 `AttackerDead` 保護但完全沒有專門測試，這次順手補上
  `CombatServiceTests` 對應的測試，補強既有邏輯的驗證覆蓋（雖然邏輯本身沒改，但這類「早就正確
  但沒測試覆蓋」的域層方法值得順手補測試，往後修改時才有回歸保護）。
