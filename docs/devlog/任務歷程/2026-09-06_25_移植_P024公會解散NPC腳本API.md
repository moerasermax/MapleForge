接上公會 NPC 腳本 `scripts/npc/2010007.js` 最後一個未接線的呼叫 `cm.disbandGuild()`，完成 P022
（`getPlayerStat`）→ P023（`increaseGuildCapacity`）→ P024（`disbandGuild`）三階段接力後，這支腳本
三個分支全部可正常運作。完成判準：會長解散公會後，全體成員（不分上下線）持久化公會欄位歸零、
公會 BBS 討論串全部清除、若在同盟中要從同盟移除、線上成員記憶體狀態同步歸零並收到解散廣播；
非會長或無公會呼叫則靜默不動作。

## 📋 背景與假設

- Java 呼叫鏈：`NPCConversationManager.disbandGuild()` → `gid<=0 || guildRank!=1` 靜默 return（**這
  次的守門檢查在 NPCConversationManager 層，不像 P023 的 increaseGuildCapacity 只在腳本層檢查**）→
  `World.Guild.disbandGuild(gid)` → `MapleGuild.disbandGuild()` = `writeToDB(true)` +
  `broadcast(null, -1, BCOp.DISBAND)`。
- `writeToDB(true)` 的 disband 分支：`UPDATE characters SET guildid=0,guildrank=5,alliancerank=5
  WHERE guildid=?`（bulk SQL，涵蓋所有成員的持久化列）→ `DELETE FROM bbs_threads/bbs_replies
  WHERE guildid=?` → `DELETE FROM guilds WHERE guildid=?` → 若 `allianceid>0` 呼叫
  `alliance.removeGuild(id, false)` → `broadcast(guildDisband(id))`（送封包給在線成員）。
- `broadcast(null, -1, BCOp.DISBAND)`：對每個成員，**在線的話直接呼叫
  `World.Guild.setGuildAndRank(charId, 0, 5, 5)` 同步記憶體中的角色物件**（不只是 DB）；離線的話
  另外呼叫 `saveCharacterGuildInfo` 補一次 DB 寫入（與前面 bulk SQL 重複，屬 Java 的防禦性冗餘）。
  這證明 Java 對 disband 特別處理了「在線成員記憶體狀態」，跟 P023 (`increaseGuildCapacity`)、既有
  `ExpelMemberAsync` 都不處理在線記憶體同步不一樣——這次要忠實對照，不能沿用 Expel 的既有限制。
- MapleForge 現況：`GuildService`/`Guild` 完全沒有任何 disband 相關方法；`V113GuildPackets.GuildDisband`
  封包格式早已存在（`GUILD_OPERATION`+`0x32`+int guildId+byte 1，與 Java `guildDisband` 逐位元組
  一致）但零呼叫者；`IGuildBbsRepository`（`GetThreadsAsync`/`DeleteThreadAsync`）與
  `AllianceService.RemoveGuildAsync(allianceId, guildId, expelled, ct)`（已含同盟移除/整個同盟連鎖
  解散判斷）都已存在且經過測試，只是從未被 Guild 解散流程呼叫過。

## ✅ 結果與結論

- 這次刻意做了「Expel 現有的既有限制不代表 Disband 也該有同樣限制」的判斷——一般直覺會覺得
  「跟既有的 Expel 邏輯保持一致」比較安全，但貼出 Java `broadcast(..., BCOp.DISBAND)` 原始碼後
  發現 Java 明確對 disband 做了在線成員記憶體同步（Expel 沒有），所以沒有照抄 Expel 的簡化模式，
  而是照著 Java 對 disband 的實際處理去做。這再次印證 P020 訂下的鐵律：「判斷是否為缺陷/該怎麼做
  一律要先貼出實際程式碼再下結論」，這次是「不能因為隔壁功能沒做就假設這個功能也不用做」的延伸。
- `GuildService.DisbandGuildAsync` 刻意只做「登記表+持久化」層，把 BBS/同盟/在線記憶體同步/廣播
  留給 Adapter 層協調——這個切法讓 `GuildService` 保持單一職責（只碰 `IGuildRegistry`+
  `ICharacterRepository`），不需要為了 disband 一個功能就讓它額外依賴 `AllianceService`+
  `IGuildBbsRepository`+`IOnlinePlayerRegistry`（那些是 Adapter 層本來就有的依賴），對照
  `V113GuildOperationHandler` 已經是「同時持有多個 Application 服務做協調」的既有模式，延伸使用
  一致，沒有發明新模式。
