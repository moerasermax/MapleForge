## 🎯 目標（執行前先寫死，過程不偷改）

P007 收尾時記下的已知問題：Java `InventoryHandler.UseCashItem` 的 `5071000` 分支用
`MaplePacketCreator.getMegaphone(sb.toString())`（plain Megaphone 封包格式，無 ear/channel 欄位），
但 MapleForge 現行把 `5071000` 與 `5072000` 併在同一個 case，共用 `SuperMegaphone` 格式建包。
完成判準：`5071000` 改用 plain `Megaphone` 封包格式建包（範圍已在 P007 修正為全服廣播，維持不變）；
`5072000` 不受影響，仍用 `SuperMegaphone` 格式；單元測試區分兩者封包格式；既有測試不退。

## 📋 背景與假設

- Java 來源（`InventoryHandler.java` 1561-1600 行）：`5071000` 讀 message + ear byte，但建包只呼叫
  `getMegaphone(sb.toString())`——**ear 變數讀了但沒用**（Java 原始碼本身的死變數，不是移植遺漏，
  照抄行為即可，不需要「修正」Java 這個小瑕疵）。
- `V113BroadcastPackets.Megaphone(string message)` 簽章本來就沒有 ear 參數（`BroadcastMessage(type:2,
  channel:0, [message], ear:false, item:null)`），與 Java `getMegaphone(String)` 對齊。
- `HandleMegaphone` 私有方法的 `buildPacket` 委派簽章是 `Func<string,int,bool,byte[]>`（message,
  channel, ear）；5071000 可以傳一個忽略 channel/ear 的 lambda，直接呼叫 `V113BroadcastPackets.
  Megaphone(message)`，不需要改動 `HandleMegaphone` 本體或 `TryReadMegaphoneMessage`（讀取 ear byte
  仍要做，只是建包時不使用，這正是要忠實重現的 Java 行為）。
