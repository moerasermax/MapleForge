## 🎯 目標（執行前先寫死，過程不偷改）

延續 P029「基礎設施已就緒但沒被使用」的排查方向，檢查 Java 其他 `FieldLimitType.*.check(...)`
呼叫點，找到 `V113ItemUseHandler.HandleUseSummonBag`/`HandleUseReturnScroll` 早就有
`V113ItemUseContext.CanUseSummonBag`/`CanUseReturnScroll` 兩個閘門欄位、內部邏輯也正確判斷，
但 `V113ChannelConnectionHandler` 唯二兩處建構 `V113ItemUseContext` 的地方都只填 `ReturnMapId`，
兩個閘門欄位永遠停在預設值 `true`（=永遠允許），從未依實際地圖的場地限制計算過。完成判準：
兩處呼叫點對照 Java 補上真正的場地限制計算。

## 📋 背景與假設

- Java `InventoryHandler.java:898`（召喚袋）：`if (c.getPlayer().isGM() ||
  !FieldLimitType.SummoningBag.check(chr.getMap().getFieldLimit())) { ...spawn... }`——GM 略過
  限制，或地圖沒設 `SummoningBag` 旗標才會真的召喚怪物；**道具本身在這個 if 之前就已經被消耗**
  （`MapleInventoryManipulator.removeFromSlot` 在檢查之前），代表場地限制只擋「召喚」這個動作，
  不擋「消耗道具」——即使被擋，道具照樣浪費掉。
- Java `InventoryHandler.java:310`（回城卷軸）：`if (!FieldLimitType.PotionUse.check(...)) {
  ...apply+consume... } else { enableActions }`——**跟一般補藥共用同一個 `PotionUse` 旗標**（不是
  獨立的旗標），且整個「套用效果+消耗道具」都包在檢查裡面，被擋時道具完全不消耗（跟召喚袋的
  「先扣後查」行為不同，各自照抄，不強行統一）。
- MapleForge `V113ItemUseHandler.HandleUseSummonBag`（`context.IsGm || context.CanUseSummonBag`）
  與 `HandleUseReturnScroll`（`!context.CanUseReturnScroll` 提前 return）的判斷邏輯與消耗道具的
  先後順序都已經跟 Java 完全對齊（早期批次移植就做對了），純粹是 `V113ChannelConnectionHandler`
  唯二兩處建構 `V113ItemUseContext` 時漏填這兩個欄位，導致邏輯形同虛設。
- 沿用 P029 剛補上的 `MapService`/`MapData.FieldLimit`/`FieldLimitType.Check`。

## 🔧 實作內容

- **`Maple.Adapters.V113`**（`V113ChannelConnectionHandler.cs`，兩處 `V113ItemUseContext` 建構）：
  - `UseSummonBag` case：`CanUseSummonBag = !FieldLimitType.SummoningBag.Check(_mapService.LoadMap(player.Character.MapId).FieldLimit)`。
  - `UseReturnScroll` case：`CanUseReturnScroll = !FieldLimitType.PotionUse.Check(_mapService.LoadMap(player.Character.MapId).FieldLimit)`
    （刻意用 `PotionUse` 而非誤植獨立旗標，對照 Java 確認回城卷軸跟補藥共用同一個旗標）。
  - `IsGm` 維持不填（預設 `false`）：MapleForge 尚無 GM 系統（P022 已確認），無人具 GM 身分是
    精確反映現狀，非造假半套。

## ⏯️ 接手點

同一輪 Java 全域搜尋 `FieldLimitType.*` 找到的其他呼叫點（`InventoryHandler`/`PetHandler` 的
`PotionUse`——一般補藥與寵物自動補藥；`FamilyHandler` 的 `VipRock`——家族傳送/家族 buff；
`PlayerInteractionHandler` 的 `Minigames`；`InterServerHandler` 的 `ChannelSwitch`；
`MapleMap` 的 `Mount`）都各自綁在更大的功能（家族 buff 系統、換頻道流程、一般補藥消耗流程）上，
這次刻意不展開，因為它們涉及的呼叫路徑跟這次的召喚袋/回城卷軸不同檔案、不同前置條件，需要
個別查證，留給後續 P-phase。

## ✅ 結果與結論

- 本輪第六次證明「基礎設施已就緒但沒被使用」是高效的排查方向，而且這次的發現比 P029 更徹底：
  不只資料來源沒接（`MapData.FieldLimit`，P029 已解決），連**判斷邏輯本身都已經寫好**
  （`V113ItemUseContext.CanUseSummonBag`/`CanUseReturnScroll` + handler 內的判斷式），純粹是
  呼叫端沒把值餵進去——這種「地基、牆都蓋好了，只是水管沒接」的缺口比從零開始寫邏輯風險低很多，
  因為邏輯正確性已經由原本移植這段程式碼的人驗證過，這次只需要確認「餵什麼值」對不對。
- 召喚袋與回城卷軸兩者對「場地限制擋下時道具是否消耗」的行為不同（前者先扣後查、後者整段包住不
  消耗），刻意沒有為了程式碼一致性去統一這兩種行為——忠實對照各自的 Java 來源，而非讓兩個功能
  看起來更「合理一致」。
