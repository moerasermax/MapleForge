## 🎯 目標（執行前先寫死，過程不偷改）

P009 查明的架構缺口：`AllianceService` 異動同盟成員關係（建立/加入/退出/解散）時，從未把結果同步
寫回 `IGuildRegistry` 的 `GuildState.AllianceId`，導致這個欄位形同虛設、永遠是 0（或建立時的初始
值），任何直接讀它判斷同盟關係的程式碼都會得到錯誤結果。完成判準：`AllianceService` 在建立同盟、
公會加入同盟、公會退出同盟、同盟解散這四個時機點，都會把對應公會的 `AllianceId` 正確寫回
`IGuildRegistry`；`ChatService`/`V113AllianceHandler` 既有的「先看 guild.AllianceId 當快取，沒有
再問 AllianceService」雙重解析邏輯自然受益（快取分支不再是必然落空的死路）；單元測試覆蓋四個時機
點；既有測試不退。

## 📋 背景與假設

- `Guild.AllianceId` 是普通 public settable int 屬性，無不變量保護，直接指派即可。
- `AllianceService` 目前有一個「公會加入同盟」的共用私有方法 `AddGuildLockedAsync`（`CreateAllianceAsync`
  走它的姊妹路徑手動 inline、`AcceptInviteAsync`/`AddGuildAsync` 共用它），與一個「公會離開同盟」的
  `RemoveGuildAsync`（含一般移除與解散兩個分支）。這是全部需要掛 hook 的地方。
- `IGuildRegistry` 目前沒有「依 guildId 直接更新單一欄位」的方法，需要新增
  `SetAllianceIdAsync(guildId, allianceId, ct)`；比照既有 `GetGuildAsync` 的 lock 模式實作，回傳
  `bool`（找不到公會就回 false，呼叫端 best-effort 處理，不拋例外——這是內部資料一致性維護，不是
  使用者可見指令，不需要完整的 `GuildCommandResult`/recipients 廣播機制）。
- `AllianceService` 需要新增 `IGuildRegistry` 依賴。檢查過沒有循環依賴風險（`GuildService`/
  `InMemoryGuildRegistry` 不依賴 `AllianceService`）。
- 修完後，`ChatService.GetAllianceRecipientsAsync`/`V113AllianceHandler.ResolveAllianceIdAsync` 的
  雙重解析寫法**不需要改**（先看 guild.AllianceId 的快取分支本來就是安全的防禦性寫法，只是過去
  快取永遠落空、退化成單純呼叫 AllianceService；修完後快取分支才會真的有機會命中，行為更接近
  Java 原始設計意圖，但呼叫端程式碼不用動）。
