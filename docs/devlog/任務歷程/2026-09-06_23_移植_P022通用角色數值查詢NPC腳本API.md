## 🎯 目標（執行前先寫死，過程不偷改）

延續 P021 之後對零呼叫者候選的全面重掃，鎖定公會 NPC 腳本 `scripts/npc/2010007.js`（公會建立/
解散/擴充人數 NPC）——該腳本大量使用 `cm.getPlayerStat("GID")`/`cm.getPlayerStat("GRANK")` 做
守門判斷（是否已有公會、是否為會長），但 MapleForge 的 `cm` 物件完全沒有這個方法。完成判準：
`cm.getPlayerStat(type)` 對照 Java `AbstractPlayerInteraction.getPlayerStat` 逐 key 實作完整映射，
單元測試覆蓋所有支援的 key（含 GM/ADMIN 的「無 GM 系統故固定回 0」與未知 key 回 -1）。

## 📋 背景與假設

- Java 來源：`AbstractPlayerInteraction.java:279-317`。這不是 `NPCConversationManager` 自己的方法，
  是共用基底類別方法，代表**很多** NPC 腳本都可能用到（不只公會腳本），先把它做完整可以一次性
  解掉一批潛在候選，而非每次遇到才臨時加一個 key。
- 完整支援的 19 個 key：`LVL`/`STR`/`DEX`/`INT`/`LUK`/`HP`/`MP`/`MAXHP`/`MAXMP`/`RAP`/`RSP`/`GID`/
  `GRANK`/`ARANK`/`GM`/`ADMIN`/`GENDER`/`FACE`/`HAIR`，未知 key 回 `-1`（Java 預設分支同）。
- `GM`/`ADMIN` 兩個 key 對照 Java 是 `isGM()`/`hasGmLevel(5)` 布林轉 int——**MapleForge 目前完全
  沒有 GM 系統**（`Character` 無任何 GM 相關欄位）。這不是「先做半套」，而是正確反映現狀：沒有
  GM 概念存在，所有玩家的 GM 身分定義上就是「否」，回 `0` 是精確值而非造假，故直接寫死 `0`，
  不新增虛的 GM 欄位（避免無中生有一個沒人使用的功能）。
- MapleForge `Character`/`CharacterStats` 已有全部需要的欄位（`Level`/`Stats.Str/Dex/Int/Luk/
  Hp/Mp/MaxHp/MaxMp`/`RemainingAp`/`RemainingSp`/`GuildId`/`GuildRank`/`AllianceRank`/`Gender`/
  `Face`/`Hair`），純讀取映射，不需要新增任何領域狀態。

## ⏯️ 接手點

`getPlayerStat`/`getBuddyCapacity` 等 cm 基礎讀取 API 就緒後，公會 NPC 腳本 `2010007.js` 的守門
邏輯可以正確判斷，但腳本實際呼叫的 `cm.increaseGuildCapacity()`（公會擴充人數）與
`cm.disbandGuild()`（解散公會）仍未接線——這兩個排入 P023、P024，`increaseGuildCapacity` 對照
P021 buddy capacity 的既有模式（Core 已有 `Guild.TryIncreaseCapacity` 域方法但零呼叫者），
`disbandGuild` 範圍較大（公會刪除 + 成員 guildId/rank 重置 + 同盟移除 + 廣播），需要獨立驗證。

## ✅ 結果與結論

- 這次選擇「先做完整的共用基底方法」而非「只做這個腳本用到的兩個 key」，是刻意的取捨：
  `getPlayerStat` 是 Java 端很多腳本共用的基礎設施方法，一次做完整可以避免未來每次遇到新腳本
  用到不同 key 時又要開一個新 P-phase 補洞；而 GM/ADMIN 兩個 key 選擇「精確反映無 GM 系統」而非
  「跳過不做」，因為 Java 原始碼裡這兩個 key 是合法输入，未知 key 才該回 -1，用 -1 表示 GM 狀態
  會誤導呼叫端（例如某腳本判斷 `getPlayerStat("GM") > 0`，用 -1 会被誤判為真）。
