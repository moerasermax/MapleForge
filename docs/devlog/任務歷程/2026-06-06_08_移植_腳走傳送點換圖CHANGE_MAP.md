3. 死亡/GM/intro 等特殊 targetid 分支＝MVP 最小化（死亡→回 ReturnMap portal 0；其餘 enableActions 不崩即可），不在本檔死磕。

## 📋 背景與假設

- 根因（已探查確認）：客戶端走 portal 送 **CHANGE_MAP=0x1E**（Java recv.properties:22 / RecvPacketOpcode.java:32），但 MapleForge `V113ChannelRecvOp` 無此 opcode → handler default 啥都不做 → 客戶端鎖在 portal 等回應。實作 0x1E handler ＝ 解鎖鑰匙。
- Java 權威：`PlayerHandler.ChangeMap`(1205)。封包＝`byte(1死/2正常)` + `int targetid(一般 portal=-1)` + `MapleAsciiString portalName` + `skip(1)` + `short wheel`。正常 portal 分支(line 1322)＝`portal.enterPortal(c)`：有 script 跑 script，否則 warp 到 portal 的 tm(目標圖)+tn(目標 portal)。
- 資料已就位：`MapService.LoadPortals` 已載入 Id/Name(pn)/Type(pt)/X/Y/TargetMapId(tm,預設 999999999)/TargetPortalName(tn)/Script。`MapData.GetSpawnPoint`、`MapPortal` 齊備。
- 落地機制：`V113ChannelPackets.SetField` line 94 `WriteByte(chr.SpawnPoint)` → 客戶端用此 portal id 自行定位。故「落在目標 portal」＝設 `chr.SpawnPoint = 目標 portal.Id` + `chr.MapId = TargetMapId` 後走 `WarpAsync`（NPC taxi 已驗證能換圖）。
- 0x1E recv 未與其他 recv 衝突（send 側 0x1E=GiveBuff 是不同方向）。
