## 🎯 目標（執行前先寫死，過程不偷改）

P007 記下的已知缺口：`USE_TREASUER_CHEST` 抽到稀有道具時，Java 會全服廣播恭喜訊息
（`GameConstants.gachaponRareItem` 判斷稀有度 + `World.Broadcast.broadcastMessage(getGachaponMega(...))`），
MapleForge 目前沒有這段。完成判準：抽到稀有度表內的道具時，全服廣播（沿用 P007 的
`ChannelBroadcastPackets` 全在線玩家廣播機制）恭喜訊息含道具資訊；非稀有道具不觸發；`REWARD_ITEM`
（非寶箱）不受影響（Java 只有寶箱這條路徑會做稀有度廣播）；單元測試覆蓋稀有/非稀有兩種情況。

## 📋 背景與假設

- Java 來源：`InventoryHandler.UseTreasureChest`（963-971 行）→ `GameConstants.gachaponRareItem(itemId)`
  （617-661 行，四級稀有度表，本次完整搬移）→ `MaplePacketCreator.getGachaponMega(message, item,
  channel)` → `broadcastMessage` type=13（`tools/MaplePacketCreator.java` 420-482 行）：封包版型是
  `[opcode][type=13][message][int channel-1][item info（無 null 判斷，一定寫）]`——與既有 type=8
  （ItemMegaphone）不同：channel 是 4-byte int 不是 1-byte、沒有 ear 欄位、item 一定寫不判斷 null。
- 訊息格式含開頭 tab 字元：`"\t恭喜 " + 玩家名 + " : 從" + box + "抽到！"`，box 是「金寶箱」或
  「銀寶箱」，原樣保留（不是我方格式習慣，是 Java 字面值）。
- 廣播範圍：`World.Broadcast.broadcastMessage` = 全服（沿用 P007 已建好的 `ChannelBroadcastPackets`
  → `BroadcastPacketToAllOnlineAsync` 機制，MapleForge 單實例架構下等於全體在線玩家）。
- `REWARD_ITEM(0x6A)`（非寶箱的另一條路徑）在 Java 沒有稀有度廣播這段，維持不動。
- 稀有度表放在 `RandomRewardsCatalog`（Application 層，與金/銀寶箱權重表同一個檔案，同屬 gacha
  網域知識），設計成 `static` 純函式（不像權重抽獎需要 `Random` instance state）。

## ✅ 結果與結論

- 這是 P007 建好的 `ChannelBroadcastPackets`/`BroadcastPacketToAllOnlineAsync` 全服廣播機制第二次
  被重用（第一次是 P007 自己的喇叭類現金道具），證明那次的基礎設施投資有持續回收。
- 封包版型細節（type=13 用 4-byte int 存 channel、無 ear、item 一定寫不判斷 null）與既有 type=8
  刻意不同，若直接照抄 ItemMegaphone 的寫法會做出錯誤版型——這次先把 Java `broadcastMessage`
  私有方法的完整 switch 讀完再動手，避免了這個陷阱。
