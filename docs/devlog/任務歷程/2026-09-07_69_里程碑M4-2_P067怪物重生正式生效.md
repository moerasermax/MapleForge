## 🎯 目標（執行前先寫死，過程不偷改）

完成 P064（資料模型）→ P065（生怪用例）→ P066（死亡通知）之後，這是怪物重生切片的最後
一步：接上排程器，讓 `RespawnMonsters` 真正開始執行。比照 P066 任務歷程記錄的判斷，直接
延伸 P063 的排程器骨架（而非另開一個 `BackgroundService`），把它從 `DropExpiryHostedService`
泛化重新命名為 `WorldTickHostedService`，同一次 tick 依序處理掉落物過期跟怪物重生——貼近
Java `handleMap` 一個迴圈做多件事的行為。**這是繼掉落物過期（P063）後第二個真正改變伺服器
行為的 P**：地圖打完的怪會重新出現。

## 📋 背景與查證

- 對照 Java `map.spawnMonster(monster, -2)`：`-2` 是 `spawnType` 參數，查證
  `V113CombatPackets.SpawnMonster(mob, sbyte spawnType = -2, ...)` 的預設值本來就是 `-2`——
  MapleForge 現有封包簽章早就對齊這個值（原本只用在初始進場 replay，這次確認同一個封包
  建構式直接適用怪物重生廣播，不需要新增變體）。
- 控制權（AI 控制/移動由哪個玩家端運算）指派刻意不在這個 handler 處理：Java
  `handleAutoAggro` 顯示控制權是玩家端主動請求（送 `AutoAggro` 封包）才指派，不是生怪當下
  就固定指定——MapleForge 既有的 `HandleAutoAggro`（P057 附近已存在）機制原本就是為了處理
  這個「誰先注意到就搶到控制權」的流程，怪物重生只要單純廣播 `SpawnMonster`（無控制者），
  玩家端看到新怪物後自然會走既有流程請求控制權，不需要另外在這裡指派。
- 排程器改名：`DropExpiryHostedService` → `WorldTickHostedService`，因為它現在服務兩個消費者
  （掉落物過期 + 怪物重生），繼續叫「DropExpiry」會誤導。改名影響範圍確認過：這個類別是
  `internal`，且 P063 當時判斷它只是排程膠水沒有寫專屬測試，所以改名不會波及任何既有測試。

- **M4-2 里程碑至此完成第二個具體切片**：伺服器啟動後，地圖上的怪物現在會在被打死後依 WZ
  `mobTime` 設定的間隔真的重新出現，忠實對照 Java 行為（含單點並發上限、地圖級生怪上限）。
