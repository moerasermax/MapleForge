## 🎯 目標（執行前先寫死，過程不偷改）

`MapleServerHost.cs` 同時有 `AddSingleton<IFamilyRegistry, FamilyService>()` 與
`AddSingleton<FamilyService>()` 兩行——這是 DI 容器的經典地雷：兩行各自建立**獨立**的
`FamilyService` 單例（一個透過介面解析、一個透過具體型別解析），若未來有程式碼透過
`IFamilyRegistry` 注入而非 `FamilyService`，會拿到一個狀態完全空、跟其他人用的那份 in-memory
狀態（`_families`/`_familyByCharacter`/`_onlinePlayers`/`_invitesByTarget`/`_pendingSummonsByTarget`
五個 Dictionary）互不相通的「影子實例」。完成判準：兩個型別解析出**同一個**實例；掃過
`MapleServerHost.cs` 全部 `AddSingleton<Interface, Impl>` 配對確認這是唯一一處這種重複註冊。

## 📋 背景與假設

- 起因：找 M6-2「family/note dispatch/DI 待補」筆記的具體內容時，順著 `IV113FamilySessionHook`
  的用法追查，確認 family 各 opcode handler**已經**透過 `_sessions.SendPacketAsync` 正確通知
  其他成員（邀請/加入回應/刪除通知/召喚聲望扣除），dispatch 迴圈只送 `SelfPackets` 是對的，不是
  bug；往上追到 DI 註冊時才發現真正的問題在這裡。
- 用 grep 掃過 `MapleServerHost.cs` 全部 `AddSingleton<Interface, Impl>()` 配對，逐一核對是否有
  對應的獨立 `AddSingleton<Impl>()`，確認全檔案**只有** `FamilyService`/`IFamilyRegistry` 這一組
  犯了這個錯；其餘（`InMemoryPartyRegistry`/`InMemoryGuildRegistry`/`InMemoryOnlinePlayerRegistry`
  等）都只註冊一次，沒有這個問題。
- **現況風險評估**：全專案 grep `IFamilyRegistry` 使用處，目前**沒有任何程式碼**透過這個介面注入
  （只有定義檔與 `FamilyService : IFamilyRegistry` 宣告本身），所以這個 bug 目前是「地雷但沒踩上」
  ——不影響現有功能，但誰下一次寫程式時很自然地選擇注入介面（符合依賴介面而非具體類別的一般
  慣例），就會踩到一個難以排查的「資料明明寫了卻查不到」症狀。
- 修法：把兩行改成 `AddSingleton<FamilyService>()` + `AddSingleton<IFamilyRegistry>(sp =>
  sp.GetRequiredService<FamilyService>())`，確保介面與具體型別解析出同一個實例，這是 .NET DI
  處理「同一個服務要用多個型別暴露」的標準寫法（對照本檔其餘所有 registry 都只註冊一次，因為
  它們沒有這個雙重暴露需求；Family 是唯一有這個需求但寫錯的）。
- 測試決策：本專案目前沒有 DI 組裝測試的既有基礎設施（無測試專案參考 `Maple.Host.Shared`），
  且 `IFamilyRegistry` 目前零消費者，寫一個獨立 `ServiceCollection` 反例測試的投資報酬比偏低
  （測試會複製貼上兩行註冊碼，未來 `MapleServerHost.cs` 改了不會自動跟著更新，維護價值有限）。
  改用 `dotnet build`（編譯期確認型別正確）+ 人工核對 grep 結果作為證據，不為此新增測試基礎設施。

- 修掉一個目前潛伏、尚未被踩到的 DI 組裝地雷：`FamilyService`/`IFamilyRegistry` 過去各自建立
  獨立單例，只是因為 `IFamilyRegistry` 目前零消費者才沒有實際發作。
- **可轉移心法**：這次不是「先看到症狀再回溯根因」，而是反過來——先系統性掃過
  `MapleServerHost.cs` 全部 `AddSingleton<Interface, Impl>()` 配對，核對是否有同一個具體型別被
  重複註冊，主動找出「還沒發作的地雷」而非等 bug 報告。這種批次核對比逐一猜測更有效率，值得作為
  往後排查 DI 組裝問題的標準手法。
- 沒有為此新增測試：`IFamilyRegistry` 零消費者、專案無 DI 組裝測試基礎設施，寫一個孤立的
  `ServiceCollection` 反例測試維護價值有限，改以 `dotnet build`+人工核對 grep 結果作為證據。
