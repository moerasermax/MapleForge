## 🎯 目標（執行前先寫死，過程不偷改）

`ChatService.GetRecipientsAsync` 的 `GroupChatKind.Alliance` 分支目前寫死回傳空陣列，註解是
「reserved until alliance runtime state is ported」——但 Alliance 的 Core/Application/Adapters
（`Maple.Core.Alliances`/`AllianceService`/`V113AllianceHandler`）其實已經在後續批次移植完成，這
段註解已經過期，只是收件人解析從未跟著補上。對照 Java `World.allianceChat`/`MapleGuild.
allianceChat`：對照 sender 所屬公會的同盟，同盟內每個公會的每個成員（排除發送者本人）都要收到。
完成判準：`GroupChatKind.Alliance` 正確解析收件人（同盟內所有公會、所有在線成員、排除自己）；
單元測試覆蓋；既有測試不退。

## 📋 背景與假設

- Java 來源：`ChatHandler.java:206`（`World.Alliance.allianceChat(chr.getGuildId(), ...)`）→
  `World.java:1339-1352`（找 sender 公會的 `allianceId`，走該同盟所有 `guildId`，對每個公會呼叫
  `g_.allianceChat(...)`）→ `MapleGuild.java:487-489`（`broadcast(multiChat(name,msg,3), cid)`，
  `cid` 是排除發送者的 exclude 參數）。
- 封包格式面完全不用動：`GroupChatKind.Guild=2`/`Alliance=3` 已經對齊 Java `multiChat` 的 type
  參數（2=公會聊天，3=同盟聊天），只是 Alliance 的**收件人清單**從未真正解析。
- 既有 `GetGuildRecipientsAsync`/`GetPartyRecipients` 是現成的參考模式（查 registry → 逐成員排除
  自己 → 查在線 → 轉 `ChatRecipient`），Alliance 只是多一層「先找同盟，再走同盟裡每個公會」。
- `IGuildRegistry.GetGuildAsync(guildId)` 與 `IAllianceRepository.FindByIdAsync(allianceId)` 都已
  存在，足以組出這條查詢鏈，不需要新增基礎設施。

  永遠是 0）。**可轉移心法**：遇到「A 欄位理論上該有值」但寫入路徑找不到時，要懷疑這個欄位是否
