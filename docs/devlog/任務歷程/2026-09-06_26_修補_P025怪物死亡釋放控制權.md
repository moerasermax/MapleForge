## 🎯 目標（執行前先寫死，過程不偷改）

P020 收尾列出的四個「需要前置設計」候選之一：`StopControllingMonster`。查證後發現實際範圍遠比
「怪物控制權轉移子系統」小——只需處理「怪物死亡時通知控制者」這一種觸發情境，不需要動到完整
的自動控制者重新分配機制（`updateMonsterController`，那個才是真的需要更大範圍設計）。完成判準：
怪物死亡時，若該怪物有控制者，對控制者（通常是擊殺者本人）送出 `StopControllingMonster` 封包；
三種攻擊路徑（近戰/遠程/魔法）共用的死亡流程統一覆蓋。

## 📋 背景與假設

- Java 全域搜尋 `stopControllingMonster` 三個觸發點：
  1. `MapleMonster` 死亡流程（約 line 494-497）：擊殺獎勵結算後，若怪物有控制者就送
     `stopControllingMonster` 給控制者，Java 註解特別標註「這通常只有隱身 GM 攻擊時才會跟擊殺者
     不同」——代表**一般情況控制者就是擊殺者本人**。
  2. `MapleMonster.switchController`：控制權轉移到新控制者前，先通知舊控制者釋放。
  3. `MapleMap.updateMonsterController`：自動幫怪物找新控制者（當原控制者離開地圖時觸發）。
  - 第 2、3 點都屬於「完整控制者自動重新分配機制」的一部分，對照 M4-2「怪物 AI／移動 tick 尚未
    正式完成（沒有完整 AI/move tick/respawn scheduler）」的既有里程碑筆記，這塊確實需要更大範圍
    設計（誰該接手控制、地圖上還有誰在線、離開地圖/斷線時機），維持不做，留給後續評估。
  - **第 1 點（死亡通知）範圍明確且獨立**：MapleForge 已有完整的怪物死亡流程
    （`CombatService.ApplyAttack`，近戰/遠程/魔法三種攻擊都收斂到同一個
    `SendCombatHitsAsync`），怪物死亡時的控制者資訊在 `field.Remove(mob.ObjectId)` 之前完全可得
    （`Mob.ControllerId` 早已存在），只是死亡流程沒有讀取它、送出對應封包。
- `V113CombatPackets.StopControllingMonster` 封包格式早已存在（`SpawnMonsterControlOp`+byte 0+int
  objectId，與 Java `MobPacket.stopControllingMonster` 逐位元組一致）但零呼叫者，過去也完全沒有
  單元測試覆蓋。

## 🔧 實作內容（依分層）

- **`Maple.Application`**（`src/Maple.Application/Combat/CombatService.cs`）：`CombatMobHit` record
  新增 `ControllerId`（預設 0）欄位；`ApplyAttack` 在建構 hit 時捕捉 `mob.ControllerId`（`field.Remove`
  前，死亡與否都捕捉，非死亡時該值本來就無意義但不影響正確性）。
- **`Maple.Adapters.V113`**（`V113ChannelConnectionHandler.cs`）：`SendCombatHitsAsync` 在
  `KillMonster` 廣播後新增呼叫 `NotifyControllerStoppedAsync`（新私有方法）：`ControllerId==0`
  不送任何包；`ControllerId==擊殺者自己` 走 session 直送；其他情況透過 `IOnlinePlayerRegistry`
  找控制者 session 送，找不到（離線）best-effort 略過。三個攻擊入口（近戰/遠程/魔法）都透過
  `SendCombatHitsAsync` 統一調用，一次改動全覆蓋。
- **範圍刻意排除**：`ItemUseService.RemoveCaughtMob`（捕捉道具移除怪物的路徑，`V113ChannelConnectionHandler`
  line ~2181）與 `KillMobWithoutRewards`（Monster Carnival Beans/MonsterBomb 自爆路徑）都是不同的
  Java 來源與觸發情境，這次不展開，維持只處理標準戰鬥擊殺死亡流程。

## ⏯️ 接手點

`updateMonsterController`（自動重新分配控制者，觸發於原控制者離開地圖/斷線）與
`switchController`（AUTO_AGGRO 之外的控制權主動轉移場景）仍需要更大範圍的設計（怪物 AI/move
tick 里程碑 M4-2 的一部分），維持不動，留給使用者評估是否要展開成獨立里程碑。

## ✅ 結果與結論

- P020 把 `StopControllingMonster` 整批歸類為「怪物控制權轉移子系統」而判定需要前置設計，這次
  拆開來看才發現 Java 三個觸發點裡有兩個確實需要更大範圍（`switchController`/
  `updateMonsterController`），但第三個（死亡通知）範圍完全獨立、且 MapleForge 既有的死亡流程
  已經具備所有必要資訊，只是沒有讀取——這是本輪（P021-P025）第三次證明「範圍評估要先拆解成
  Java 的個別觸發點分開查證，不能整批用一個籠統標籤（如『控制權轉移子系統』）就判定全部需要
  前置設計」。這個教訓值得記下：下次遇到類似「聽起來像一個大子系統」的候選，先拆 Java 呼叫點，
  逐一查證範圍，可能其中一部分早就可以獨立完成。
