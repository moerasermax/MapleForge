## 🎯 目標（執行前先寫死，過程不偷改）

延續 P033「拆解反作弊籠統標籤」的手法，找到反作弊 3 件裡另一個範圍獨立、可以完整完成的
候選：拾取地上物品的距離異常檢查（Java `InventoryHandler.ItemPickup` 的
`ITEMVAC_CLIENT`/`ITEMVAC_SERVER`）。完成判準：對照 Java 行為補上兩段距離檢查，用戶端回報
距離異常只記錄，伺服器已知距離異常記錄並真的擋下拾取。

## 📋 背景與查證

- 對照 Java `InventoryHandler.ItemPickup`：
  ```java
  final double Distance = Client_Reportedpos.distanceSq(mapitem.getPosition());
  if (Distance > 2500) {
      registerOffense(ITEMVAC_CLIENT);        // 只記錄，繼續往下走
  } else if (chr.getPosition().distanceSq(mapitem.getPosition()) > 90000.0) {
      registerOffense(ITEMVAC_SERVER);
      sendPacket(enableActions());
      return;                                  // 真的擋下
  }
  ```
  兩個分支是 `if/else if`——**互斥**，不是各自獨立判斷：用戶端回報距離已經異常時，完全不會
  再去檢查伺服器已知距離（也就不會因為這個分支被擋下，Java 這裡選擇「只記錄可疑，仍放行」）。
- 查證 MapleForge 現有 `HandleItemPickupAsync`（`V113ChannelConnectionHandler.cs`）：完全沒有
  距離檢查，直接呼叫 `_dropService.TryPickup`。但 `V113DropPackets.ParseItemPickup` 早就有
  解析 `ClientPosition`（用戶端回報座標）卻從未被使用——是典型的「架構就位、資料沒接線」
  缺口（跟 P029 FieldLimitType 同一類）。
- `DropService.TryPickup`（Application 層）已有 `field.Get(dropObjectId)` 這種免鎖 peek 查詢
  可用（`FieldInstance.Get`），不需要新增基礎設施，只要在呼叫 `TryPickup` 之前先查一次掉落物
  座標即可，符合「Java 距離檢查在 `lock.lock()` 之前就先做完 null 檢查」的對照精神。
