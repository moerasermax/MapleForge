## 🎯 目標（執行前先寫死，過程不偷改）

P041/P042 收尾留下的其中一項：現金傳送石（2320000/5040000/5040001/5041000）地圖模式
要求目標地圖必須先在玩家的已註冊傳送石清單裡才能傳送。完成判準：`Character` 補上純
查詢方法，`HandleCashTeleportRock` 接上對應的高級／一般清單檢查。

## 📋 背景與查證

- Java `InventoryHandler.UseTeleRock`：
  `(itemId == 5041000 && c.getPlayer().isRockMap(target.getId())) || (itemId != 5041000 && c.getPlayer().isRegRockMap(target.getId())) || (itemId == 5040004 || itemId == 5041001)`
  ——`5041000`（高級順移之石）要求目標在 `rocks`（10 格、對照 C# `VipRocks`）已註冊清單；
  其餘（`2320000`/`5040000`/`5040001`）要求目標在 `regrocks`（5 格、對照 C# `RegularRocks`）
  已註冊清單；`5040004`/`5041001` 無條件通過。
- 查證確認 `5040004`/`5041001` 在 Java `UseCashItem` 的 `switch(itemId)` 從未出現在會呼叫
  `UseTeleRock` 的 case 清單裡（該兩個 itemId 在整個 `InventoryHandler.java` 只出現在
  `UseTeleRock` 內部判斷式本身，是死路徑），MapleForge 現有的外層 switch
  （`2320000 or 5040000 or 5040001 or 5041000 => HandleCashTeleportRock`）本就不含這兩個
  itemId，因此「無條件通過」分支不需要實作，維持忠實對照。
- MapleForge 的 `Character.cs`（P030 前後建立）已有 `RegularRocks`（5 格）/`VipRocks`
  （10 格）的新增/移除方法，但沒有純查詢的成員檢查方法，只缺這一塊。

## ✅ 結果與結論

- 這次順手發現並修正了 P041/P042 遺留的測試精準度問題：VipRock／MapleLand 阻擋測試
  原本用未註冊的目標地圖，實際上會被「未註冊」擋下而不是被真正要測的那個條件擋下
  （結果剛好一樣所以測試沒有壞掉，但驗證的因果關係是錯的）——這次一併補上註冊前置，
  讓每個測試只隔離驗證自己該驗證的那個規則。
- 傳送石地圖模式的 Java 判斷式至此只剩「大陸比對」（`victim.getMapId() / 100000000`）
  這項，且只出現在玩家導向傳送模式（`mode=1`，目前整段仍是 deferred 狀態），沒有獨立
  的地圖模式副本，暫不需要另開 P-phase。
