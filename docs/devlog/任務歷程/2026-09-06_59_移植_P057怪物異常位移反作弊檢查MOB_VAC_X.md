## 🎯 目標（執行前先寫死，過程不偷改）

反作弊 3 件的第 3 件（完整 CheatTracker 系統）本身太大，但延續 P033/P056「拆解籠統標籤」
的手法，在 Java `MobHandler` 找到另一個範圍獨立的候選：`CheckMobVac_x`（怪物移動 X 座標
單次落差異常，對照玩家操控怪物移動來偵測「吸怪」外掛）。完成判準：非飛行怪物單次
MOVE_LIFE 移動的 X 座標落差超過門檻只記錄，不阻擋，門檻與偵測邏輯忠實對照 Java。

## 📋 背景與查證

- 對照 Java `MobHandler.CheckMobVac_x`：在 `MoveMonster`（MOVE_LIFE）opcode 處理裡，從
  `res`（解析出的移動片段）算出 `endPos`，`reduce_x = abs(startPos.x - endPos.x)`；非飛行
  怪物（`!monster.getStats().getFly()`）且 `reduce_x > 500` 才觸發，用一個計數器
  `chr.getMobVac_X()` 每 10 次才記一次 log 避免洗版，同時有 GM 專屬訊息分支
  （`chr.hasGmLevel(1)`，MapleForge 無 GM 系統，比照既有慣例略過不寫）。
- 查證 MapleForge 現有 `HandleMoveLifeAsync`（`V113ChannelConnectionHandler.cs`）：MOVE_LIFE
  封包解析與怪物移動更新（`mob.MoveTo`）都已存在，`data.StartX`（宣稱起始座標）也已解析，
  純粹缺這段距離異常檢查——同一類「架構就位、資料沒接線」缺口。
- 查證 `MobStats`（Core 領域模型）目前只有合併的 `Mobile` 旗標（`move` 或 `fly` 節點任一存在
  即為 true），沒有單獨的 `Fly` 欄位可用來做飛行豁免判斷。對照 Java
  `MapleLifeFactory`：頂層 `.img` 出現 `fly` 節點就 `setFly(true)` 同時 `setMobile(true)`，
  跟 MapleForge 既有 `mobile = mobImg?["move"] is not null || mobImg?["fly"] is not null`
  是同一個資料來源，只是沒有把 `fly` 單獨存下來。
- **刻意簡化**：Java 用計數器把記錄頻率降到每 10 次一次，純粹是避免洗版，不影響防護邏輯
  本身（這個檢查全程只記錄、不阻擋任何行為）。這次選擇不新增計數器欄位，改成每次觸發都記
  ——省掉一個新持久化欄位的設計成本，且不影響「偵測到異常」這個核心行為的正確性，只是
  記錄頻率跟 Java 不同（已在程式碼註解與此文件明確記下這個刻意偏離）。
