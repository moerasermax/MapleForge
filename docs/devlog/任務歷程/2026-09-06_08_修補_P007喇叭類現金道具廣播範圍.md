## 🎯 目標（執行前先寫死，過程不偷改）

對照 Java `InventoryHandler.UseCashItem`：`5070000`（一般喇叭）是**地圖內**廣播
（`getMap().broadcastMessage`），但 `5072000`/`5073000`/`5074000`/`5076000`/`5077000`（高效能/
愛心/骷髏/物品/三行喇叭）與 avatar megaphone fallback 全部是 `World.Broadcast.broadcastSmega`
＝**跨頻道全服**廣播；MapleForge 目前這些全部走同一條 `MapPackets`→`BroadcastPacketToMapAsync`
（只送同地圖），範圍錯了。完成判準：一般喇叭維持地圖範圍不變；其餘喇叭類現金道具改廣播給**全部
在線玩家**（含自己，比照 Java `broadcastSmegaPacket` 對 `PlayerStorage` 全體廣播不排除自己）；
單元測試覆蓋範圍區分；既有測試不退。

## 📋 背景與假設

- Java 來源逐項核對（`handling/channel/handler/InventoryHandler.java` 1523-1834 行）：
  - `5070000`（普通喇叭）→ `c.getPlayer().getMap().broadcastMessage(...)` = 地圖範圍。**不動**。
  - `5071000` → `c.getChannelServer().broadcastSmega(getMegaphone(...))` = 頻道範圍，但封包格式是
    **plain Megaphone**（不含 ear/channel 欄位）。
  - `5072000`（高效能喇叭）→ `World.Broadcast.broadcastSmega(getSuperMegaphone(...))` = 全服範圍。
  - `5073000`（愛心喇叭）/`5074000`（骷髏喇叭）/`5076000`（物品喇叭）/`5077000`（三行喇叭）→ 皆
    `World.Broadcast.broadcastSmega(...)` = 全服範圍。
  - MapleTV 系列（5075000-5075005）：本服目前 dropMessage「無 MapleTV 可廣播」/stub，維持不動。
- **已知但本次不修的獨立問題**：MapleForge 現有程式把 `5071000` 與 `5072000` 歸在同一個 case
  （`5071000 or 5072000 => HandleMegaphone(..., SuperMegaphone 封包格式)`），但 Java 對 `5071000`
  實際用的是 plain Megaphone 封包格式，不是 SuperMegaphone。這是封包**格式**問題，與本次要修的
  廣播**範圍**問題是兩回事；本次只修範圍（`5071000`/`5072000` 都改成全服廣播，範圍對了），格式
  不對的部分留給下一個專門任務，避免一次改兩件事風險疊加。
- MapleForge 目前是單實例單頻道架構（多實例 M5-6 未啟用），Java 的「頻道範圍」與「全服範圍」在
  這個限制下實質等價（都等於「這個 process 目前所有在線玩家」）。故 `5071000`（頻道範圍）與其餘
  （全服範圍）在本次可以用同一套「廣播給所有在線玩家」機制實作，等多實例真正啟用時才需要再細分
  頻道 vs 全服的邊界（屆時 `IOnlinePlayerRegistry` 大概率也要按 channel 分桶，屬未來工作）。
- `IOnlinePlayerRegistry` 目前沒有列舉全部在線玩家的方法（只有 `FindById`/`FindByName`），這是
  本次要補的基礎設施缺口。
- Java 的 `broadcastSmegaPacket`（`PlayerStorage` 對全體玩家廣播）沒有排除發送者本人的邏輯，故
  喇叭訊息應該連自己都收到（符合真實體感：發喇叭的人自己也會看到訊息）。

## ✅ 結果與結論

- 修正一個真實的廣播範圍 bug：高效能/愛心/骷髏/物品/三行喇叭與 avatar megaphone 過去只送到與
  發送者同地圖的玩家，現在正確送到（本 process 內）所有在線玩家，比照 Java `World.Broadcast.
  broadcastSmega`。
- 這是本次 session（P004→P007）第三次發現「同一種模式的範圍/資料新鮮度缺陷」（PartySearch 的
  stale PartyMember → 隊伍 SILENT_UPDATE/LOG_ONOFF 缺失 → 喇叭類廣播範圍錯誤）——**可轉移心法**：
  MapleForge 早期批次移植時，凡是「這個封包該送給誰」的範圍判斷（自己/同地圖/同頻道/全服），比
  單純的封包格式更容易被簡化過頭，值得在後續清尾時系統性複查一輪所有 broadcast 呼叫點對照 Java
  的實際廣播目標，而不是逐一等使用者回報。
