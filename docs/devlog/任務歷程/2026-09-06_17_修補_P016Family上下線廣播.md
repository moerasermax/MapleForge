## 🎯 目標（執行前先寫死，過程不偷改）

P015 收斂了「線上狀態資料本身」的同步缺口（`_onlinePlayers` 字典成員關係），但 Java 對照組
`MapleFamily.setOnline` 在狀態實際翻轉時還會廣播 `familyLoggedIn` 通知封包給族譜可視範圍內的
其他在線成員——這個封包（`V113FamilyPackets.FamilyLoggedIn`）在 MapleForge 早就存在，但零呼叫者。
完成判準：家族成員上線/下線且狀態確實翻轉時，依 Java 的範圍規則（leader 通知全家族在線成員，
一般成員只通知自己的族譜可視範圍）發送通知；狀態未翻轉（例如短時間內收到兩次登入通知）不重複
廣播；單元測試覆蓋上線、下線、狀態未翻轉三種情況。

## 📋 背景與假設

- Java 來源：`MapleFamily.setOnline`（`handling/world/family/MapleFamily.java:295`）：
  ```java
  public final void setOnline(final int cid, final boolean online, final int channel) {
      final MapleFamilyCharacter mgc = getMFC(cid);
      if (mgc != null && mgc.getFamilyId() == id) {
          if (mgc.isOnline() != online) {
              broadcast(FamilyPacket.familyLoggedIn(online, mgc.getName()), cid,
                  mgc.getId() == leaderid ? null : mgc.getPedigree());
          }
          mgc.setOnline(online);
          mgc.setChannel((byte) channel);
      }
  }
  ```
  `broadcast(packet, exceptionId, cids)` 只送給 `cids`（`null`＝全家族）清單內、目前在線、且不是
  觸發者本人的成員。leader 上下線影響全家族觀感故廣播全體；一般成員上下線只有自己的族譜視窗
  （長輩/晚輩可視範圍，`mgc.getPedigree()`）在乎，故縮小範圍。
- MapleForge 現況：`V113FamilyPackets.FamilyLoggedIn(bool online, string name)` 這個封包建構式
  已存在（應是早期批次移植遺留），但 grep 全專案零呼叫者——上下線的「資料」同步了（P015），但
  「通知」完全没做。
- 修法：`FamilyService` 新增 `SetOnline(Player, bool online, int channel)`，把「更新 `_onlinePlayers`」
  與「判斷狀態是否翻轉＋計算通知對象」合併成一次操作（回傳 `FamilyOnlineStatusChange` record），
  範圍計算重用既有的 `Family.GetPedigreeMembers`（族譜可視範圍查詢，本來就是為 UI 準備的同一份
  資料，語意與 Java `mgc.getPedigree()` 相符）。`V113FamilyHandler` 的 `NotifyLogin`/`NotifyDisconnect`
  （P015 剛加的同步方法）就地改造成 `NotifyLoginAsync`/`NotifyDisconnectAsync`，多做一步：狀態
  翻轉了才呼叫 `_sessions.SendPacketAsync` 廣播。
- 範圍邊界：只補「上下線通知」這一個封包的派送，不動 `FamilyService` 既有的家族操作邏輯（邀請、
  刪除、加成等）。P015 剛加的呼叫點（登入/登出區塊）不需要再改——只是內部實作從「純同步」升級成
  「同步+視情況廣播」，呼叫端簽章從同步方法變成 async（因為現在要送封包）。

## ✅ 結果與結論

- 這是「一個既有但零呼叫者的封包建構式」類型的缺口，與 P013/P014/P015 的「邏輯完全沒寫」不同——
  代表早期批次移植時封包格式已經照著 Java 搬過來，但串接到觸發點這一步被漏掉了。這提示了一個新的
  排查手法：grep 每個 `V113*Packets.cs` 檔案裡的 public 方法，逐一確認是否真的有呼叫者，可能還
  藏著其他類似的「建了但沒接」封包，值得之後開一個專門的 P-phase 掃描。
- `FamilyOnlineStatusChange` 用一個 record 同時帶「是否要動作」+「動作內容」，讓 Adapter 層
  （`V113FamilyHandler`）完全不用知道「狀態要不要翻轉」「範圍怎麼算」這些 Application 層邏輯，
  只管「有變化就照著名單發包」——這個模式（Application 回傳決策結果，Adapter 只管派送）與
  P006 Party 的 `NotifyLoginAsync` 回傳結構一致，是這個專案已經穩定下來的分層慣例。
