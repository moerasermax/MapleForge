## 🎯 目標（執行前先寫死，過程不偷改）

延續 P065 記錄的下一步：把「怪物死亡」跟它出生的 `MobSpawnPoint` 串起來——死亡時要重算
重生點的下次可重生時間、歸還並發額度，否則 `RespawnMonsters`（P065）永遠會覺得這個點還
被佔用，實際上不會有任何怪物真的重生。**仍然沒有接上任何排程器**，`RespawnMonsters` 依然
沒有生產程式碼呼叫它，玩家端完全感受不到差異——這步只是讓「死亡→重生點狀態更新」這條線
補完整，讓 P065 建立的用例真正具備正確運作的前提條件。

## 📋 背景與查證

- 追 Java `listener.monsterKilled()` 的呼叫點（`server/life/MapleMonster.java` 兩處）：都在
  `MapleMonster` 死亡流程的核心方法裡，不分「一般攻擊擊殺」還是「自爆」等其他死法，只要這隻
  怪物物件轉為死亡狀態就會觸發——因為 listener 是註冊在怪物物件本身上的，不是掛在特定攻擊
  路徑上。對照到 MapleForge：`CombatService.ApplyAttack`（一般攻擊擊殺）跟
  `KillMobWithoutRewards`（MonsterBomb 自爆路徑）是目前僅有的兩個「怪物死亡並從 field 移除」
  的地方（`RangedMagicCombatService` 內部也是委派回 `CombatService.ApplyAttack`，不是獨立
  路徑），兩處都要掛上通知。
- 怎麼找到「這隻死掉的怪是哪個重生點生出來的」：`Mob.Definition` 跟
  `MobSpawnPoint.Definition` 本來就共用同一個 `MapMonster` 物件實例（`SpawnMapMonsters`/
  `RespawnMonsters` 建立 `Mob` 時都是直接傳入 `point.Definition`，沒有複製），所以用參照相等
  （`ReferenceEquals`）就能唯一對應，不需要幫 `Mob` 額外加一個「我是哪個重生點生的」欄位——
  維持 `Mob` 這個 Core 領域物件的最小化，不為了這個內部管理用途污染它的公開介面。

## 🔧 實作內容

- **`Maple.Application`**（`CombatService.cs`）：新增私有 `NotifySpawnPointKilled(field, mob)`
  ——掃 `field.SpawnPoints` 找出 `ReferenceEquals(point.Definition, mob.Definition)` 的那個
  （找不到就靜默略過，因為未來其他生怪路徑，例如玩家召喚怪，本來就不該有對應重生點），呼叫
  `point.OnMonsterKilled(_timeProvider.GetUtcNow())`。`ApplyAttack`（`field.Remove` 之後）跟
  `KillMobWithoutRewards`（`field.Remove` 之後）都掛上這個呼叫。

## ✅ 結果與結論

- M4-2 怪物重生切片的邏輯層（P064 資料模型 → P065 生怪用例 → P066 死亡通知）至此走完，
  三塊拼圖都齊了但**仍然沒有任何排程器**——跟掉落物過期切片（P061-063）的分階段節奏完全
  對稱：P061≈P064（資料模型）、P062≈P065（用例）、P063 尚未有對應（排程器接線）。
- 下一步（P067）：接上排程器，讓 `RespawnMonsters` 真正開始執行。可以評估兩個方向——
  (a) 直接在 P063 的 `DropExpiryHostedService` 裡追加一段呼叫 `RespawnMonsters`，讓掉落物過期
  跟怪物重生共用同一個 3 秒 tick（最省事，Java 原版 `handleMap` 本來就是同一個迴圈做兩件事）；
  (b) 趁這個時機把它重構成通用的 `WorldTickHostedService`，讓兩個消費者都掛在同一個排程器
  骨架下但邏輯分開。方向 (a) 更貼近 Java 原版行為（同一次 tick 同時處理掉落物跟怪物），
  且改動範圍更小，傾向優先採用，但留給實際動手那個 P-phase 再拍板。
- 也要注意：怪物重生一旦真正接上排程器，會是繼掉落物過期後第二個**改變伺服器實際行為**的
  P（地圖打完的怪會重新出現）——影響面比掉落物過期大（牽動練功刷怪節奏），排程器那個
  P-phase 完成後應該建議使用者實際跑一次伺服器驗證觀感，而不只是看單元測試綠燈。
