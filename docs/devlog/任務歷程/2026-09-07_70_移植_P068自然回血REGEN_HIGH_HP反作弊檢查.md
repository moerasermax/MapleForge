## 🎯 目標（執行前先寫死，過程不偷改）

延續 P033/P056/P057/P058「拆解 registerOffense 籠統標籤」手法，找到 Java
`PlayerHandler.Heal`（`HEAL_OVER_TIME` opcode，自然回血 tick）的 `REGEN_HIGH_HP` 檢查。
過程中先查證了一件重要的事：這個 opcode（自然回血本身）在 MapleForge 早就完整實作
（`V113StatsHandlers.HandleHealOverTime` → `StatsService.RecoverOverTime` →
`Player.RecoverOverTime`，含 1 秒節流的 `CanRecoverHp`/`CanRecoverMp`），只缺反作弊檢查
這一層——不是之前以為的「整個功能未實作」。

## 📋 背景與查證

- 追 Java `RecvPacketOpcode.HEAL_OVER_TIME` → `PlayerHandler.Heal`：`updateTick` 之後讀
  `healHP`/`healMP`（short），`stats.getHp() <= 0` 整段擋下；`healHP != 0 && chr.canHP()` 才
  檢查跟套用，`check = stats.getShouldHealHP()`，`healHP > check*5` 才
  `registerOffense(REGEN_HIGH_HP, ...)`，回血本身（`chr.addHP(healHP)`）**不受這個檢查結果
  影響，永遠套用**；MP 那一側的 `registerOffense(REGEN_HIGH_MP, ...)` 呼叫在 Java 原始碼裡本身
  就是註解掉的死碼（`//  chr.getCheatTracker()...`），比照不移植。
- 查證 `getShouldHealHP()`：基礎值 10 + 疊加多個特定技能（HP 增幅類，橫跨數個職業）的效果值
  + 坐椅 +150。查證 MapleForge 目前沒有對應的「查詢任意技能效果數值」管線可以逐一對照這些
  技能 id，若要完整移植整條公式，範圍會膨脹成技能效果系統的擴充，不符合這次「反作弊拆解」
  系列一貫的小範圍精神。**刻意簡化**：只算基礎值（10）+ 坐椅加成（150，`Player.ChairItemId`
  已存在可直接讀），略過技能加成——因為這個檢查在 Java 本身也只記錄不阻擋（回血永遠套用），
  簡化公式最壞情況只是讓持有那些技能的玩家偶爾觸發一筆不精確的 log，不影響任何實際遊戲
  行為，風險等級跟 P056/P057 的「只記錄」檢查一致。
- 查證回血本身：`Player.RecoverOverTime`（`Player.Stats.cs`）已經完整對照 Java
  `canHP()`/`canMP()` 的 1 秒節流（`CanRecoverHp`/`CanRecoverMp`，各自獨立的
  `_lastHpRecoveryAtMs`/`_lastMpRecoveryAtMs`）跟死亡擋下（`IsAlive` 檢查對應 Java
  `stats.getHp() <= 0` return），確認這條路徑本身已經是忠實移植，這次真的只補反作弊記錄
  這一小塊。
