## 🎯 目標

延續 P041-043 對現金傳送石的查證，看「玩家導向模式」（`HandleCashTeleportRock` mode=1，
目前整段 deferred）是否可比照 P047 用既有基礎設施接上；同時查證
`V113RepairHandler`（`REPAIR`/`REPAIR_ALL` 實際修理動作）為何從未接進中央 dispatcher，
排除它是否為另一個零呼叫者缺口。

## 📋 查證過程與結論

### 傳送石玩家導向模式（`HandleCashTeleportRock` mode=1）

- 對照 Java `InventoryHandler.UseTeleRock` 的玩家分支：找目標玩家（`getCharacterByName`）
  → 排除 GM／`EventInstance`／楓之島 → VipRock 場地限制 → 高級道具或同大陸 → 用
  `victim.getMap().findClosestSpawnpoint(victim.getPosition())` 傳送到「離目標玩家最近的
  重生點」。
- 查證確認 `IOnlinePlayerRegistry.FindByName` 已存在且直接帶 `Player`（跟 P047 剛建立的
  `MapPlayerEntry.Player` 同一種模式），GM／`EventInstance` 排除依 P022/P046 已確認的
  「MapleForge 尚無 GM／活動副本系統，等同恆為 true」慣例可直接沿用，VipRock／MapleLand／
  大陸比對三個檢查都已有現成寫法（`IsVipRockWarpBlocked`/`IsMapleLand`）可重用。
- **阻塞點**：`WarpAsync`（中央 dispatcher 的唯一傳送入口）只接受 `mapId` +
  `spawnPortalId`（依索引選編號傳送門），沒有「傳送到任意座標附近最近重生點」的能力；
  順手查了 `FamilyWarpTarget.DestinationPosition`（家族召喚功能，同樣是「傳送到別的
  玩家旁邊」情境）以為是既有先例，結果它雖然帶了目標座標，實際消費端
  （`V113ChannelConnectionHandler.cs:1601-1603`／`1621-1625`）仍只用了
  `DestinationMapId` 傳去編號 0 傳送門，`DestinationPosition` 從未真正用上——整個
  MapleForge 目前沒有任何一處真正實作「傳到座標附近最近重生點」，這是比單一功能更底層的
  共用能力缺口，不適合為了單一傳送石情境臨時湊一個。

### `V113RepairHandler`（REPAIR/REPAIR_ALL 實際修理動作）確認為刻意不接

- 全域確認 `V113RepairHandler` 有 DI 註冊（`AddSingleton<V113RepairHandler>()`）但從未被
  中央 dispatcher 建構子注入或呼叫——一度懷疑是另一個零呼叫者缺口。
- 查證 Java 原始碼 `src/properties/recv.properties` 第 101-102 行：
  `#REPAIR_ALL = 0x72` / `#REPAIR = 0x73` **本身就被註解掉**——這個 v113 版本的 Java
  server 自己也沒有路由這兩個收封包 opcode。`V113RepairPackets.cs` 頂端的既有註解
  「Java recv.properties comments these out」原本就精準記錄了這件事。
- **結論：現狀正確，不需要修。** 這是「對照 Java 神諭應該保持不接線」的案例，不是遺漏——
  記錄下來避免未來 session 誤判成零呼叫者缺口重新查一次。

## ✅ 結果與結論

- 傳送石玩家導向模式的真正阻塞點不是「找不到玩家」（`IOnlinePlayerRegistry` 早就夠用），
  而是 MapleForge 的傳送 API 本身只支援「傳送門索引」，沒有「座標最近重生點」這個更底層
  的能力——這個能力同時也是讓家族召喚功能的 `DestinationPosition` 真正生效的前提，兩個
  功能共用同一個缺口，適合合併成一個獨立、更大範圍的 P-phase（新增
  `MapData` 重生點查詢 + `WarpAsync` 支援座標入口），不適合在本輪臨時做小範圍近似。
- `V113RepairHandler` 未接線屬於「查證後確認現狀正確」，非缺口，本次順手排除一個容易被
  誤判的候選。
- 無程式碼異動。
