## 🎯 目標（執行前先寫死，過程不偷改）

系統性重掃全部 `V113*Packets.cs` 的 public static 方法，找零呼叫者候選（沿用 P016-P023
已驗證有效的方法論）。找到 `V113RepairPackets.RepairWindow`（`SendRepairWindow` 封包，
opcode 0xD5）已經寫好編碼但從未被任何地方呼叫。完成判準：對照 Java
`NPCConversationManager.sendRepairWindow` 接上 `cm.sendRepairWindow()` NPC 腳本 API，
比照 P021/P022/P023 已驗證的橋接模式。

## 📋 背景與查證

- 全域 grep 掃描腳本重新確認方法論可靠性：初版腳本對「同檔案內以 dispatcher pattern
  （如 `Encode`/`EncodeResult` 這種 union-switch 入口）間接呼叫」與「以 method group 形式
  傳遞（如 `.Select(V113SkillPackets.UpdateSkill)`，不含括號）」都會誤判為零呼叫者，
  兩次修正後排除假陽性，剩餘候選人工逐一核對。
- Java `scripting/NPCConversationManager.java:1107` 的 `sendRepairWindow()` 呼叫
  `MaplePacketCreator.sendRepairWindow(npc)`，是暴露給 NPC 腳本的 `cm` API（跟
  `increaseGuildCapacity`/`disbandGuild` 同一類）。
- 確認真的有 NPC 腳本使用：`MapleStory_Server/scripts/npc/2080000.js`（神木村武器製造 NPC）
  第 238 行 `cm.sendRepairWindow(); cm.dispose();`——選擇「修理裝備」對話分支後呼叫，
  腳本自己接著呼叫 `cm.dispose()` 結束對話（不像 `cm.openStorage` 那樣需要自動結束）。
