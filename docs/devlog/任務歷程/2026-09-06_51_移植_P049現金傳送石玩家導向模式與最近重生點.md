## 🎯 目標（執行前先寫死，過程不偷改）

P048 查到「座標最近重生點」是共用底層缺口，卡住現金傳送石玩家導向模式（mode=1，整段
deferred）與家族召喚的精確落點。這次先補上最小可行的那塊：`MapData` 的最近重生點查詢，
並用它把傳送石玩家導向模式做完整（家族召喚的 `WarpAsync` 座標入口留給後續，見結論）。

## 📋 背景與查證

- 對照 Java `MapleMap.findClosestSpawnpoint(Point)`：在該地圖所有 `pt=0/name="sp"` 的
  出生點裡，取歐氏距離最近的一個。
- `MapData`/`MapPortal` 早就有 `IsSpawnPoint`（`Type==0 && Name=="sp"`）與依序號取出生點
  的 `GetSpawnPoint(byte)`，只缺「依座標找最近」這個查詢，補上即可，不需要新資料模型。
- 對照 Java `InventoryHandler.UseTeleRock` 玩家導向分支，逐條核對可重用的既有基礎設施：
  - 找玩家：`IOnlinePlayerRegistry.FindByName`（P047 建立的「registry 直接帶 Player」模式）。
  - GM／`EventInstance` 排除：MapleForge 尚無 GM／活動副本系統，依 P022/P046 已確認的
    慣例視為恆不成立，程式碼裡略去不寫（不是遺漏，是忠實對照「這個分支永遠不會擋」）。
  - 楓之島排除：`IsMapleLand`（P042 已有）。
  - VipRock 場地限制：`IsVipRockWarpBlocked`（P041 已有，本就支援任意目標地圖 ID）。
  - 大陸比對／高級道具豁免：`mapId / 100_000_000` 整除比較 + `itemId == 5041000` 直接
    通過（`5040004`/`5041001` 因不在外層 switch 的 case 清單裡維持不處理，同 P043 結論）。

## ✅ 結果與結論

- `MapData.GetClosestSpawnPoint` 是純函式、零外部依賴，補上後同時也讓家族召喚
  （`FamilyWarpTarget.DestinationPosition`）未來要接上精確落點時有現成工具可用——但
  這次刻意只動傳送石這一條路徑，`WarpAsync`／家族召喚呼叫點維持不動，避免同一個
  P-phase 動兩個獨立功能。
- `5040004`/`5041001`（免大陸限制的道具）延續 P043 結論：這兩個 itemId 從未出現在外層
  `switch` 的 case 清單裡，屬於 Java 端亦不可達的路徑，程式邏輯裡保留判斷式（
  `itemId == 5041000`）已涵蓋玩家導向模式唯一可達的高級道具豁免，不需要額外為不可達
  itemId 寫分支。
