## 🎯 目標（執行前先寫死，過程不偷改）

任務追蹤.md M3「同圖內部傳點 USE_INNER_PORTAL(0x5F)」條目殘留 TODO：「距離反作弊...仍待移植」。
這項目過去被歸在 P004 記錄的「反作弊 3 件」裡，跟其他兩件一起被判定需要前置研究，但拆開來看
這一件的 Java 實際行為非常單薄——完成判準：對照 Java 補上「跟宣稱使用的傳送門距離過遠時記錄
警訊」，不需要建置完整的違規累積/自動封禁系統（那才是真的需要前置設計的部分）。

## 📋 背景與假設

- Java `PlayerHandler.InnerPortal`（`handling/channel/handler/PlayerHandler.java:1330-1349`）：
  找到 portal 後，`else if (portal.getPosition().distanceSq(chr.getPosition()) > 22500)` 才呼叫
  `chr.getCheatTracker().registerOffense(CheatingOffense.USING_FARAWAY_PORTAL)`——**這一行呼叫
  完全不影響後續流程**：無論距離是否過遠，`chr.getMap().movePlayer(chr, new Point(toX, toY))`
  都無條件執行。換句話說，Java 這裡做的事只是「記一筆」，不是「擋一次」。
- `CheatTracker`/`registerOffense` 是 Java 端一個獨立、貫穿多處呼叫點的違規累積系統（達到閾值後
  觸發自動封禁/警告），這才是「反作弊 3 件」真正需要前置設計的部分——但**這次的任務只需要「記錄
  這一次違規發生了」，不需要重建整個累積/封禁系統**。MapleForge 目前完全沒有這類系統，若要完整
  對照 Java 的 `CheatTracker` 需要一個新的橫切服務（記錄各類違規、按帳號累計、觸發後續動作），
  這次刻意只做「偵測+記錄」，用既有的 `ILogger` 基礎設施（`_log.LogWarning`，這個 handler 到處
  都在用），不新建任何違規累積的資料結構或持久化。
- `22500` = 150² —— Java 用平方距離比較（省開根號），MapleForge 已有 `Position.DistanceTo`
  （開根號版本），但為了跟 Java 的整數精度完全對齊（避免浮點開根號在邊界值產生誤差），這次
  改用同樣的整數平方比較，不呼叫 `DistanceTo`。

## 🔧 實作內容

- **`Maple.Adapters.V113`**（`V113ChannelConnectionHandler.cs`）：
  - 新增 `internal static bool IsFarFromPortal(MapPortal portal, Position position)`：對照 Java
    `distanceSq(...) > 22500` 的整數平方距離比較（`(long)dx*dx + (long)dy*dy`，用 `long` 避免
    座標極端值時的 `int` 溢位，雖然實務上地圖座標不會到那個量級，但求穩）。
  - `HandleUseInnerPortalAsync`：找到 portal 後、`MoveTo` 之前呼叫 `IsFarFromPortal`，為真則
    `_log.LogWarning(...)`（含玩家名稱、當前座標、傳送門名稱與座標，供人工事後查閱）——**不擋
    `MoveTo`**，忠實對照 Java「只記錄不阻擋」的行為。
